- # Fit-Agent 产品需求文档

  ## 1. 项目背景与求职目标

  Fit-Agent 主要用于个人求职、简历展示和面试演示。项目重点不是堆叠健身功能，而是在一个真实的垂直领域中，展示企业级 Agent 工程化落地和完整 Web 产品设计能力。

  希望重点体现的技术能力包括：

  - 上下文压缩与长会话延续；
  - Prompt Cache 与调用成本观测；
  - 单 Agent ReAct 循环与工具调用；
  - 会话记忆和长期业务记忆管理；
  - 健身垂直领域规则与安全边界；
  - 前后端完整产品体验；
  - Agent 行为测评。

  项目参考 `pi-coding-agent` 的 Agent Harness 设计，并将需要的能力以 Python 实现。上下文压缩可以作为核心技术亮点，在成熟设计基础上增加少量健身领域扩展。

  ## 2. 产品定位

  Fit-Agent 是一个本地自部署、单用户的智能健身计划、训练打卡与复盘 Web Agent。

  用户可以通过自然语言与 Agent 交流，由系统完成训练建档、计划生成、今日训练指导、训练记录整理和阶段复盘。系统只提供训练辅助建议，不进行伤病诊断，也不替代医生或其他专业人员。

  ## 3. 目标用户

  首版面向希望进行规律增肌或基础力量训练，并愿意记录训练过程的个人用户。

  用户可以是：

  - 有少量训练经验，希望获得稳定计划和渐进建议的人；
  - 没有完整历史记录，需要先完成动作负荷校准的人；
  - 希望通过自然语言快速打卡并查看进步趋势的人。

  ## 4. 核心使用流程

  ```text
  配置模型
  → 完成建档与安全筛查
  → 生成并确认训练计划
  → 查看今日训练与状态调整
  → 自然语言打卡
  → 确认结构化记录
  → 确认需要接回时：轻量接回引导（用户主动声明，或训练间隔提示后确认；条件分支）
  → 查看训练复盘和进步趋势
  ```

  Agent 应在不同会话之间记住用户已确认的档案、限制、当前计划和训练历史。长对话发生上下文压缩后，核心事实仍应保持一致。

  ## 5. 功能需求

  ### 5.1 模型配置与隐私提示

  - 用户可以配置本地模型或云端模型。
  - 界面明确展示当前使用的是本地模型还是云端模型。
  - 使用云端模型时，系统说明哪些训练和健康文本会发送至云端。
  - 未配置可用模型时，系统展示配置指引，其他 Agent 功能不可使用。

  ### 5.2 首次建档与安全筛查

  用户首次使用时通过对话提供以下信息；对话与 Agent 是唯一业务变更发起入口，不提供独立建档表单。Agent 生成结构化草稿后，用户可在草稿卡中轻量纠错，最终点击确认并通过后端校验后才保存为正式档案：

  - 训练目标和训练经验；
  - 每周训练频率；
  - 单次可用时长；
  - 可用器械；
  - 已知动作限制；
  - 当前身体状态和红旗症状。

  系统行为：

  - 信息缺失时继续询问，不自行补造。
  - 普通动作限制经用户确认后长期保留。
  - 出现胸部异常不适、晕厥、异常气短、锐痛、麻木、放射痛等红旗症状时，不生成常规训练处方，并建议线下专业评估。
  - Agent 不诊断具体疾病，不自动新增或解除永久禁忌。

  ### 5.3 训练计划生成与确认

  首版内置一种计划模板：三分化 PPL（示例如下）。不将 PPL 写死，便于后续扩展五分化等其他模板

  三分化训练示例：**推 / 拉 / 腿（PPL）**

  - **推日**：胸、肩前/中束、肱三头 → 卧推、哑铃肩推、双杠臂屈伸
  - **拉日**：背、肩后束、肱二头 → 引体向上、杠铃划船、面拉
  - **腿日**：股四、腘绳、臀、小腿 → 深蹲、罗马尼亚硬拉、腿屈伸

  计划展示：

  - 计划开始日期和复核日期；
  - 每周训练安排；
  - 每个训练日的动作顺序；
  - 工作组、次数区间和目标 RIR；
  - 动作对应的渐进方式；
  - 计划当前状态和版本。

  规则：

  - 计划先作为草稿展示，用户确认后才正式启用。
  - 同一时间只存在一个当前计划。
  - 修改计划时保留历史版本，不静默覆盖，正式版本的处方内容不可原地修改。恢复旧计划内容时生成新版本并关联来源版本，按最新条件重新校验、确认，不重新激活旧版本。
  - 系统在确认前检查训练频率、单次时长、器械条件、动作限制和重复动作冲突。
  - 首版只提供带复核节点的训练计划块，不实现复杂的周期阶段和自动跨周期切换。

  ### 5.4 起始重量与动作渐进

  - 有可信历史记录时，计划可以参考用户过去的训练负荷。
  - 没有可信记录时，系统不得猜测重量，而是将动作标记为需要校准，并提供逐级试重、通过标准和停止条件。
  - 每个动作采用与自身类型匹配的渐进方式。
  - 双重渐进只适用于具有稳定负重和次数区间的动作。
  - 计时、等长、技术、自重、有氧和反向负重动作不强制使用双重渐进。
  - 符合加重条件时，只建议采用器械允许的最小增量。

  ### 5.5 当次及后续训练安排与状态调整

  用户训练前后可以报告睡眠、疲劳、酸痛、训练意愿和身体状态；也可以训练结束后反馈，用于制定未来几天的训练安排，不限定为当天训练指导。

  - 每次安排明确对应训练日期或训练次序，绑定具体计划版本与训练日，保存目标和已接受调整的快照；实际训练记录与安排分别保存。
  - 临时调整只影响对应训练安排，不改长期计划；长期调整和接回方案仍形成新计划版本。未来安排使用时仍须按最新限制和红旗状态复核。
  - 用户点击确认接受安排或调整时立即落盘，并保存真实接受时间；与草稿提交、领域复核及 `context_version +1` 同事务完成，重复确认幂等。不得等打卡或补录时再补写为“当时已接受”。
  - 训练发生时间与系统接受、记录、更正确认时间分别保留；事后反馈可以影响后续安排，不能倒改已发生训练的对照标准。
  - 日程与完成率分母在训练日到达（或该次已确认完成／漏练）时锁定，不能删除或改期洗掉漏练；未来尚未锁定的安排可经确认换日或删减，不改变已锁定部分。
  - 日程锁定不等于当次处方锁定：当天仍可在执行相关训练前确认减组等调整，接受时立即落盘，不得事后倒改。

  | 状态       | 系统行为                             |
  | ---------- | ------------------------------------ |
  | 正常       | 执行原计划                           |
  | 一般状态差 | 建议减少一组或目标 RIR +1，二选一    |
  | 明显状态差 | 提供最低训练版或建议休息             |
  | 红旗症状   | 不生成常规训练处方，建议线下专业评估 |

  普通调整必须说明原因，并允许用户接受或拒绝。红旗阻断不能由 Agent 自行解除。中断后首次训练，接回方案（§5.12）优先于当日状态调整；状态正常也按接回档执行，不能直接跳回中断前处方。

  ### 5.6 自然语言训练打卡

  用户可以输入类似：

  > 今天卧推 60kg 做了 3 组，每组 8 次，最后一组还剩 2 次余力。

  系统将其整理为可确认的结构化草稿，包括：

  - 动作及器械变式；
  - 每组重量和次数；
  - 用户明确报告的 RIR；
  - 用户明确报告的动作质量；
  - 热身组和工作组；
  - 无法识别或存在歧义的信息。

  规则：

  - 用户未明确提供的 RIR 和动作质量保持为空。
  - 相似动作名称统一匹配到标准动作，同时向用户展示匹配结果。
  - 存在歧义时必须询问用户，不自行选择。
  - 用户确认后才保存为正式训练记录。
  - 重复确认同一草稿不得产生重复记录。
  - 支持一天多练，每次训练有独立身份，日期不作为唯一身份；补充同次训练与新增另一次训练必须区分，有歧义时在确认卡前询问，不自动拆分训练。
  - 同一次安排的多次反馈最多贡献一次计划完成；不建设早晚训练模板或复杂排程。
  - 草稿、待补全训练记录不参与 PR；补全并经用户确认成为正式有效记录后自动纳入，无需另行确认“纳入 PR”。缺 RIR 本身不阻止记录正式确认或重量／次数 PR；Agent 复盘报告是否完成不影响 PR。
  - 记录关联可信的当次安排快照，不随后续计划修改而变化；无可信安排时允许不关联计划，不强行套用当前计划或补造目标。
  - 无对照安排的记录仅作为“历史表现数据”，不得作为“执行度证据”，Agent 后续复盘同样遵守。
  - 历史更正通过对话生成草稿并确认，保留同一次训练的完整修订版本、修改前后内容、确认时间与来源草稿，不新增训练次数；整次误录可确认作废，不物理删除历史。

  #### 待补全记录转正式

  采用“实际事实可明确解释即可”，不要求填满所有主观字段，不做组级部分提交：必填事实完整 + 用户确认最终草稿 + 后端校验通过 = 整条记录转正式。

  | 内容 | 转正式要求 |
  |---|---|
  | 训练日期 | 明确实际发生日期；“今天”等相对日期须解析并在草稿中显示具体日期 |
  | 训练归属 | 明确新增还是补充／更正；目标不唯一时必须询问 |
  | 动作身份 | 标准动作及必要器械变式匹配明确 |
  | 组类型 | 最终草稿明确热身组或工作组；未说明时不得静默认定，必须展示并由用户确认 |
  | 实际完成数据 | 每个动作的实际组数及每组次数／时长明确；热身摘要按下述例外处理 |
  | 计划关联 | 可空；一旦关联，必须准确匹配对应安排 |
  | 用户确认 | 确认最终草稿且后端校验通过，沿用版本检查与原子提交规则 |

  - 外加负重次数型：组数、每组次数、重量、单位及负重口径明确。
  - 自重次数型：组数、每组次数明确，不虚构 0kg。
  - 计时型：组数、每组时长及单位明确，不强填次数或 RIR。
  - 当前不建设器械辅助／配重抵消的“辅助负重型”；朋友人工辅助是单组执行信息，不是动作记录类型。
  - 热身只报告“递增至 60kg”等摘要时可保留原文，不强迫补齐逐组数据，但不纳入精确组次统计。
  - 训练反馈可选，确认卡可主动询问，不作为转正式门槛；RIR、动作质量、中断原因、辅助次数允许为空。“力竭”或“有人辅助”保留原意，不擅自生成 RIR。
  - 未提疼痛表示“未报告”，不能写成“无疼痛”；明确疼痛时保存事实并触发既定安全处理，事实记录不等于训练推荐。
  - 没有体感反馈时，依据目标、既定渐进方式及可信记录提出调整，不把未报告视为正常或轻松，不因缺反馈默认加重；计划变更仍须确认。
  - 正式记录不等于完成一次计划训练，完成率仍按 §5.8 的独立条件计算。补全后仍须用户确认，不自动提交；更正草稿未确认前，旧正式版本仍有效。

  #### 人工辅助与保护

  - 采用异常申报制：未提辅助时，最终确认草稿显示“无辅助”，用户确认后按独立完成记录，确认前不作为正式事实。不要求对每组额外询问是否有人辅助。
  - 用户只说“辅助”而含义不明确时，继续询问是旁边保护还是实际接触、发力帮助完成动作，不自行归类。
  - 独自完成，或有人旁边保护但全程不碰杠铃、未发力帮助完成动作，按独立完成；有人实际帮忙深蹲起立、卧推推起等，标记“有辅助”。
  - 人工辅助组仍可成为正式工作组，计入实际工作组数及总次数，并明确标注辅助；重量记录实际器械重量，辅助次数知道则记录，不知道可空，不估算朋友承担的重量。
  - 辅助组不参与普通重量／次数 PR，不设置辅助 PR，也不自动拆出独立完成次数计算 PR；辅助标记不单独阻止转正式或主导计划调整，不自动推导 RIR、强度匹配或加重条件。

  ### 5.7 动作限制与动作替代

  - 用户可以限制某个具体动作，也可以限制深蹲、髋铰链、水平推等动作模式。
  - 训练计划不得包含已确认限制所覆盖的动作。
  - 当动作不可用、器械缺失或用户拒绝某个动作时，Agent 可以提供符合相同训练目的的候选替代动作。
  - 替换结果必须再次由用户确认。

  ### 5.8 训练统计与复盘

  首版展示：

  - 计划工作组；
  - 已完成工作组；
  - 符合处方目标的工作组（以当次安排快照为准，不直接按计划版本判定；无对照安排时不判定）；
  - 按计划版本与计划周 Wn 统计的训练完成率；
  - 同一动作及器械变式的最高训练重量；
  - 同重量下的最高次数；
  - 数据最后更新时间。

  工作组判定与统一状态：

  - 保留组数，展示名称为“符合处方目标的工作组”，用于说明实际表现是否符合当次处方，不代表动作技术、安全性或训练效果合格，也不能单凭该数量自动加重。
  - 工作台与复盘沉淀共用“符合目标／未符合／待补全”三种组级判定状态及同一计算结果，一一对应；原“信息不足”统一称为“待补全”，不另设同义状态。
  - 首版展示三桶组数，不额外展示合格组百分比。先检查是否有已知目标未满足：有则为“未符合”，可同时提示缺失字段；否则缺少必要判定信息时为“待补全”；全部目标满足时为“符合目标”。不能仅因缺失信息判为未符合。
  - 无对照安排、额外组或不适用次数＋RIR 的训练不进入这三桶，单独展示实际表现，不要求补造不存在的目标。
  - 组级判定与整条训练记录是否正式有效是不同维度：正式记录中的组可因缺 RIR 在处方判定上“待补全”，但其已确认重量和次数仍可参与 PR；整条记录处于草稿或待补全时不参与 PR。
  - RIR 采用处方明确给出的接受区间，包含端点，不另加隐藏容差；确认的单值目标按同值上下界处理，不能在复盘时改写。次数同样按已确认区间判定，超过上界也不属于符合目标，但不代表该组无效。
  - RIR 输入接受非负有限数值，包括小数，不自动取整；负数、非有限数值不能通过校验。处方优先使用整数或明确区间，不从模糊语言推导小数，模糊表述保留原文并询问，未明确的结构化 RIR 保持为空。

  完成率与计划周：

  - 采用按训练次数的口径：该版本、该计划周内已完成的计划训练次数 ÷ 截至当前已到训练日期的应训练次数。休息日和未来未到日期的安排不进分母，漏练保留；整周安排次数可另外展示，不能只从已有打卡推算分母。
  - 用户在正式记录中明确确认本次训练已完成，且至少包含一个实际工作组，才计入完成次数；完成不等于全部工作组符合处方目标。同一次安排最多计一次，额外训练不增加计划完成率。
  - W1 为计划版本开始日期起连续 7 天，W2 为随后 7 天，以此类推。完成率与训练复盘按计划周 Wn，不使用全局“周一至周日”口径；步数、体重的自然周口径不因此扩展为首版新增功能。
  - 新计划版本开启独立统计区间，不继承旧计数；旧版本连同历史完成率归档，不迁移、不合并，但仍允许真实记录更正并重算。此处仅为统计分段，不建设复杂周期系统。
  - 没有应训练次数时显示“暂无”，不显示 0% 或 100%。
  - 事后实际补练属于额外训练，展示实际表现，不改变原漏练及其分母；当天实际完成但后来才补录属于历史事实更正，不与事后补练混淆。

  PR 纳入规则：

  - 仅使用正式有效记录的最新修订中的可比较、独立完成工作组；草稿、待补全训练记录、作废记录、旧修订、热身组、回归期记录及人工辅助组均不参与。独立完成包含有人旁边保护但全程未接触、未发力帮助完成动作的情况。
  - 例如先独立完成深蹲 100kg，一周后在他人实际帮助下完成 110kg，PR 仍为 100kg；若确认只是旁边保护、全程不碰杠铃且独立完成，则 110kg 在满足其他 PR 条件时可更新纪录。
  - 无计划关联的正式有效记录可贡献 PR，但不能作为执行度证据；缺 RIR 不阻止已确认重量、次数参与 PR。
  - 同一动作、器械变式和负重记法分别比较；单位可换算，单只哑铃重量与双只总重不能直接混比。
  - 最高重量须有至少一次明确完成的次数；同重量最高次数取单组，不累计多组。
  - 自重、计时、反向辅助负重不套用“重量越大越好”的 PR；首版保存实际表现，不新增特殊 PR 算法。

  复盘规则：

  - 图表和数值由确定性计算结果提供。
  - Agent 负责解释表现、指出缺失信息并给出下一步建议。
  - Agent 不得修改统计数值，也不得补充没有数据支持的因果关系。
  - 杠铃、哑铃、史密斯机等动作变式分别统计 PR。
  - 首版不计算估算 1RM，也不将 `重量 × 次数` 总和直接当作进步指标。

  - 统计仅使用每次训练最新有效的确认版本，新增、更正或作废后重算受影响数据，并显示数据更新时间；旧修订不得重复计入。
  - 已生成复盘文本不静默改写；依据数据变化后标记已变更，允许重新生成。

  防污染规则：接回期训练标注为“回归期”，不进入常规“连续进步／处方目标符合情况”的对比口径（首版不展示合格组百分比），也不计入 PR 类统计；实际工作组仍展示，按接回安排单独计算完成情况，不混入常规训练对比。用户确认恢复常规计划内容所形成的新版本后，后续训练才恢复常规口径，不按训练次数自动结束接回期。既有回归期标记随训练历史保留，不因计划切换而重新并入上述统计；标记录错只能经历史更正确认修正。

  ### 5.9 会话记忆与恢复

  - 用户可以继续之前的会话。
  - Agent 记住已经确认的用户档案、动作限制、当前计划和训练记录。
  - 长对话需要压缩时，快速完成用“已整理上下文”toast 提示，3 秒自动消失；明显等待时“正在整理上下文”常驻至整理结束。可自动恢复的失败不报错，展示层只说明确定的影响，不自行宣布任务失败。
  - 压缩后，当前目标、计划版本、安全限制和待确认事项不能丢失。
  - 用户可以纠正 Agent 引用的错误信息，确认后的更正用于后续对话。

  ### 5.10 回答展示与运行恢复（2026-09-07 已确认）

  面向普通用户，仅展示回答、草稿、压缩提示、可理解的失败原因及必要运行状态；不建设原执行轨迹与运行指标面板。

  - 回答实时流式展示，分批保存部分内容；取消或失败后保留已保存部分并标注未完成，最后尚未落盘的片段允许丢失，不承诺逐块恢复。
  - “依据与说明”随结果展示真实来源、引用及简短说明，可折叠，无内容不展示空区域；不独立流式化，不展示原始或隐藏思维链，不编造处理过程。
  - Run 展示状态为“处理中、已完成、已取消、未完成”。“未完成”对应失败终态，附可理解原因，不再等待；“已取消”为独立终态。手动重试创建新 Run，不续跑旧 Run。
  - 草稿已持久化才通知就绪；Run 已完成不表示草稿已确认生效。当前草稿状态以业务接口为准，不以历史通知为准。
  - 草稿首次确认在事务内同时校验业务基线版本与用户看到的草稿修订版本，拒绝确认已被修改的内容，并复查领域规则；已提交草稿重复确认仍返回原结果，已丢弃草稿不得提交。纠错、确认、丢弃走业务接口，不扩展全站事件总线。
  - 断线仅提示连接中断、正在恢复，不取消、不重跑 Agent，不直接判为失败。断线或刷新后加载已保存会话内容、Run 和相关草稿当前状态，替换本地展示，不重复拼接。
  - Run 仍执行则轮询当前已保存内容与状态到终态，本次不再接回 SSE；不保证每段中间输出或历史通知重放。重启中断显示“未完成”及原因，保留已保存内容和草稿，不自动恢复执行。
  - 心跳不显示在聊天里：15 秒无业务事件发送 heartbeat；收到业务事件或心跳更新接收时间，45 秒无事件或连接报错则关闭 SSE 转查询。查询失败按 1、2、4、8、15 秒退避，成功恢复正常轮询；页面恢复可见立即检查当前状态，终态或卸载清理连接与计时器。
  - 工具轨迹、Token/Cache 等指标保存在后台供排错与测评，不意味着前端需要展示；密钥不得进入事件、日志及错误详情。

  验收：断线或刷新后不重复拼接、不重跑；取消、失败或重启后仍能查看已保存内容与草稿；过期草稿修订确认被拒绝，重复提交保持幂等；快速压缩 toast 3 秒消失，长等待提示持续到整理结束。技术事件与时间参数以 PLAN.md 已拍决策为准，本节不授权实现。

  ### 5.11 动作内容与本地媒体

  - 首版只提供完成训练计划所需的一组核心动作。
  - 只有经过检查并标记为可用于计划的动作，才会被 Agent 主动推荐。
  - 动作别名、器械变式和负重方式必须能够区分。
  - 用户可以选择本地动作媒体目录，用于展示动作图片或 GIF。
  - Fit-Agent 不内置或再分发 `exercises-dataset` 的图片和 GIF。

  ### 5.12 训练中断与接回

  - 触发方式（MVP 不做后台自动检测和主动提醒推送）：
    1. 用户主动说“重新开始”“中断回归”等，直接进入接回评估。
    2. 用户发起今日训练等训练相关操作时，系统根据已确认训练记录计算训练间隔。距最近一次训练不少于 7 天时，仅提示用户确认是否属于训练中断；用户确认后才进入接回评估，不自动修改计划。没有已确认训练记录时不判定为中断，按 §5.4 进入校准。
  - 7 天阈值作为可配置的产品约定，不宣称具有医学依据，Agent 不得自行修改。
  - 判定输入（复用已有数据，不新造概念）：中断时长、中断原因（可选）、当前症状与恢复（复用 §5.2 身体状态、红旗症状）、可用时间或器械是否变化。
  - 输出：
    1. 接回处置结果共四种：正常接回、降级接回、最低任务、建议休息或线下专业评估。红旗症状直接进入“建议休息或线下专业评估”，接回判定无权解除 §5.2 的红旗阻断。
    2. 可执行接回方案共三档：正常版保留原计划结构，但负荷仍按本节铁律重新确定；降级版的主项更保守并减少 1 组；最低版只保留启动活动和一个主要动作模式，约 10–20 分钟。前三种处置结果分别生成对应方案；“建议休息或线下专业评估”不生成训练处方。
    3. 为前三种可执行结果提供未来 3–7 天的简单日程。
  - 铁律：不补课、不进行惩罚性训练；不照搬中断前重量（以最近确认记录为上限按保守比例降载，无记录则按 §5.4 校准）；接回方案作为新计划版本产出，遵守 §5.3“不静默覆盖”；病后恢复必须由用户明确表示已获专业允许，才可进入普通接回，否则只给最低活动建议或转介。

  ## 6. 首版范围边界

  首版不包含：

  - 完整训练周期阶段和自动跨周期切换；
  - 自动猜测新用户起始重量；
  - 医学诊断、康复处方或自动永久禁忌；
  - 估算 1RM、MRV或训练量地标；
  - 穿戴设备和 HRV；
  - 全量动作数据集和多语言支持；
  - 多用户、账户系统或公网服务。
  - 后台自动中断检测与主动提醒推送（训练间隔只在用户发起训练相关操作时同步计算；达到 7 天阈值仅提示确认，不直接判定中断或修改计划）；
  - 医疗分级康复路径（病后/术后恢复需要专业允许，系统只转介不规划）；
  - 接回完成后自动恢复原计划的自动化（由用户经复盘确认，基于原计划内容生成并启用经过最新条件校验的新常规版本，不重新激活旧版本）。
