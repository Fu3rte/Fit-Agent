## 1. 目标与阶段关系

Stage 2 不是仅增加 API，而是用 Stage 1 已有档案实现一条真实的「保存草稿 → 查询与纠错 → 确认 → 原子落盘」链路，再提供前端可调用的业务接口。

| 阶段 | 责任 | 本阶段与其交界 |
|---|---|---|
| Stage 1：业务域骨架 | 档案、限制、动作身份与确定性校验 | 复用既有领域规则、内部写入和统一版本载体 |
| **Stage 2：草稿与事务** | 草稿生命周期、Diff、修订、档案确认、幂等、过期拦截及 API | 用真实档案数据验收，不预建计划域或通用插件框架 |
| Stage 3：核心业务 | 计划、日程、训练记录、更正、统计 | 接入共用事务；实现并验收真实「档案＋计划」组合提交、日程联动和安排接受即落盘 |
| Stage 4：Agent 运行时 | 对话生成草稿、Run、取消、SSE、模型重算 | 调用既有业务能力；实现一键重算与关联新草稿，不获得直接正式写入权限 |

**完成 Stage 2 不等于完成第 01 章所有验收项。** 本阶段没有真实对话生成草稿入口；自动化通过内部应用层准备草稿，再调用真实 HTTP 接口验证查询、纠错与确认。不得据此声称聊天闭环已打通。

## 4. 核心实现约束

### 4.1 草稿与生成基线

- 草稿仅有 Pending／Committed／Discarded；过期是基线冲突，不新建持久化生命周期状态。
- 最小数据包含：身份、档案草稿内容、来源关联、`base_business_version`、revision、生成基线与拟议结果快照、状态、提交凭据及必要时间。
- 来源关联现有会话／Run 身份；内部调用不得凭空伪造一次真实模型执行。自动化的来源数据在测试库准备。
- `base_business_version` 来自生成输入读取时的同一业务快照，不能在保存时改取最新版本。生成期间发生正式提交，仍保存原基线并在首次确认时拦截。
- 纠错只修改 Pending 草稿，成功后 revision 递增并重算拟议结果与 Diff；保留原业务基线，不自动重基到最新正式数据。
- Diff 由后端根据快照计算，不信任客户端传入的 before、after、版本、状态或提交结果。未知、明确否认和已知事实不能混为默认值。
- `parent_draft_id` 与计划草稿补丁职责按第 01 章保留为后续接入契约；本阶段不制造重算记录或计划草稿。未来需要的存储字段可随对应阶段增量迁移，不预建业务内容。

### 4.2 首次确认与重复确认

确认请求只提交草稿身份及用户所见 revision，不携带一份可替换最终草稿的业务内容。确认在唯一连接、唯一锁、同一事务内依次执行：

1. 读取草稿；已 Committed 返回保存的原提交结果，不重新检查其旧业务版本或旧 revision，不重复写入。
2. 拒绝 Discarded；不存在的身份明确返回未找到，不创建新草稿。
3. 读取当前档案和 `context_version`；严格检查业务基线及用户所见 revision。
4. 对数据库保存的最终草稿重新做结构、补丁、动作／模式引用和相关领域校验；读取与复查均使用当前事务连接，不嵌套取锁。
5. 写正式档案、`context_version +1`、草稿 Committed 与不可变提交凭据。
6. 提交事务后再响应；任一步异常不得留下部分档案、版本或草稿提交状态。

原提交结果至少能识别草稿、已提交 revision 和该次提交后的业务版本。后续业务变化不能改写这份结果；客户端要看最新档案时另查只读接口。

事务内只做本地确定性计算和数据库操作；不调用模型、工具执行或 SSE，不增加第二把业务数据库锁。正式业务版本只由确认编排推进，领域 repo 不自行推进。

### 4.3 档案规则不扩张

- 复用 Stage 1 三态事实、两种限制粒度、已拍动作模式、清单外症状需澄清及体重必填语义。
- 本次追加拍板 1B：首次建档必须达到完整条件才能确认。目标、经验、频率、时长、器械、体重、动作限制与身体情况共八项全部要求明确回答（2026-09-10 拍板：原「身体状态」与「症状询问」两项合并为「身体情况」，九项变八项）；“明确无”有效，“未知”不算完整。缺失时不能正式提交，不补造字段；明确回答仍须符合对应字段的类型与领域校验，不能以“无”替代必需的有效数值。完整性仅表示信息齐备，不表示没有症状或已获训练安全许可。
- 2026-09-10 拍板（身体情况合并）：档案身体情况为单一字段 `body_conditions`，保存用户报告原文并保留三态；六类红旗清单只在读取／安全检查时匹配；`SessionConditions` 使用同一字段；首次建档不单独追问动作限制（`action_restrictions` 仍必填，结论由身体情况推出）；面向用户不使用「红旗」术语。**已于 2026-09-11 实现并提交（`16b9e52`）：本阶段交付代码现为八字段结构**（`body_conditions` 取代 `body_state` + `red_flags`），旧库 JSON 读旧写新、不新增迁移；测试 396 → 415，既有 S2 用例随结构同步更新、未放宽断言。
- “今天只能用哑铃”的结构化当次条件不得作为长期补丁提交；本阶段不负责从自然语言判别今天／以后。
- 保存用户报告的红旗事实不等于给出处方。不得因发现红旗而拒绝记录该事实，也不得因确认成功自动解除红旗或限制。
- Stage 1 `preview_patch` 的已知限制状态风险不得透传为“已完成安全筛查”；复用经核对的确定性规则，不以一次预览结果替代事务内复查。

- **依赖**：后续实现授权；本计划确认不是自动开始编码。
- **验收**：输出字段和调用路径映射；不存在把三态事实压成空数组／默认值、把限制名称直接当稳定身份、把部分档案显示成完整档案的问题。
- **完整性契约**：首次建档完整条件已按 §4.3 拍定（2026-09-10 后为八项：身体情况替代原身体状态与症状两项）；逐项映射到现有结构，补齐确认入口的完整性校验，不自行沿用 Stage 1 部分事实可保存能力作为生产确认规则。自动化覆盖每类信息缺失／未知时拒绝首次确认，以及全部明确回答时可进入后续确认校验；对允许明确无的字段验证其与未知的区别。
- **验证**：Windows 既有全量测试，记录实际基线；不沿用 243 的数字声称本轮通过。

### S2-02：草稿表与事务内访问能力

- **工作**：增加一份连续编号迁移；草稿 repo 保存快照、revision、来源与凭据；为档案与动作引用读取补齐最小事务内访问路径。
- **依赖**：S2-01。
- **验收**：空库迁移、Stage 0／1 库升级、重复启动、迁移失败回滚、高版本库拒绝启动均正确；旧会话、档案、动作目录、设置及版本不变。
- **边界**：只新增 `business_drafts`，不增加计划或统计业务表；既有表集合和凭据泄漏扫描断言显式扩展，不删测试、放宽断言或 skip。
- **验证**：临时文件库升级、约束失败及关闭重开自动化；事务内读取不会嵌套取锁或读取另一连接的快照。

### S2-03：内部草稿创建、查询与 Diff

- **工作**：从档案与版本同一快照准备生成输入；内部应用层保存 Pending 档案草稿；按身份／会话查询 SQLite 当前草稿并返回结构化 Diff。
- **依赖**：S2-02。
- **验收**：建草稿前后正式档案及版本不变；保存时间不能替代读取基线；不同来源关联不混淆；未建档、字段变更、限制增删均能正确表达前后值。
- **验证**：读版本 V → 另一草稿提交至 V+1 → 保存原草稿仍为 V；重开后内容、基线、来源和 revision 一致；调用方传入对象不被原地修改。

### S2-04：轻量纠错与丢弃

- **工作**：仅接受档案草稿允许纠错的内容，复查最终结构并更新 revision／Diff；丢弃只改变草稿状态。
- **本次追加拍板 2B**：普通档案字段、动作限制与身体情况均允许在草稿中内联纠错（2026-09-10 合并后身体情况为一项，替代原「红旗与身体状态」两项）；仍需结构化表达、后端校验与最终确认。允许用户纠错不等于 Agent 获得自动解除限制／红旗的权限。
- **本次追加拍板 3（前端交接约束）**：以当前已保存草稿 revision 的内容为比较基准，无本地未保存修改时禁用“提交纠错”、允许“确认草稿”；有本地未保存修改时允许“提交纠错”、禁用“确认草稿”。纠错成功后以服务端返回的新 revision／内容更新基准；请求失败不能误标为已保存。按钮还须服从 Pending、输入有效、请求未在进行等前提，不因无本地修改而放行终态或已知过期草稿。前端按钮逻辑另行接线，后端仍独立校验最终内容与 revision。
- **注意**：本地内容与已保存草稿是否相同，不等于拟议结果与正式档案是否相同；后者已拍方案 A：无业务变化时拒绝首次确认、版本不变、草稿保持 Pending，见 §8；按钮可用性不能代替后端判定。
- **依赖**：S2-03。
- **验收**：不能借纠错修改草稿身份、来源、业务基线、状态或凭据；非法纠错不部分更新；Committed／Discarded 不可继续纠错，Discarded 不可确认，Committed 不可被丢弃撤销。
- **并发**：纠错请求携带所见 revision，避免两个页面静默覆盖；确认与纠错、确认与丢弃须串行判定最终状态。重复丢弃返回已丢弃结果，不新增正式副作用。
- **验证**：旧 revision 纠错被拒绝、纠错前后 Diff 与正式库隔离、非法类型与非法引用、两类并发竞态；过期草稿即使纠错也不刷新业务基线。

### S2-05：档案确认事务与持久化幂等

- **工作**：实现 §4.2 顺序，复用 Stage 1 内部档案写入，集中推进版本并保存提交结果。
- **依赖**：S2-02–04。
- **验收**：真实档案与限制只在确认后生效；一次成功确认仅 +1；确认最终内容重新校验；重复确认始终返回原凭据，包括后续版本已变化和数据库关闭重开之后。
- **验证**：同草稿并发确认仅一次生效；分别在档案写入后、版本更新后、草稿／凭据写入后且 COMMIT 前注入失败，全部回滚。
- **取消边界**：提交前取消不得遗留半事务；提交成功但响应丢失时，通过重复确认找回原结果，不假定连接断开代表业务未提交。复用底座取消保障并测试，不另写一套事务管理器。

### S2-06：过期拦截与可核实变更信息

- **工作**：首次确认基线冲突返回 `409 draft_stale`；用保存的业务基线与当前档案快照计算变更项；revision 不符返回 `409 draft_modified`。
- **依赖**：S2-03、S2-05。
- **验收**：同版本两草稿中第一份提交后第二份被拦截，即使修改字段无关；已提交草稿的重复确认优先幂等；不改变过期草稿的状态、基线或正式数据。
- **信息边界**：只能报告可核实的字段变化，不虚构“谁何时修改”。若版本变过又恢复到相同值，仍拦截，并明确业务版本已变化、当前快照无字段差异。
- **验证**：同字段冲突、无关字段冲突、值改回但版本不同、仅 revision 变化、两种版本同时冲突；错误响应不伪装为成功。
- **后移**：不提供实际重算；向 Stage 4 交接旧草稿身份、基线与内容查询能力。

### S2-07：业务 API 与前端契约交接

- **工作**：在已有路由位置接入应用层；路由只负责校验传输、转换响应与错误映射，不承担领域规则或独立 SQL。
- **依赖**：S2-03–06。

| 接口（沿用现有前端路径，单草稿查询为补充） | 本阶段行为 |
|---|---|
| `GET /api/profile` | 当前正式档案与版本；缺失／未知明确表达，无写入副作用 |
| `GET /api/sessions/{session_id}/drafts` | 该会话已持久化草稿的当前状态，不依赖历史通知 |
| `GET /api/drafts/{draft_id}` | 当前草稿内容、revision、Diff、状态及必要结果信息 |
| `POST /api/drafts/{draft_id}/revise` | 内容＋所见 revision；返回更新后的草稿，不能自动提交 |
| `POST /api/drafts/{draft_id}/confirm` | 所见 revision；返回持久化提交结果 |
| `POST /api/drafts/{draft_id}/discard` | 丢弃待确认草稿，不撤销已提交事实 |

- **契约差异**：当前前端 `reviseDraft` 仅传 payload，交接须明确新增所见 revision；现有前端 `/recalc` 不在本阶段可用接口中。其他错误码和 DTO 命名为实现细节，在交接中统一，不新增业务语义。
- **验收**：非法 JSON／类型、未知字段、不存在身份、非法状态均明确拒绝；不能把客户端 payload 当可信最终事实；响应不含凭据配置或内部异常堆栈。
- **验证**：现有 ASGI／HTTP 测试方式覆盖全部端点、错误形状、读后可见性及 Host／Origin 既有边界；由内部应用层在临时库创建草稿，不开放测试专用生产路由。
- **交付边界**：提供 DTO 映射、请求响应样例及前端待改清单；不为联调增建聊天、模型或伪 Run，不要求此时切换整个前端到真实后端。
