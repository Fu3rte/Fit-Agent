# Pi Agent Harness — Code-Level Research Report

> Scope: this monorepo (HEAD `e266507b6`, after v0.84.4)
> Method: source reading (packages/agent, packages/ai, packages/tui, packages/coding-agent)
> Focus: what capabilities are implemented and how they are implemented

---

## 0. Architecture at a Glance

Pi is a terminal AI coding agent, organized in layers with strict one-way dependencies:

```
packages/tui       Terminal UI framework (differential rendering, components, layout)
packages/ai        Unified multi-provider LLM API (Provider abstraction, stream normalization)
packages/agent     Agent runtime (tool-calling loop, state, event stream)  ← depends only on ai, not coding-agent
packages/coding-agent  Interactive CLI / sessions / extensions / resource system  ← composes the layers above
packages/telemetry / session-backends/sqlite-node / evals                    ← cross-cutting support
packages/protocol + server + client                                          ← experimental remote protocol (CBOR/byte streams)
```

Key decoupling: `packages/agent` **does not depend on any concrete LLM provider** — it uses constructor injection of a `StreamFn` (`agent/src/stream-fn.ts`; the host installs it via `setDefaultStreamFn()`). `packages/ai` does not depend on coding-agent. This lets the three layers be published and tested independently.

## 1. Capability: Unified Multi-Provider LLM Layer (packages/ai)

**Capability**: 30+ providers (Anthropic / OpenAI / Gemini / DeepSeek / Groq / Cerebras / local llama.cpp …) behind one API, with automatic auth, streaming, thinking modes, prompt caching, cost accounting, and model-catalog refresh.

**Implementation**:

- **Two core abstractions** (`ai/src/models.ts`):
  - `Provider` — the runtime unit of one provider = `id + models (model list) + credential + api (ProviderStreams) + refreshModels (catalog refresh)`.
  - `Models` — collection that registers/queries/refreshes providers; unified entry points `stream()` / `streamSimple()` / `complete()`. `applyAuth()` (models.ts:636) injects the resolved credential (API key, OAuth token, subscription cookie) into every request before it goes out.
- **Each API implementation is a `StreamFunction`** (e.g. `ai/src/api/anthropic-messages.ts`): it translates the provider's native SSE event stream into the unified `AssistantMessageEventStream`. For Anthropic (stream fn, line 501):
  - `content_block_start/delta/stop` → unified `text_start/text_delta/text_end`, `thinking_*`, `toolcall_*` events (`input_json_delta` increments are fed through `parseStreamingJson` so partial tool arguments are visible mid-stream).
  - Usage is captured at `message_start`; `calculateCost()` then prices it from the model's rate table; `stop_reason` is normalized into a unified `StopReason` (`mapStopReason`).
  - Thinking: interleaved thinking, thinking signatures passed through; caching: `cache_control: ephemeral` + `PI_CACHE_RETENTION` selects short vs 1h retention.
  - `retryProviderRequest` for robust retries; `validateToolArguments` (TypeBox) validates tool inputs.
- **Lazy loading** (`ai/src/api/lazy.ts`): `lazyApi()` routes every provider implementation through a **dynamic import, loaded only on first stream call** (tree-shaking friendly, keeps startup memory low); `lazyStream()` pushes async setup (auth resolution, module load) behind the stream and converts failures into an `error` event instead of throwing.
- **Model catalog refresh**: `refresh()` (models.ts:386) runs phases (fetch provider catalog → validate → `publishProviderModels` with a generation counter; a newer refresh `supersedeProviderRefresh`s older in-flight ones). The static catalog `models.generated.ts` is generated by `packages/ai/scripts/generate-models.ts` — never edited by hand.
- Three auth kinds: subscription OAuth (`/login`, callbacks in `oauth.ts` + `bun-oauth.ts`), API keys (`env-api-keys.ts` + credential store), and GitHub Copilot's dynamic request headers (`github-copilot-headers.ts`).

## 2. Capability: Agent Tool-Calling Loop (packages/agent)

**Capability**: the multi-turn "LLM reply → parse tool calls → execute → feed results back → request again" loop, with parallel tools, steering messages, abort, retry, and per-turn model/context switches.

**Implementation** (`agent/src/agent-loop.ts`):

- **Two-level loop `runLoop`** (line 156):
  - Inner: `streamAssistantResponse` (streamed LLM reply) → if it contains `toolCall`s, `executeToolCalls` → tool results are pushed back into context as `toolResult` messages → next round; no tool calls → inner loop exits.
  - Outer: after the inner loop stops, if queued follow-up messages exist, continue the whole cycle; otherwise `agent_end`.
- **Steering messages**: user input typed between turns is polled each round via `config.getSteeringMessages()` and injected before the next LLM request; `shouldStopAfterTurn` / `shouldStopAfterToolBatch` are termination hooks (extensions can plug their own stop policy).
- **`prepareNextTurn` hook**: called after every completed turn; may return **a new context / model / thinking level** — automatic compaction hooks in here, swapping in a shortened context before the next request.
- **Two tool-execution modes** (`executeToolCalls`, line 424): parallel by default (`executeToolCallsParallel`); sequential when a tool declares `executionMode: "sequential"` or config demands it. Each call's lifecycle: `prepareToolCall` (argument validation; `immediate` tools return results directly) → `executePreparedToolCall` (streamed output) → `finalizeExecutedToolCall` (post-processing) → emit `tool_result` message.
- **Defense**: when `stopReason === "length"` (output cut by the token limit) **every tool call in the message is failed as a batch**, so truncated-JSON arguments are never executed.
- **Event model**: the loop emits `agent_start / turn_start / message_start|update|end / tool_execution_start|update|end / tool_result / turn_end / agent_end`; the UI subscribes and renders without touching loop internals — this is how UI and loop stay decoupled.
- The `Agent` class (`agent.ts`) is a stateful wrapper over the loop: message queues (steering/followUp), `abort()`, subscriptions, state reduction.

## 3. Capability: Tool System and Built-in Tools (coding-agent/src/core/tools)

**Capability**: 8 built-in tools — read / write / edit / bash / grep / find / ls / powershell (4 enabled by default) — restrictable via `--tools` / `--exclude-tools`, with extensions registering custom tools of the same shape.

**Implementation**: every tool is a **`ToolDefinition`** with three parts (see `read.ts`, `bash.ts`):

1. **TypeBox parameter schema**: type safety + automatic argument validation (paired with `validateToolArguments` in the ai layer — a bad call from the LLM is rejected and the error returned).
2. **execute callback**: the actual work.
3. **Custom rendering**: how results appear in the TUI (`formatReadResult` line-number/theme-aware rendering, `BashResultRenderComponent` component rendering).

The key design is **pluggable operations**:

- `ReadOperations` / `BashOperations` abstract file reading and process execution (`executeBashWithOperations` in `bash-executor.ts`). Default implementations run locally (`createLocalShellOperations`), but sandboxing extensions (Gondolin/Docker) can **replace these operations without touching the tool itself** — this is the implementation basis of `examples/extensions/sandbox`.
- Bash tool details: spawns a process, streams stdout/stderr, **throttled batched refresh** (`scheduleOutputUpdate` merges high-frequency output into periodic TUI updates instead of rendering per chunk), timeout abort, output truncation/formatting, exit-code reporting.

## 4. Capability: Session Persistence and Branching (coding-agent/src/core/session-manager.ts)

**Capability**: sessions are stored as JSONL trees; any node can branch; `/tree` navigates in place, `/fork` derives a new session; `/resume` fully restores after restart (including rendered state, model, thinking level, extension-injected messages).

**Implementation**:

- **File format**: every entry carries `id / parentId / timestamp` (`SessionEntryBase`), which naturally forms a tree; `SessionManager.getTree()` rebuilds it. The entry union (`SessionEntry`, line 144):
  - `message` (the AgentMessage verbatim), `model_change`, `thinking_level_change`, `compaction`, `branch_summary`
  - `custom`: extension-private data (NOT in LLM context; used for restoring extension state across restarts)
  - `custom_message`: **participates in LLM context** (`buildSessionContext()` converts it to a user message) — the official channel for extensions to "speak into" the conversation (e.g. system state injection)
  - `label` (bookmarks), `session_info` (display name)
- **Branch semantics**: `/tree` navigates/continues **within the same file** (no new file, full history kept); `/fork` copies into a new file. Continuing = `findEntry` + rebuilding context from that node.

## 5. Capability: Context Compaction (coding-agent/src/core/compaction/)

**Capability**: long sessions get old messages summarized automatically or manually while recent context is kept; context-overflow turns recover automatically and continue.

**Implementation** (`compaction.ts`, four steps):

1. **Usage estimation**: `estimateContextTokens` prefers the latest assistant message's real usage (`getLastAssistantUsage`); falls back to a `chars/4` heuristic (`estimateTokens`).
2. **Decision**: `shouldCompact` compares against the context window (threshold trigger); overflow (providers returning context-overflow errors) takes the `overflow` branch — after compaction the interrupted turn **retries automatically** (`_overflowRecoveryAttempted` + `willRetry` in agent-session.ts).
3. **Cut point**: `findCutPoint` only cuts at turn boundaries (user or assistant messages), targeting `keepRecentTokens` of recent content.
4. **LLM summarization**: `generateSummary` summarizes the pre-cut messages with the same model; the result is written as a `compaction` entry (`firstKeptEntryId`, `tokensBefore`, usage); `buildSessionContext` skips entries before it.

Extensibility: `AgentSession.compact()` (agent-session.ts:1941) fires an extension hook first; extensions may return a **custom compaction result** (e.g. a structured artifact index), falling back to the built-in summary; the `compaction_end` event lets the UI show the summary and its cost.

## 6. Capability: Interactive TUI (packages/tui + coding-agent/src/modes/interactive/)

**Capability**: a flicker-free terminal chat UI: message stream, editor, footer (tokens/cost/model), collapsible tool output, thinking blocks, image paste, tree selector, hot-reloading themes.

**Implementation**:

- **Differential rendering** (`doRender` in `tui/src/tui-main-screen.ts`, line 262): each render = component tree produces a **new line array** → diff against the previous line array to find `firstChanged..lastChanged` → **write only the changed range** (`\r\n`-positioned). Full redraws only happen on: first render, terminal width change (reflow), content shrink (`clearOnShrink`), except Termux height changes (software keyboard would cause false triggers).
- **Flicker prevention**: all writes are wrapped in `CSI ?2026h / ?2026l` (synchronized output) so the terminal updates atomically.
- **Component system**: `Component` interface (render()) + built-ins (Text/Markdown/Input/Editor/SelectList/ScrollView/VStack/HStack/Image…); `TuiMainScreen` (main buffer, keeps scrollback) vs `TuiAltScreen` (alternate buffer) + `layout.ts` constrained layout via VStack/HStack/ScrollView (see root `tui-plan.md`, a recent focus).
- **Images**: inline rendering via kitty/iTerm2 graphics protocol; the diff range is expanded to cover image placeholder rows (`expandChangedRangeForKittyImages`).
- The interactive **composition root** is `interactive-mode.ts` (6576 lines): subscribes to the agent event stream (`handleEvent`, line 3179) and renders events as chat entries; `getUserInput` editor loop; every slash command is a method (login, model picker, /tree, /settings…); extension UI (selector/confirm/input/editor/widget/footer/header) is bound to the TUI here.

## 7. Capability: Extension System (coding-agent/src/core/extensions/)

**Capability**: TypeScript extensions can register tools, slash commands, keybindings, event handlers, UI components, custom providers and compaction strategies; resources hot-reload (`/reload`).

**Implementation**:

- **Loading**: `ResourceLoader` (resource-loader.ts) discovers extensions/skills/templates/themes from the global `~/.pi/agent/`, project `.pi/`, and installed pi packages; extension modules load via dynamic import; factory functions (default export) run at startup (async factories supported for one-time init); `reload()` supports in-place reload with diagnostics (`detectExtensionConflicts`, `addExtensionConflictDiagnostics`).
- **Running**: `ExtensionRunner` (extensions/runner.ts) is the event dispatch hub — each extension gets an `ExtensionContext` (`createContext`, line 723) exposing `registerTool / registerCommand / on(event) / setStatus / UI dialogs`; the `emit*` methods dispatch agent/session events (`message_end`, `tool_call`, `tool_result`, `before_agent_start`, `input`, `context`…) to extensions in registration order; on duplicate tool names **the first registrant wins** (`getAllRegisteredTools`).
- **Tool prompt injection**: snippets from extension-registered tools are concatenated into the system prompt each turn (agent-session.ts maintains `_toolPromptSnippets`), so the LLM knows extension tools exist.
- **UI API binding**: extension UI calls (select/input/notify/custom components/widget/footer/header/editor replacement) are implemented in InteractiveMode (`showExtensionSelector` and friends, interactive-mode.ts:2501+), temporarily swapping the editor position for dialog components — degraded/disabled in non-interactive modes (`ExtensionMode = "print"`).
- By design pi ships **without** built-in sub-agents / plan mode / MCP / permission popups — those are all "someone else's extension" capabilities; the core stays minimal.

## 8. Capability: Resource System (Skills / Prompt Templates / Themes / Pi Packages)

**Key implementation points**:

- **Skills** (`core/skills.ts`): follow the Agent Skills standard — directory + `SKILL.md`; the model loads them on demand during the conversation (`/skill:name` or model judgment), injecting the instructions into context.
- **Prompt Templates** (`core/prompt-templates.ts`): Markdown + `{{variables}}`, expanded via `/name`; variables filled through a UI dialog.
- **Themes**: a theme is a JSON color table bound to components' theme interfaces; **hot-reload** (editing the active theme file applies immediately).
- **Pi Packages** (`core/package-manager.ts`, 2699 lines): `pi install npm:.../git:...` installs into `~/.pi/agent/{npm,git}/`; a `pi` manifest (or conventional directories) registers the four resource kinds; `pi update/config/list/remove` manage the lifecycle.

## 9. Capability: Four Run Modes + SDK

- **Interactive**: `interactive-mode.ts` (see §6).
- **Print**: `modes/print-mode.ts` — one request, print the final text, exit; piped stdin is merged into the prompt.
- **JSON event stream**: `modes/json-event.ts` — emits every agent event as JSON Lines (for script consumption).
- **RPC**: `modes/rpc/` — strict LF-delimited JSONL over stdin/stdout for non-Node process integration (`rpc-entry.ts`).
- **SDK** (`core/sdk.ts` + `core/agent-session-runtime.ts`): `createAgentSession()` packages the whole stack (ModelRuntime + SessionManager + AgentSession) into an embeddable API for Node applications.

All modes share the same `AgentSession`/`Agent` core; they differ only in "where input comes from and how events are presented" — which is why the mode layer is so thin.

## 10. A Full Prompt Journey (data flow)

```
User types in editor → InteractiveMode.getUserInput()
  → AgentSession.prompt(text)
    → Agent.prompt() → runLoop (agent-loop.ts)
      → streamAssistantResponse: AgentMessage[] → convertToLlm → Models.stream()
        → Models.applyAuth() → Provider.stream() (lazy provider module load)
          → provider SSE → AssistantMessageEventStream (unified events)
        → events surface: tool_call → executeToolCalls (TypeBox argument validation)
          → tool execute (read/bash/...) → toolResult messages back into context
      → loop until no tool calls → agent_end
  → AgentSession._handleAgentEvent: every step persisted to the JSONL session file (id/parentId)
  → InteractiveMode.handleEvent: rendered as TUI message lines / tool output components
    → tui component render → line diff → incremental terminal writes wrapped in CSI 2026
```

## 11. Quick Start (reference)

```bash
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
export ANTHROPIC_API_KEY=sk-ant-...   # or run /login after startup
pi                                          # interactive
pi -p "Summarize this codebase"             # one-shot Q&A
pi --provider openai --model gpt-4o "..."   # explicit provider/model
pi --tools read,grep,find,ls -p "..."       # read-only mode
pi -c / -r                                  # continue / resume session
```

Developing this repo:

```bash
npm install --ignore-scripts && npm run build
./pi-test.sh       # run pi from sources
./test.sh          # tests (skips ones needing API keys)
npm run check      # lint + typecheck (required before commits)
```
