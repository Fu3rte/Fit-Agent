# 1. 共用应用层：草稿确认与业务事务

> 本章仅搬运已拍设计，不授权实现；验收标准均为待实现验证。

## 本章已拍结论

| 决策 | 选项 | 选了 | 为什么 |
|---|---|---|---|
| 业务事实确认与写入 | A 按钮确认结构化草稿 / B 按钮与自然语言均可直接确认 | A | 确认对象必须明确，不依赖模型解释“好的”等表述；Agent 不得直接修改正式业务事实 |
| 业务交互形态 | A 对话发起、页面只读 / B 对话与完整编辑表单双入口 | A 增强版：对话唯一发起，草稿展示结构化结果与 Diff，支持关键字段内联纠错 | 避免单数字微调也必须重新对话，不建设完整计划编辑器；纠错后仍须最终确认 |
| 草稿适用范围 | 所有数据库写入 / 用户业务事实变更 | 用户业务事实变更（2026-09-07） | 运行日志、动作目录种子等系统写入不走草稿，不得借系统写入绕过用户业务确认 |
| 草稿状态 | Pending/Committed / 加入已丢弃态 | Pending、Committed、Discarded（2026-09-07，沿用历史决策） | 拒绝后不得提交；已提交草稿重复确认返回原结果 |
| 业务意图与组合草稿 | A 按业务对象拆卡、分别确认 / B 组合提交 | 受限 B：同一次意图中有直接依赖关系的档案与计划变更放入同一计划草稿 | 一张卡、一次确认、原子提交；不支持任意跨业务拼装，不建设通用组合草稿系统 |
| 草稿过期判定 | A 统一业务版本 / B 按依赖分别检查版本 | A：`context_version`，草稿保存 `base_business_version` | 接受无关业务变更也使旧草稿过期，避免遗漏依赖及旧草稿覆盖新数据 |
| 过期草稿恢复 | 拦截后重算 / 自动合并或静默采纳 | A 增强版：拦截 + 按最新数据一键重算 | 新草稿关联旧草稿、展示 Diff 并再次确认，不自动合并 |
| 当前交付范围 | P0 / P1 及其他后期内容 | 只锁定 P0；后期内容待拍 | 后期需求、分期与优化不作为当前成品交付前提，不预先设计具体机制；PRD 安全底线仍有效 |

## 责任边界

负责：

- 草稿生命周期与草稿数据基线的编排（见 1.3）
- 确认事务：幂等返回、版本检查、领域复查、原子提交（见 1.4）
- 受限组合计划草稿、过期拦截与一键重算链路（见 1.5、1.6）

不负责：

- 领域规则本身：由业务代码负责，不塞进 Agent 框架，也不依赖 Prompt 充当正式写入的安全校验（见 1.2）
- 各业务对象的具体内容规则：归第 2–6 章
- SQLite 连接、事务与迁移：归第 7 章

## 业务规则

### 1.2 交互与事实边界

- 对话与 Agent 是唯一业务变更发起入口；业务页面为纯只读看板，可独立查看，不直接编辑正式事实。
- 档案与限制变更、计划启用或替换、训练记录保存及历史更正均须生成结构化草稿，由用户点击确认按钮后经业务接口校验提交；自然语言同意不直接生效。
- 草稿卡展示结构化结果和变更 Diff，支持关键字段轻量内联纠错，例如动作、重量、次数、RIR、日期及档案单个字段。纠错只修改待确认草稿，展示结果和 Diff 随之更新，不自动提交，不建设完整业务编辑表单或计划编辑器。
- 历史正式记录只读；“发起更正”进入对话并生成新草稿，确认后生效并保留修改痕迹，不直接覆盖历史。
- 草稿就绪仅表示已持久化、可查看且待确认；通知引用草稿身份和修订版本，不是当前状态的事实来源。草稿纠错、确认和丢弃走业务接口，不依赖历史通知。
- Run 已完成不等于草稿已确认或业务已提交；草稿确认前不污染正式业务事实。
- 领域规则独立于 Agent 框架，由业务代码负责；共用应用层编排草稿流程和事务，不依赖 Prompt 充当正式写入的安全校验。

### 1.3 草稿数据与生命周期

`business_drafts` 保存用户业务事实变更的前置草稿、生成基线、纠错修订版本、前后快照与来源，以及幂等确认凭据。草稿与正式数据共用 SQLite，不另建草稿数据库。

| 数据 | 业务含义 |
|---|---|
| `base_business_version` | 草稿实际生成依据的 `user_profile.context_version`，必须绑定读取时的业务版本，不能在生成结束后补标为最新版本 |
| 草稿修订版本（revision） | 标识用户看到并准备确认的草稿内容版本，防止提交已被修改的草稿 |
| `proposed_profile_patch_json` | 计划草稿中可空的拟议档案变更，仅供该草稿的计划调整和校验使用 |
| `parent_draft_id` | 重算后新草稿关联的旧草稿身份 |
| 提交凭据 | 已提交草稿重复确认时返回原结果，不重复正式写入或递增业务版本 |

生命周期为 Pending／Committed／Discarded；过期是业务基线冲突，不替代已丢弃状态。用户拒绝则丢弃草稿，正式数据及业务版本不变；Discarded 不得再提交。

端到端链路：自然语言输入 → Agent 提取意图并调用领域工具 → 按读取的业务基线生成 Pending 草稿 → 展示结构化内容、Diff 并允许轻量纠错 → 用户点击“确认采纳” → 事务内版本检查与领域复查 → 正式写入并将草稿置为 Committed。

### 1.4 统一业务版本与确认事务

- `context_version` 是统一用户业务版本，不是模型上下文或压缩机制；草稿以 `base_business_version` 保存生成时的业务版本，不引入第二套业务版本计数器。
- 每次成功提交正式业务变更使版本 +1，包括档案、伤病/动作限制、器械条件、正式计划变更或恢复、训练安排及调整确认、训练记录新增、更正或作废。同一次受限组合提交只递增一次，不按表或对象数量递增。
- 聊天、草稿生成与内联纠错、拟议档案变更暂存、运行轨迹、模型设置不递增业务版本。

确认在同一数据库事务内依次完成：

1. 先处理已提交草稿的幂等返回，再拒绝已丢弃草稿；不能因后续业务版本变化，把重复确认已提交草稿误报为过期。
2. 对可首次确认的草稿，严格检查 `draft.base_business_version == user_profile.context_version`，并校验用户所见草稿修订版本；拒绝确认已被修改的草稿。
3. 以最终草稿内容复查领域规则，前端纠错不能绕过后端校验。含拟议档案变更时，先校验补丁，再按应用补丁后的拟议条件校验计划，不能只按旧条件校验。
4. 写入正式业务数据、统一业务版本 +1、草稿置为 Committed，并保留幂等确认凭据。

- 版本检查、领域复查、正式写入、版本递增和草稿状态变更是一次原子提交；任一步失败全部回滚，不留下部分正式写入或版本递增，不留检查与写入之间的 TOCTOU 空隙。
- 所有数据库操作共用一个 `asyncio.Lock`；多语句事务从 BEGIN 到 COMMIT 或 ROLLBACK 全程持锁。事务内复查是本地确定性校验；模型生成与重算在事务外进行，不跨模型请求、工具执行或 SSE 推送持有数据库事务。连接与迁移规则归第 7 章。
- 接受保守拦截：一次正式业务提交成功后，所有旧业务版本的未提交草稿均过期，即使实际无关。
- 安排调整经用户确认接受时须立即落盘安排及真实接受时间，沿用本节原子事务与版本规则；不得先在会话中视为已接受，等打卡或补录再补写。发生时间与接受、记录、更正确认时间分开，不倒填接受时间；安排历史规则归第 4、5 章。

### 1.5 受限组合计划草稿

- 仅允许同一次用户意图中有直接依赖关系的档案与计划变更组合提交，不因业务模块划分强制拆卡。
- 拟议档案变更保存在计划草稿，不是短期记忆，不新增记忆系统；正式档案仍是长期档案事实的唯一来源，确认前绝不修改。
- 草稿中的拟议条件只用于该草稿，不能当成已确认的长期事实。

“以后只能用哑铃，帮我调整计划”的流程：

1. 读取当前档案、限制、计划及对应业务版本。
2. 将长期器械变更保存在计划草稿的 `proposed_profile_patch_json`，基于拟议条件在提交事务外生成调整后的计划。
3. 一张卡展示长期器械变更与计划 Diff，不要求先单独确认器械变更。
4. 用户确认后，在同一事务内检查业务基线及草稿修订，校验补丁和新计划，更新正式档案、激活新计划版本、将旧版本退出当前状态并保留历史、提交草稿，业务版本仅 +1。计划切换的日程联动仍按已拍规则执行，归第 4 章，不因本例省略而取消。
5. 任一步失败全部回滚；用户拒绝则丢弃草稿，正式数据及版本不变。

“今天只能用哑铃”只作为当次训练条件，不写入拟议长期档案补丁，也不修改长期档案。

### 1.6 过期拦截与一键重算

- 首次确认业务版本不一致时，返回 `409 Conflict`，机器错误码 `draft_stale`，并指出相关变更项，例如“已新增动作禁忌”；不得提交旧草稿。
- 用户点击“按最新数据一键重算”后，以最新业务上下文生成新草稿，通过 `parent_draft_id` 关联旧草稿。
- 新草稿展示与旧草稿的 Diff，以及对正式业务数据的变更；必须再次确认才生效。不自动合并，不因曾确认过旧内容而自动采纳重算结果。
- 一键重算是对话与 Agent 变更链路的快捷操作，不是独立业务编辑入口；若触发 Agent 执行，仍遵守全局单 Run、用户取消等约束。

## 验收标准（待实现验证）

1. 草稿生成和内联纠错不改变正式事实或业务版本；Run 已完成但草稿未确认时仍不生效，自然语言同意不直接提交。
2. 用户看到 revision 1 后草稿变为 revision 2：首次确认旧修订被拒绝；确认最新修订仍须业务版本与最终内容的领域校验，不能通过内联纠错绕过规则。
3. 同一业务版本生成两份草稿：第一份成功提交后，第二份首次确认返回 `draft_stale`；重复确认第一份仍返回原结果，不重复写入或递增版本。
4. 确认后立即重启，正式数据、接受时间及提交凭据仍在；注入事务失败时无部分写入、状态变更或版本递增；丢弃草稿不得提交。
5. “以后只能用哑铃”确认前档案与当前计划均不变，确认后两者同事务生效、版本仅 +1，旧计划保留历史；失败全部回滚，重复确认不重复提交。“今天只能用哑铃”不污染长期档案。
6. 过期草稿显示变更项；一键重算生成关联旧草稿的新草稿并展示新旧 Diff 和正式业务变更，再次确认前不生效，不自动合并或采纳。
7. 确认接受当次安排调整后立即重启，安排及真实接受时间仍在，业务版本仅递增一次；不得等到打卡时补写，也不得将事后反馈倒填为事前接受。
