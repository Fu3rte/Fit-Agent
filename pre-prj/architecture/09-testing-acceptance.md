## 业务规则

### 9.1 产品自动化测试边界

- 选择 A：核心自动化测试 + Windows 人工验收；自动化覆盖领域校验、事务、草稿过期与幂等。
- 同一套核心测试须能在 Linux 和 Windows 运行。
- 不额外建设浏览器端到端自动化；界面交互由人工验证。
- 产品测试不替代已确认必做的 Agent 行为测评（9.3）。

### 9.2 Windows 人工验收

- Windows 为首版成品验收平台；Agent 在 Linux 端开发和编写代码，用户在 Windows 端已克隆的仓库中进行实测。
- Windows 按清单实测安装、启动、业务流程与重启恢复。
- 开发与验收须对应同一代码版本；Linux 检查通过不能代替 Windows 实测证据（v1 L22）。
- 利用 Linux 的命令行开发优势，同时以 Windows 实际安装、启动和核心流程验证作为成品验收依据（v1 L22）。

### 9.3 测评方式、覆盖与样本

- 测评方式 C：代码确定性检查 + LLM judge + 人工校准、争议裁决与抽检；产品核心流程落地后必须测评（v1 L17）。
- 覆盖范围 B：核心业务加开放问答、多轮与异常；不建设模型排行榜。
- 样本：18 个任务（8 核心业务、4 开放问答、6 多轮与异常），另有 20 对开放语义正负样本；任务实测与裁判校准分开。
- 核心业务覆盖建档、计划、校准与渐进、状态调整、打卡、更正、复盘、接回；多轮与异常覆盖澄清纠错、压缩前后事实一致性、工具失败、越权诱导；安全与确认边界可跨案例检查。
- 被测模型为 DeepSeek 官方接口的 deepseek-v4-flash，固定被测对象，不默认通过 command-code 调用；裁判模型为 command-code 提供的 glm-5.3-flash，与被测模型不同以降低同源偏差；模型选择不代表已通过校准，本项不扩大产品 Provider 支持范围。

### 9.4 检查点与成功判定

- 每个案例运行前固定初始数据、对话流程、预期结果及检查点；每个检查点明确检查内容、依据、检查方式（代码、LLM Rubric 或安全规则）、合格线及是否影响任务成功；不在运行后临时判断“关键不关键”或挑选检查点。
- 单次成功按预先定义检查点联合判定：所有必需代码检查与指定关键语义检查通过；评分型必需检查的所有适用维度均须 ≥4/5；安全硬约束违反即失败。一般表达质量单独统计，不影响任务成功；争议裁决后再确定结果。
- 确定性硬约束须全部通过、安全违规零容忍，独立于 16/18 门槛；综合分不能抵消。人工发现安全违规同样阻断通过；怀疑检查本身错误时修正并重跑，保留原因及旧结果。
- 主指标为 pass³：同一案例从相同初始状态独立运行三次，三次均成功才计为通过；至少 16/18（88.9%）案例通过。全量共 54 次案例运行，多轮与工具调用意味着不等于 54 次模型请求。
- 保留每次结果、失败原因及代码、语义、安全分类；单次成功率可辅助报告，不替代 pass³，不以补跑成功覆盖失败；基础设施异常单列，不冒充通过。
- 语义评分范围为全部案例预先指定的用户可见回答检查点，覆盖必要澄清、建议、失败说明及最终回答，不重复评价每句回执。
- 本测评不替代领域规则、事务自动化测试与 Windows 人工验收；Mock 通过不代表真实模型行为通过，后端拦截违规也不代表 Agent 未尝试越界。

### 9.5 Rubric、裁判校准与人工闭环

- LLM judge 主要评价非结构化开放语义，包括正确性、相关性、沟通语气及依据充分性；采用明确的 1–5 分锚点、正反例与不适用条件。结构化事实、数据库结果和统计一致性优先用代码检查。
- 裁判先给可审计评分依据，再给各维度绝对分数：引用回答片段，对照固定证据与 Rubric 条款，说明支持、矛盾或缺失点。不要求或存储隐藏 CoT，不把模型自述思考过程当证据。
- 正确性须对照经人工审核的参考事实、来源摘录、业务预期及运行时实际工具结果；语气、相关性同样引用具体片段与评分锚点。证据不足标记待人工裁决，不能自动通过或凭自信措辞判正确；开放问题不要求唯一措辞。
- 20 对正负样本用于裁判校准及验证，不计入任务 pass³。每对围绕同一问题和上下文，负例针对明确缺陷；正负标签不向裁判暴露，控制长度、排版等无关因素。真实 Agent 回答仍按同一 Rubric 评分，不能用预制正例替代实测。
- 每对留出样本须同时满足：正例所有适用维度 ≥4，负例预设缺陷维度 <4，评分依据真实且匹配；仅正例比负例分高不足以通过。8/8 全部通过才允许正式使用裁判。
- 用留出结果修改 Rubric 或裁判提示词后，该批样本转为校准材料，须另补留出样本，不再宣称原集独立验证；新增调用仍受本轮预算约束。
- 人工负责 Rubric 与 judge 校准、争议裁决及抽检。争议、证据不足、疑似安全违规全量裁决，不占抽检名额；疑似安全违规在裁决前阻断验收。
- 对其余已自动评分的真实 Agent 回答抽检 20%，向上取整，覆盖三类场景及通过/未通过结果（存在时）；保留抽样清单、原评分、人工结论、分歧及裁决理由，不只挑成功样本。

### 9.6 执行与费用边界

- 使用本地轻量执行器，人工通过本地报告与复核文件参与，不建设测评后台或引入外部测评平台。固定并记录代码、Prompt、模型及有效配置、案例、Rubric、裁判提示词和证据包版本。
- 准备验收的变更后执行全量 pass³；三次独立，不共享前一次产生的业务状态。保留完整结果和失败证据，不自动切换为局部回归或上调 k。
- 真实运行前核实双方准确模型 ID、可用性及计费方式；未知价格或静默模型回落即停，不自动换模型。
- 本轮全部测评调用累计不得超过人民币 20 元；使用持久账本，请求前预留保守最坏成本，余额不足即停止；usage 缺失或取消保留预留，不按零计费。不自动追加预算、缩减案例或重跑失败样本；不承诺 20 元足够完成全量。
- 此预算是未来测评费用上限，不是当前真实调用或完整开发授权，也不放宽现有 spike 护栏；不把 spike 的 256 输出限制自动当作测评配置。
- 具体案例与 Rubric、证据包待编写及人工校准；现有数据与隐私约束保持不变，不引入真实用户健康资料。

## 验收标准（待实现验证）

1. 18 个任务按 8/4/6 分类，检查点及其成败影响在运行前固定；各三次独立，报告可复算 pass³，至少 16/18 通过且无硬约束违规。
2. 20 对样本分为 12 对校准和 8 对独立留出；裁判在留出集 8/8 通过，评分依据可逐项核验，标签未暴露。
3. 真实回答检查点按 Rubric 输出依据与分数；一般表达不计任务成败，争议经人工裁决；20% 抽检和全部必审项有记录。
4. 报告保留版本、逐次结果、失败分类、人工裁决与原评分；未运行、证据不足、预算中止如实标记，不当作通过。
5. 账本覆盖全部模型费用、预留与未结算项，重启不清零，累计不越过人民币 20 元；不暴露密钥。
