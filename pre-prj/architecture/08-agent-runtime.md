# 8. Agent 运行时

> 本章仅搬运已拍设计，不授权实现；验收标准均为待实现验证。运行时表的存储形态、写入事务配对与幂等键归第 7 章；全局架构不变量清单归第 11 章。

## 本章已拍结论

| 决策 | 选项 | 选了 | 为什么 |
|---|---|---|---|
| Run 状态 | `pending`、`running`、`completed`、`failed`、`cancelled` 五种；`cancelled` 为独立终态 | 正常流转 `pending → running → completed \| failed`；用户可将 `pending` 或 `running` 转为 `cancelled`；所有终态不可恢复 | 用户主动取消不计作执行失败；终态不可复活 |
| Run 并发与活跃会话 | 多 Run 并行 / 全局单 Run | 全局最多一个 `pending` 或 `running` Run；同一时刻只允许一个会话发起 Agent 对话 | 单用户首版不设计多会话并行或跨会话排队 |
| 同会话互斥 | 排队 / 拒绝 | 已有 `pending` 或 `running` Run 时，不同请求返回 `409 conversation_busy`；相同 `client_request_id` 返回已有 Run | 保证上下文与消息顺序确定 |
| 运行中输入 | Queue / Steer / 均不支持 | 首版不支持 Queue 或 Steer | 先完成核心产品，成品后再评估 |
| 用户取消 | 仅取消按钮 / 断线也算取消 | 仅由用户点击取消按钮触发；`pending` 或 `running` 转为 `cancelled` | SSE 断开或页面刷新不取消；取消为尽力中断，不承诺回滚已发生副作用 |
| 重启恢复 | 断点续跑 / 启动时统一标失败 | 启动时将遗留的 `pending`、`running` 统一改为 `failed` | 不做断点续跑，由用户手动重试 |
| 中断错误码 | 沿用普通失败码 / 独立错误码 | `interrupted_by_restart` | 区分服务重启中断与普通执行失败 |
| 对外事件 | A 产品语义映射 / B 直接转发框架事件 | A（2026-09-07） | 前端不依赖 PydanticAI 内部事件；简单映射，不建设通用事件转换框架 |
| 依据与说明传输 | 独立流式 / 随结果展示 | 随结果展示（2026-09-07） | 展示真实来源、引用和简短说明，可折叠，不把内部推理流当作可信依据 |
| 断线恢复 | A 按事件 ID 补读 / B 查询当前状态 | B（2026-09-07） | 首版恢复 Run、已保存回答及草稿当前状态即可，不保证每段中间输出或历史通知重放；中断回答分批保存的持久化规则归第 7 章 7.4 |
| 心跳与失联处理 | 显式心跳并转查询 / 仅依赖网络发现断线 | 15 秒 heartbeat、45 秒失联后转查询（2026-09-07） | 防止界面假等待，断线不改变 Run 执行结果 |
| 压缩提示 | A 轻提示不打断 / B 仅明显拖慢时提示 | A（2026-09-07） | 快速完成 toast 提示 3 秒自动消失；明显等待时提示常驻至整理结束；可自动恢复的失败不报错 |
| SSE 前端展示范围 | A 产品必要事件 / B 加简单工具进度 / C 完整执行面板 | A（2026-09-07） | 面向不懂编程的普通用户，展示回答输出、草稿、压缩提示、可理解的失败原因和最小运行状态；不展示工具调试面板及 Token/Cache 数值 |
| 可折叠说明 | A Provider 返回的原始推理 / B 依据与说明 / C 不设独立折叠区 | B（2026-09-07） | 展示有事实支持的依据、缺失信息与建议理由，不冒充原始思维链，不展示隐藏思维链或编造处理过程 |
| 用户可见 Run 状态 | 仅回答输出 / 补充最小运行状态 | 处理中、已完成、已取消、未完成（2026-09-07） | 等待、取消、失败和重启中断均有明确反馈，不暴露内部状态码 |
| 生产 Harness 参数管理 | A 固定不可调参数 / B 本地配置 + 硬边界 / C Web 设置页 | B（2026-09-07） | 适配不同模型与运行环境，保留必要调节能力，不增加 Harness 设置页面；配置不能越过硬边界，Agent 不得修改 |
| 重试与纠错范围 | A 不自动重试 / B 有限分类重试与受限纠错 / C 广泛自动恢复 | B（2026-09-07） | 在明确可恢复、安全且预算受控的边界内处理暂时故障与可修正校验失败，不用自动恢复绕过业务事实、人工确认或安全限制 |

## 业务规则

### 8.1 Run 状态机

- 状态枚举仅 `pending | running | completed | failed | cancelled`（列定义归第 7 章 7.4）。
- 正常状态流转为 `pending → running → completed | failed`；用户可以将 `pending` 或 `running` 转为 `cancelled`；所有终态不可恢复。
- `cancelled` 为独立终态，用户主动取消不计作执行失败。
- 不另建错误终态体系，只有一套权威 Run 状态；失败附可理解原因；“未完成”为 `failed` 终态，停止等待，不可续跑。
- 手动重试创建新 Run，不复活旧记录；`retry_of_run_id` 列语义归第 7 章 7.4。

### 8.2 并发互斥与请求幂等

- 全局最多一个 `pending` 或 `running` Run；同一时刻只允许一个会话发起 Agent 对话；单用户首版不设计多会话并行或跨会话排队。
- 创建顺序：先按 `client_request_id` 查重，相同客户端请求返回已有 Run、不重复创建；再检查是否已有活跃 Run。
- 已有活跃 Run 时，不同请求返回 `409 conversation_busy`，不创建消息或 Run。
- 首版不支持 Queue 或 Steer。
- 一键重算若触发 Agent 执行，仍遵守全局单 Run、用户取消等约束（第 1 章 1.6）。

### 8.3 取消

- 仅由用户点击取消按钮触发；SSE 断开、页面刷新及客户端暂时离线均不触发取消。
- 取消后不得再写 Assistant 消息或改为其他终态；条件更新与同事务追加取消事件的写入形态归第 7 章 7.5。
- 取消会尽力中断当前模型请求并禁止启动后续模型调用或工具；已经开始且无法安全中断的调用允许收尾，已发生的副作用不自动回滚，唯一执行名额在底层调用实际退出后才释放。
- 展示层：用户主动取消显示“已取消”；中断前的文本可保留，但须标明输出未完成，不冒充完整成功回答。

### 8.4 重启恢复与手动重试

- Schema 迁移完成后，在一个事务内将遗留的 `pending`、`running` 改为 `failed`，写入 `interrupted_by_restart` 并追加对应错误事件（迁移前置归第 7 章 7.2）。
- 不做断点续跑，不自动重试；用户手动重试创建新 Run。
- 前端显示“未完成”及中断原因，保留已保存内容和草稿，不恢复执行。

### 8.5 Harness 参数管理

- 选 B：本地配置 + 硬边界。超时、执行步数、输出上限等通过本地配置调整，启动时校验。
- 每次 Run 开始时固定本次配置，运行中不得因外部配置变更而中途改变其限制；配置文件格式、位置与加载实现属于实现细节。
- 不建设 Harness 参数 Web 设置页；本项不改变模型 Provider 配置页面的既有边界；Agent 无修改 Harness 配置或绕过硬边界的路径。
- spike 的 max_tokens≤256、禁重试及费用阈值仅属于 spike 授权，不能自动用作生产 Harness 参数；本项不放宽当前真实调用护栏，也不授权业务或 Harness 实现。
- 四项离线桩验证已于 2026-09-08 通过（事件流纠错计入共享预算、SDK 禁重试后单次实际发送、取消期间禁止新尝试、框架无原生幂等层须适配层核对），证据见 `test/spike/evidence/harness-offline-stub-checks.md`；历史归档归第 12 章。

### 8.6 有限分类重试与受限纠错

- 模型请求：仅对明确可重试的暂时性故障进行有限重试；永久性错误不重试。
- 输出与工具参数：对明确、可修正且尚未产生副作用的校验失败，允许反馈模型纠错；事实缺失或目标歧义必须询问用户，不得通过重试补造事实或擅自选择目标。
- 工具执行：仅对已确认可安全重试的操作恢复；写入结果不确定时先核对状态，不盲目重发。
- 业务冲突、安全拒绝及人工确认边界遵循既定业务流程，不由模型自动绕过。身体状况更新后，Agent 必须先询问是否调整长期计划；用户拒绝即不调用计划草稿工具，用户确认需要后也只可提出 Pending 草稿。非红旗当次保守调整只提出对应安排草稿，不得写长期计划；红旗及安全信息不明时不得通过纠错、工具重试或用户确认绕过阻断（2026-09-12）。
- 草稿路由（2026-09-12 已拍）：用户明确「只记录」身体状况 → 只提档案草稿；明确「同时调整长期计划」→ 提**一条**受限组合计划草稿（档案补丁＋计划 payload 一起待确认、两项 Diff、一次确认只推进一次 `context_version`）；未明确选择 → 先追问、不落库；已有正式计划且用户随后明确要求调整 → 独立计划草稿。当次安排不是长期调整的同意；自然语言只产生 Pending 草稿，正式生效必须由用户在草稿卡点击确认。
- 安全投影（2026-09-12 已拍）：会话内待确认档案草稿的拟议条件（含限制与红旗）纳入 guidance 安全复核，未确认期间不得放可执行处方；另加 C 层文本兜底——只扫当前 Run 最新用户消息，精确子串命中已拍红旗词（10 条，独立命中、不含「功能受限」）即本 Run 强制 `usable=false`，模型仍可追问／说明。同 Run 的处方草稿创建（`propose_plan_draft` 首次建档／长期修订／受限组合与 `propose_arrangement_draft`）在命中时同样不落草稿（无草稿行、无处方；记录草稿与档案草稿不变）；只读接口 `GET /api/plan/guidance` 只服务正式事实、不携带聊天 Run 状态，不在 C 覆盖内。C 不解析否定句（否定式命中按 fail-closed 保守阻断，已知局限）；B（结构化评估／必做步骤）经用户拍板暂缓、未实现，不得当作已有保证。
- 所有额外尝试纳入统一执行与费用预算；取消后不再启动重试或纠错；禁止框架、SDK 与应用层多层隐式重试叠加。
- 已拍次数、超时、退避、错误映射及流中断不重放规则见本章「Stage 4 已拍 Harness 策略」。先检查生产版本 PydanticAI 及 Provider SDK 的已有机制，再决定必要适配，不预建通用恢复框架。
- 本项仅确认生产设计原则，不授权实现、真实模型调用或放宽 spike 的禁重试与费用护栏。

### 8.7 SSE 对外事件与恢复

对外事件全集与边界：

| 事件 | 内容与边界 |
|---|---|
| Run 状态变化 | 唯一权威 Run 状态；失败附可理解原因；“未完成”为 `failed` 终态，停止等待，不可续跑；手动重试创建新 Run |
| 回答文本块 | 实时流式输出；恢复只保证已保存部分，最后尚未落盘片段允许丢失；分批持久化方式归第 7 章 7.4 |
| 依据与说明结果 | 随结果展示有事实支持的来源、引用及简短说明，可折叠，不独立流式化，无内容不展示空区域 |
| 草稿就绪 | 草稿已持久化才通知，引用身份与修订版本；通知不是当前草稿状态的事实来源 |
| 上下文压缩状态 | 快速完成显示“已整理上下文”toast，3 秒自动消失；明显等待时常驻显示“正在整理上下文”，至整理结束撤下；可自动恢复的失败不报错 |
| heartbeat | 无业务事件 15 秒时发送的连接保活事件，不入库、不分配 ID、不显示在聊天里 |

- 前端不依赖 PydanticAI 内部事件，做产品语义简单映射，不建设通用事件转换框架。
- 工具轨迹、Token/Cache 等保留后台，不向产品界面转发原始日志；不建设工具调试面板或全站业务事件总线。
- 草稿纠错、确认和丢弃走业务接口，不得只靠刷新时查询状态；确认事务规则归第 1 章。
- Run 已完成不等于草稿生效；部分回答不作为完整成功 Assistant 消息；成功消息与 `completed` 同事务提交、取消后不得写成功消息的约束归第 7 章 7.5。
- 本节替代 v1 与 `frontend/PLAN-FRONTEND.md` 中 SSE 按事件 ID 补读、事件 ID 用作恢复游标及“断线补读待拍”的旧约定；原生 EventSource 选型不变，但不依赖浏览器自动重连或 Last-Event-ID 补读；run_events 不承担首版客户端事件重放契约（第 7 章）。

断线、刷新与心跳规则：

1. 断线仅提示连接中断、正在恢复，不取消、不重跑 Agent，不直接判定 Run 失败。
2. 断线或刷新后，通过业务接口加载已保存会话内容、Run 状态和相关草稿当前状态，替换本地展示，不重复拼接。通知不是唯一事实来源。
3. Run 仍在执行时，轮询当前已保存内容和状态直至终态；本次不再接回 SSE，不保证恢复每段中间输出或历史通知；轮询不新增配置系统。
4. 连续 15 秒没有业务事件时发送 heartbeat；前端收到业务事件或心跳均更新最后接收时间。
5. 连续 45 秒未收到事件，或触发 error，主动调用 EventSource.close() 并转查询，避免浏览器自动重连形成另一套恢复路径。
6. 查询失败按 1、2、4、8、15 秒有界指数退避，后续上限为 15 秒；查询成功恢复正常轮询间隔。
7. 页面恢复可见时立即检查连接与当前状态，避免后台标签页计时器节流影响判断；终态或页面卸载时关闭连接、清理计时器。
8. 服务重启仍按既定规则将遗留 pending/running 标为 failed，原因 interrupted_by_restart；前端显示“未完成”及中断原因，保留已保存内容和草稿，不恢复执行（见 8.4）。

### 8.8 前端展示边界

- 展示范围为产品必要事件：回答输出、草稿、压缩提示、可理解的失败原因和最小运行状态；不展示工具调试面板及 Token/Cache 数值。
- 前端折叠区标题为“依据与说明”；不恢复 PRD §5.10 已删除的执行轨迹和运行指标面板，不改变 §5.9 的压缩提示要求。
- 前端状态是显示映射，不新增或替换后端状态：`pending/running → 处理中`、`completed → 已完成`、`cancelled → 已取消`、`failed → 未完成`；重启中断归属 `failed`，提供可理解的中断原因。
- 取消或失败时，中断前的文本可保留，但须标明输出未完成；用户主动取消仍显示“已取消”。
- 草稿就绪仅表示可查看、待确认；Run“已完成”不代表草稿已确认或正式业务已提交。
- 后端工具轨迹与指标持久化不等于前端展示；后台记录用于排错与测评，密钥不得进入事件、日志或错误详情（密钥边界归第 10 章）。

### 分类恢复与执行参数

- 明确暂时故障最多重试一次，作用域为每 Run；仅在本次尝试尚未向消费方产出任何输出/事件时生效。可重试白名单：连接建立失败与连接期超时（框架 `ModelAPIError`）、HTTP 500/503、HTTP 429（有 `Retry-After` 时等待其指示值，超过 10 秒则结束而非提前重发；无该头用默认退避 1 秒）。永久失败：HTTP 400、401、402、404、422，以及内容过滤、`length`、`insufficient_system_resource`、`aborted` 等流式结束原因（finish_reason）、用户取消、已开始输出的流中断、存储失败、业务冲突与安全拒绝。判定依据只能是 HTTP 状态码、框架异常类型与 finish_reason，不解析官方未定义的错误响应体字段。
- 流式输出开始后断流不自动重放，保留已保存内容并标未完成。
- 无副作用且可修正的输出/工具参数校验纠错，每 Run 合计最多两次：由适配层持有权威的 Run 级计数，输出校验与工具参数校验共同扣减，超出即终态失败，不静默接受无效结果。框架 `retries` 的 output 预算为 Run 级、工具预算为 per-tool，不得单独决定追加尝试；配置必须保证框架不会在适配层计数之外额外发起纠错请求。事实缺失仍询问用户。写工具不做通用自动重试，结果不确定先核对状态；核对查询计入工具调用预算，不占重试或纠错计数。
- 重试与纠错各自独立计数（重试池 1 次、纠错池 2 次，作用域均为每 Run），均计入每 Run 20 次实际请求预算；摘要请求与普通请求共用同一重试池；手动重试创建新 Run 并清零计数。
- SDK 隐式重试关闭，框架 per-tool 默认纠错预算不得与 Run 级计数叠加；所有实际模型请求统一按框架 `RunUsage.requests` 计数。退避默认 1 秒；服务端要求等待最多接受 10 秒，超过则结束而非提前重发。取消期间禁止新尝试。

| 参数 | 已拍默认值（2B） | 允许范围／硬上限 |
|---|---:|---|
| 每 Run 实际模型请求数（含摘要、重试、纠错） | 20 | 1–24 |
| 每 Run 工具调用数 | 32 | 1–40 |
| 单次模型输出上限 | 8192 tokens | 512–8192，且不超过模型能力 |
| Run 总时限（含压缩与退避） | 300 秒 | 30–600 秒 |
| 单次模型请求总时限 | 120 秒 | 10–180 秒，并受 Run 剩余时间约束 |
| 连接超时 | 10 秒 | 1–30 秒 |

每 Run 固定有效配置；到时/超限禁止新调用，已发生操作不自动回滚，无法立即停止的底层调用实际退出前不释放执行名额。上述是经用户确认的初始参数，不是实测最优值，也不构成美元费用保证。

### 首事件与流空闲超时（2026-09-12）

- 选 A（2026-09-12）：**不新增首事件计时器或流空闲计时器**。首字节到流结束的整体墙钟由既有「单次模型请求总时限 120 秒」覆盖；该时限由适配层实现，不依赖传输层 read timeout。
- 到时分类按本次尝试是否已产出业务输出：未产出时属可重试暂时故障，用重试池那 1 次（受 Run 剩余时间约束）；已产出时按「已开始输出的流中断」处理，不重放、保留已保存内容并标未完成。
- 新增机器可读错误码 `model_request_timeout`（单次请求超时）与 `run_timeout`（Run 总时限到期），登记进 S4-01 契约冻结清单；重试用尽、Run 剩余时间不足或已产出输出时同样以 `model_request_timeout` 结束。永久性模型失败（HTTP 400/401/402/404/422、`finish_reason` 内容过滤／`length`／`insufficient_system_resource`／`aborted`、已输出后的流中断）与请求／工具／纠错计数池耗尽另用 `model_request_failed`（2026-09-12 用户拍板新增，见下条）。
- 依据：DeepSeek 官方文档说明流式请求期间持续下发 SSE 保活注释 `: keep-alive`，且请求未开始推理 10 分钟后服务端关闭连接；官方未给出任何客户端超时建议值。故传输层 read timeout 只反映「有无字节」而非「有无业务输出」，不能用作空闲判据；低于请求时限的额外阈值会误杀慢生成，高于请求时限则被请求时限先覆盖。
- 官方证据（2026-09-11 只读核对，`https://api-docs.deepseek.com` rate_limit/error_codes/create-chat-completion）：保活注释、10 分钟未开始推理关连接、`finish_reason` 枚举含 `insufficient_system_resource`/`aborted`、无 408、无 `Retry-After`、无断流续读能力。
- 离线探针证据（2026-09-12，`test/spike/.venv`，pydantic-ai 2.40.0 + openai 3.8.0，127.0.0.1 本地假服务端、无真实调用）：保活字节会重置传输层 read timeout（3 秒空转不超时）；一条内容块后彻底静默约 1 秒触发 `httpx2.ReadTimeout`，body 阶段异常裸抛、不经 `ModelAPIError` 映射；已消费的文本在异常前已交付上层且 `get_output()`/`usage` 仍可用；SDK 隐式重试只包响应头之前，body 阶段断流不重发。该探针不覆盖真实保活间隔与 10 分钟断连。
- 本项只记录设计，不授权实现或真实模型调用；需生产版本 PydanticAI（2.41.0）与 DeepSeek SDK 复测时一并核对。

#### 流式重放边界（2026-09-12 用户拍板选 1）

- **非流式**（`agent.run`，当前生产路径）：未产出输出且属可重试白名单时，用重试池那 1 次重发（即上一条「到时分类」口径原样适用）。
- **流式**：`request_stream` 的流水一旦交给消费方，即使尚未产出任何文本块也**不重放**，按 fail-closed 结束（保留已保存内容并标未完成，取本次失败对应的终态原因码）。这是比上一条更严的边界：适配层的流上下文无法二次 yield，重放整次请求属更高一层的事。
- 交付范围：S4-05 按上述边界实现；S4-07 的 SSE 入口不另建更高层重放（下条已收口）。

#### 流式重放边界收口（S4-07，2026-09-12 用户拍板）

- **问题**：首个业务事件产出之前，是否要实现更高一层的重放（消费者尚未收到任何可见内容时重新发起整次请求）？
- **选项**：(a) 建更高层重放（首块前重发整次请求）；(b) 不建：`request_stream` 的流水一旦交给消费方即 fail-closed 结束，即使尚无可见文本块。
- **选择**：(b)。适配层的流上下文无法二次 yield，重放属更高一层的重建；真实 SSE 行为未验证前不预建恢复路径。
- **判定边界**：**任何产品/业务事件之后绝不重放**；provider keepalive 字节、隐藏思考（`ThinkingPart`／思考增量）、框架调试事件与 token/cache 数据都**不是**产品/业务事件，它们出现过不构成「已产出产品事件」。失败按本次失败对应的终态原因码结束，保留已保存的可见内容并标未完成（第 7 章 7.4）。
- **不受影响**：非流式 `agent.run` 仍按上一条已拍 A 在未产出输出时用重试池那 1 次；本项不改次数、超时、退避与错误码。
- **受影响文档**：本章「流式重放边界」、`../stage/stage4.md` §3／§6（S4-07）、`design-decisions.md` Stage 4 增量表、`../stage/evidence/S4-evidence.md`。

### 永久失败与计数池耗尽的错误码（2026-09-12）

- 新增已冻结 Run 终态码 `model_request_failed`，只表示「模型请求无法继续且不是墙钟超时」：永久性模型失败（HTTP 400/401/402/404/422 及其余白名单外状态、`finish_reason` 为 content_filter／length／insufficient_system_resource／aborted／error、已开始输出后的流中断、框架纠错预算耗尽）与每 Run 请求 20／工具 32／纠错 2 计数池耗尽。
- 语义边界：`model_request_timeout` 仍只表示单次请求墙钟（受 Run 剩余时间约束）与「重试用尽／剩余时间不足／已产出输出」；`run_timeout` 仍只表示 Run 总时限到期；三者不相互代用。`finish_reason=length` 仍属不重试的永久结果，不静默接受截断回答。
- 依据：08 原错误码集合没有能如实表达永久失败与池耗尽的码，前端封闭联合需要机器可读原因；本项不改变任何已拍次数、超时、退避与重试白名单。

### 思考模式默认（2026-09-12）

- 选：**保持 Provider 默认开启 Thinking**。Provider 同时支持非思考模式，因此这是本阶段的产品策略而非能力限制：不提供按 Run 的思考开关、不传关闭参数，默认行为即生效。模型 profile 必须如实声明思考支持与默认行为（不得声称模型无法关闭思考）。隐藏推理不进产品页面与 SSE 输出（见 8.7、8.8）。
- 依据（2026-09-12 真实调用实测，`backend/scripts/deepseek_smoke.py`，生产路径 pydantic-ai 2.41.0 + openai 3.13.0）：`deepseek-flash` 的响应包含思考内容（框架 `ThinkingPart`），官方 Models & Pricing 页也写“Supports both non-thinking and thinking (default) modes”；而框架的 DeepSeek profile 按 `deepseek-v4-*` 前缀推断，会把该 id 错报为 `supports_thinking=False`、`openai_reasoning_enabled_by_default=False`，因此**必须由本仓模型目录显式覆盖**为 `supports_thinking=True`、`openai_reasoning_enabled_by_default=True`（`thinking_always_enabled` 保持 False，如实反映 Provider 也能跑非思考模式）。
- 边界：思考 token 计入输出 token 与费用（实测 1 个词的回答消耗 15–23 输出 token），因此可见 `max_tokens` 不是总输出上界；单次请求的费用预检按**模型总输出上限**（384,000）与有效输入上限（250,000）保守计入（见 `../stage/evidence/S4-evidence.md`）。
- 本项只确定模型默认行为与 profile 归属，不新增 Harness 参数、不授权实现；执行侧模型参数与预算冻结仍归 S4-05。

### 容量、估算与溢出（2026-09-12）

模型窗口以生产 `deepseek-flash` 为准：context length 1,000,000、最大输出 384,000（官方 Models & Pricing 页面 2026-09-11 只读核对；`deepseek-v4-flash` 等旧别名已停用）。首版只支持该模型，配置出现未知模型 id 时启动拒绝。框架（pydantic-ai 2.41）的已知模型名与 DeepSeek profile 尚未包含该 id，实现时须显式覆盖模型 profile，并把该行为列入 S4-01 离线断言。

| 参数 | 已拍值 | 说明与边界 |
|---|---:|---|
| 压缩触发点（活跃 prompt 估算） | 有效输入上限 × 80% | 默认 200,000；随上限派生，不单独配置 |
| 有效输入上限（预算） | 250,000 tokens | 硬边界 32,768–524,288 |
| 保留最近完整交互 | 有效输入上限 × 10% | 默认 25,000；随上限派生，压缩后原样保留 |
| 摘要输出上限 | 6,144 tokens | 摘要请求的 max_tokens |
| 普通输出预留 | 8,192 tokens | 普通请求的 max_tokens，等于单次输出上限 |
| 安全余量 | max(4,096, 10% × 估算) | 仅用于「估算输入 + 输出预留 + 余量 ≤ 窗口」校验 |

- 活跃 prompt 指一次请求实际携带的全部输入（系统提示、工具定义、业务事实、历史与本轮消息）。token 估算取官方口径上界 `ceil(0.6 × 字符数)`，并与「最近一次真实 `usage.input_tokens` + 0.6 × 新增字符」取较大值；官方无 token 计数端点，首版不引入离线 tokenizer。
- 每次构造请求前重新估算：达到触发点先压缩；仍超过有效输入上限，或「估算输入 + 输出预留 + 安全余量」超过模型窗口时不发送，Run 以 `context_budget_exceeded` 结束。启动校验：`保留目标 < 触发点 ≤ 有效输入上限`，且摘要请求上界（触发点 − 保留目标 + 旧摘要上限 + 提示词余量）≤ 有效输入上限，且 `有效输入上限 + 输出预留 + 安全余量 ≤ 窗口`，不满足拒绝启动。`context_budget_exceeded` 属机器可读错误码，须登记进 S4-01 契约冻结清单（含中文展示语义，前端错误码为封闭联合）。
- 不建设 provider 报告上下文溢出后的应急压缩重试；`finish_reason=length` 归入不重试的永久结果。压缩因没有安全切点或摘要请求放不下而放弃后，同一上下文状态不再重复尝试，等上下文变化再试。
- 摘要请求自身放不下时收缩待摘要区间（只摘要最老的、放得下的部分，其余原样保留），收缩有界；缩到无可摘要区间即放弃压缩、保留旧有效上下文；真实请求仍放不下则按上述上限规则结束。

### 压缩 A 与失败 B

- 由 LLM 摘要旧历史，保留最近完整交互；不拆工具调用与结果，当前请求及当前 Run 完整交互不压缩。首版不实现 split-turn，实测频繁出现单轮过长再另议。
- 容量参数（触发点、有效输入上限、保留目标与摘要输出上限）见上方「容量、估算与溢出」；达到预算的 80% 尝试压缩。完整交互边界优先于精确数量。
- 每次构造请求重新检查容量；没有安全切点不硬切当前交互，放不下则明确结束。
- 摘要是历史辅助，不替代最新档案、安全限制、计划或草稿状态；这些事实仍从业务表读取。摘要输入与后续投影遵循第 7 章：排除未完成回答，保留失败/取消请求、经查询核实的操作与中断标注，不把部分回答转述为已发生事实。
- 摘要失败保留旧上下文；仍在安全输入预算内才继续，放不下则结束，不静默丢历史或反复原样请求。存储提交失败或取消不得通过此降级继续。
- 成功摘要持久化保存覆盖范围与来源关联，不删除原消息；新摘要提交成功才启用，取消先发生则不启用。持久化边界归第 7 章。

## Stage 4 联调费用护栏（2026-09-12 拍板）

- 本批 Stage 4 真实模型联调累计额度为 **10 美元**，是本轮新确认额度，不恢复旧授权；不包含 Stage 5 正式测评，也不作为产品长期默认预算。
- 每次实际请求发送前，按调用前核实并冻结的价格与计费口径预留费用上界；余额不足不发送，不自动提高额度。沿用已拍总输出上界口径，不以可见回答的 8192 tokens 代替总输出上界；缓存信息缺失按未命中计。价格或计费口径无法核实时不发送。
- 完成后按真实 usage 结算；断流或 usage 缺失时按本次预留额保守扣账，余额足够即可继续，不要求停下人工核账，不把未知费用记为零。
- 本批共用跨重启持久账本；正常请求、摘要、自动重试、纠错与手动重试全部纳入累计额度。重启、换会话、新建 Run 均不重置预算；重启后无法结算的在途请求按未知 usage 处理，不释放其预留额。
- 本地账本是保守费用护栏，不是 Provider 账单保证；既有请求数、超时、取消与重试边界不因额度充足而放宽。
- 当前仅授权拍板与文档同步，不授权实现或立即发真实请求；实现待后续指令，真实调用前仍须核实凭据和上述计费前置条件。密钥边界沿用第 10 章。

## 验收标准（待实现验证）

SSE 前端展示边界：

1. 用户可看到逐步输出的回答、草稿入口和最终运行结果；实际发生上下文压缩时有明确提示。
2. 后端五种状态按显示映射展示；失败和重启中断显示“未完成”及可理解的原因，取消显示“已取消”，残留文本不呈现为成功回答。
3. “依据与说明”可折叠且有事实支持；不展示原始或隐藏思维链、工具调试面板、Token/Cache 数值，不泄露密钥。
4. Run 已完成但草稿尚未确认时，正式业务事实保持不变，页面明确区分运行完成与草稿生效。

SSE 事件与当前状态恢复：

5. 输出中断网：关闭 SSE 并转查询；已保存部分可恢复且不重复拼接，不新建或取消 Run；最后未保存片段允许缺失。取消或失败后的部分文本标明未完成。
6. 刷新时执行仍在继续：恢复当前内容并轮询到终态；完成后页面不再等待。重复恢复不重复生成消息或草稿，也不重放历史通知。
7. 用户看到草稿 revision 1 后草稿已变为 revision 2：首次确认旧修订被拒绝；以最新修订确认仍须业务版本及领域校验。已提交草稿重复确认返回原结果，不重复递增业务版本。
8. 无业务事件 15 秒收到 heartbeat，数据库无心跳记录；45 秒无任何事件或触发 error 后，EventSource 被关闭并转查询。查询失败依次退避至 15 秒上限，成功恢复正常轮询。
9. 页面重新可见立即核对当前状态；终态及卸载清理连接和计时器。服务重启后遗留 Run 显示“未完成”及原因，已保存回答与草稿仍可查询。
10. 快速压缩完成的 toast 在 3 秒后消失；明显等待时提示不会在 3 秒后消失，持续到整理结束；可自动恢复的压缩失败不弹错误，不由展示层擅自更改 Run 状态。
11. 依据与说明随结果展示且可折叠，无独立推理流；草稿通知仅引用已持久化对象，确认与当前状态查询不依赖历史通知。

Harness 参数管理：

12. 启动时对本地配置进行校验，非法值或越过已拍硬边界的值被拒绝，不得静默放宽限制。
13. Run 开始后修改外部配置，不改变该 Run 已固定的有效配置。
14. Agent 无修改 Harness 配置或绕过硬边界的路径；不提供 Harness 参数 Web 编辑入口。

有限分类重试与受限纠错：

15. 模型请求永久性错误不触发自动重试；暂时性故障只按后续已拍错误映射及次数限制重试。
16. 无副作用、明确可修正的输出或工具参数校验失败可进入受限纠错；缺失事实、目标歧义转为询问用户，不补造业务事实。
17. 写入结果不确定时先核对已保存状态，不盲目重发；未经确认可安全重试的工具操作不自动恢复。
18. 草稿过期、安全拒绝与人工确认要求不能被自动重试或模型纠错绕过。
19. 每次额外尝试均计入统一执行与费用预算；取消后不再启动新尝试；核对框架、SDK 与应用层配置，确保不存在隐式重试叠加。
