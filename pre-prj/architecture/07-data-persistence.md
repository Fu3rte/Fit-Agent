# 7. 数据与持久化

> 本章仅搬运已拍设计，不授权实现；验收标准均为待实现验证。业务表职责已按归属拆入第 1–6 章（`business_drafts` 归第 1 章），本章不重复其表职责，只承载 SQLite 连接与事务、Schema 编号迁移、固定业务时区与运行时表。

## 本章已拍结论

| 决策 | 选项 | 选了 | 为什么 |
|---|---|---|---|
| 业务数据存储 | Markdown 文件为主 / 全关系明细 / SQLite 关系骨架与快照混合 | SQLite 唯一事实源 + 关系事实骨架 + 不可变 JSON 处方快照 + 训练完整修订 + Markdown 复盘正文（2026-09-07） | 兼顾事务与关联约束、完整历史还原、结构化统计及可读解释；Markdown 正文存在 SQLite，不另建文件事实源 |
| 持久化底线 | 执行句柄仅内存 / 状态全量持久化 | 任务状态、消息和执行轨迹必须写入 SQLite，不得仅存内存 | 服务重启后仍可检查历史状态与执行记录 |
| SQLite 访问 | ORM / `aiosqlite` + 手写 SQL | `aiosqlite` + 手写 SQL | 不引入 ORM；保持异步单体的简单边界 |
| SQLite 连接 | 连接池 / 单连接加单锁 | FastAPI 生命周期内保持一个连接；所有操作由同一个 `asyncio.Lock` 串行化 | 防止共享连接上的读取插入未提交事务 |
| Schema 迁移 | Alembic / 重建数据库 / 编号迁移 | 编号迁移 + `PRAGMA user_version` | 不引入 SQLAlchemy/Alembic，也不以重建数据库代替迁移 |
| 会话事实源 | 并行维护 pi JSONL 会话副本 / SQLite 单一事实源 | SQLite；不再并行维护 pi JSONL 会话副本 | 具体会话存储适配接口按 PydanticAI 与已拍持久化语义另行整理 |
| 业务日期时区 | A 固定业务时区，首次取本机时区 / B 始终跟随系统当前时区 | A（2026-09-07） | 固定“今天”、训练日期与到期锁定的解释口径，避免系统时区变化改写日程归属 |

## 责任边界

负责：

- SQLite 连接、串行化与事务规则（见 7.1）
- Schema 编号迁移与 `PRAGMA user_version`（见 7.2）
- 固定业务时区的持久化（见 7.3）
- 四张运行时表 `conversations`／`messages`／`runs`／`run_events` 的存储形态与运行时写入事务（见 7.4、7.5）

不负责：

- 11 张业务表的职责与业务语义：已按归属拆入第 1–6 章，`business_drafts` 归第 1 章
- 草稿确认事务内的版本检查、领域复查与业务写入编排（第 1 章；本章提供其连接与锁基础）
- Run 状态机流转、并发互斥、取消中断语义、重启恢复与 SSE 事件（第 8 章；本章只定运行时表的存储形态、事务配对与幂等键）
- 数据目录位置、密钥边界与备份操作（第 10 章）

## 业务规则

### 7.1 连接与事务

- FastAPI 生命周期内保持一个 `aiosqlite` 连接，不使用连接池。
- 所有数据库操作（包括读取和单语句写入）通过同一个 `asyncio.Lock` 串行访问；多语句事务从 `BEGIN` 到 `COMMIT` 或 `ROLLBACK` 全程持有该锁，防止共享连接上的读取插入未提交事务。
- 启用 WAL、外键和 `busy_timeout`。
- 事务只包含数据库操作，绝不跨越模型请求、工具执行或 SSE 推送；模型生成与重算在事务外进行。
- 第 1 章草稿确认事务、安排接受落盘等业务事务沿用本节连接与锁规则；事务内的编排与业务规则归第 1 章。

### 7.2 Schema 编号迁移

- Schema 变更采用编号迁移，以 `PRAGMA user_version` 记录当前版本；不引入 SQLAlchemy/Alembic，也不以重建数据库代替迁移。
- 具体迁移文件组织属实现细节，不逐项拍板（v1 L227「文件组织」）。
- Schema 迁移完成是启动流程中重启恢复的前置：迁移完成后才处理遗留 `pending`／`running` Run；状态转换规则归第 8 章。

### 7.3 固定业务时区

- 首次启动取本机时区并持久化为固定业务时区；之后判断“今天”、训练日期与日程到期均使用该时区。
- 不随系统当前时区变化或重启重新取值；存储位置属实现细节，不逐项拍板。
- 第 4 章日程生成与到期锁定、第 6 章“今天”与完成率 Wn 归属均消费本时区；到期锁定与计划切换日程联动的业务规则归第 4 章。

### 7.4 运行时表

四张最小运行时表与 11 张业务表分离，业务结构范围不包含运行时表：

| 表 | 职责与约定 |
|---|---|
| `conversations` | 会话 |
| `messages` | 用户与 Agent 消息 |
| `runs` | 一次 Agent 执行及其状态；`status` 仅允许 `pending | running | completed | failed | cancelled`；`client_request_id` 全局唯一，作为创建幂等键；`error_code` 保存机器可读错误码（重启中断使用 `interrupted_by_restart`）；手动重试通过 `retry_of_run_id` 指向旧 Run，不复活旧记录 |
| `run_events` | 后台工具轨迹、状态变化和指标；`event_type + payload_json` 通用形态，不为每种轨迹建立独立表；`id` 为 `INTEGER PRIMARY KEY AUTOINCREMENT`，仅作数据库行身份 |

- 会话事实源为 SQLite，不再并行维护 pi JSONL 会话副本；消息适配契约见下节。
- `run_events` 不承担首版客户端事件补读或重放契约；数据库行 ID 不等于前端恢复游标；不新增事件自动清理策略。SSE 事件与恢复规则归第 8 章。
- 回答实时流式展示，合并文本分批持久化，不逐 Token 或逐传输块写库；取消、失败及断线后可恢复已保存部分，最后尚未落盘片段允许丢失；部分回答不冒充完整成功 Assistant 消息。
- 完整 API Key 不得进入 `run_events` 或异常详情；密钥边界归第 10 章。
- 运行时表字段名、索引与传输字段按既定语义整理，不逐项拍板；前端展示契约不必直接复制数据库表。

#### 消息存储与上下文适配契约

- 用户提交的消息是应用事实，与 pending Run 同事务保存；框架完整 `ModelRequest` 在运行中形成，不替代或覆盖已保存的用户请求。
- 框架消息使用 PydanticAI `ModelMessagesTypeAdapter` 原生 JSON 序列化与反序列化，保留允许存储的消息结构、工具调用与结果、顺序和 Run 关联；完整 Key 不得进入消息负载。消息历史不冒充实际 Provider wire 请求审计。
- 只追加本次 Run 的新增框架消息，不重复保存传入的整个会话历史；用户请求事实与框架请求中的用户内容关联，在模型上下文中不得重复注入。框架负载保存在 `messages` 职责内，物理行粒度、字段和索引由实现者确定，不新增消息副本事实源或工具配对触发器要求。
- 持久记录、用户展示与模型上下文分开：已保存部分回答可以展示，但必须与完整成功回答区分；未完成回答不作为正常 Assistant 回答回灌。提示新鲜度在运行时处理，不为更新提示而删除已保存的允许存储的原始消息内容。
- 取消事务提交后，不补存晚到的框架运行快照，也不另建终态后诊断快照写入路径。保留此前已保存的用户请求、消息、部分回答和轨迹，接受最后一段运行记录不完整；迟到结果不能写成成功回答或覆盖终态。底层取消、收尾及已发生副作用核对仍须执行，业务状态不因取消而自动回滚。
- 下一轮上下文保留失败/取消请求及已确认的工具结果或业务状态，排除未完成回答，并明确标注中断状态；不因 Run 未完成而整段丢弃用户请求和已发生操作的语境。仅使用已保存记录或经业务查询确认的状态，不为补上下文而回写被拒绝的晚到快照。
- 缺失或不确定的工具结果不能解释为“操作未发生”；框架的悬空调用修复只解决消息格式，真实副作用必须查询业务状态。构建历史不执行工具、不恢复旧 Run；历史中的取消请求不是待自动执行指令，手动重试仍创建新 Run。
- Stage 0 验证存储、原生序列化及取消后的拒写边界；实际上下文投影、模型/工具接线和业务状态核对由 Stage 4 负责。

#### Stage 4 已拍：摘要持久化

- 成功摘要保存覆盖范围与来源关联，不删除原消息；摘要只是派生的上下文辅助，不成为业务事实源。
- 新摘要提交成功后才启用；提交时核对 Run 状态，取消先发生则不启用、不补写迟到摘要。失败保留旧有效上下文。
- 复用既有 SQLite 持久化边界；具体字段及索引由实现者整理，不引入 pi JSONL 副本。压缩行为与剩余策略见第 8 章 Stage 4 已拍 Harness 策略。
- 来源：Stage 4 计划讨论用户明确确认；只授权设计记录，不授权实现。

### 7.5 运行时写入的事务规则

- 用户消息与 `pending` Run 在同一事务创建。
- Assistant 消息与 `completed` 状态在同一事务提交，且状态更新必须检查原状态为 `running`。
- 用户取消以条件更新将 `pending` 或 `running` 改为 `cancelled`，并在同一事务追加取消事件；取消后不得再写 Assistant 消息或改为其他终态。取消的触发条件与中断语义归第 8 章。
- 相同 `client_request_id` 的请求返回已有 Run，不重复创建消息或 Run；活跃 Run 检查与 `409 conversation_busy` 归第 8 章并发互斥。

- 第 1 章确认事务沿用本章连接、单锁与事务规则；事务内版本检查与领域复查归第 1 章。
- Run 状态机流转、并发互斥、取消中断、重启恢复与 SSE 事件恢复归第 8 章；本章只定运行时表存储形态、写入事务配对与 `client_request_id` 幂等键。
- 固定业务时区供第 4 章（日程生成与到期锁定）与第 6 章（“今天”与 Wn 归属）消费。
- Provider 配置和明文 API Key 与会话、业务数据保存在同一个 SQLite 数据库；数据目录位置、密钥边界与备份方式（含运行中备份使用 SQLite Backup API）归第 10 章。

## 验收标准（待实现验证）

1. 服务重启后已保存的会话、消息、Run 状态与后台执行轨迹仍可查询；任务状态、消息和轨迹不因仅存内存而丢失（v1 L31、L345–346）。
2. 相同 `client_request_id` 重复发起请求返回已有 Run，不重复创建消息或 Run（v1 L356）。
3. 用户消息与 `pending` Run 同事务创建；Assistant 消息与 `completed` 同事务提交且检查原状态为 `running`；取消以条件更新改状态并同事务追加取消事件，取消后不再写 Assistant 消息或改为其他终态（v1 L362–364）。
4. 输出中断线或取消后，已保存的部分回答可恢复，最后尚未落盘片段允许丢失；部分回答不冒充完整成功 Assistant 消息（v1 L361）。
5. `run_events.id` 不作为前端恢复游标，首版不做事件 ID 补读或重放，也不新增事件自动清理策略（v1 L359；PLAN.md 2026-09-08 收窄前「SSE 事件与当前状态恢复」覆盖范围 L113（历史来源）；现承载见第 7 章 7.4、第 8 章 8.7）。
6. Schema 变更按编号迁移 + `PRAGMA user_version` 执行，不引入 Alembic、不以重建数据库代替迁移；迁移完成后才执行启动恢复（v1 L34、L368）。
7. 首次确定业务时区后，修改操作系统时区并重启，固定业务时区保持不变；同一时刻的业务日期、到期锁定及完成率分母不因系统时区切换而改变（PLAN.md 2026-09-08 收窄前「业务表设计」L249（历史来源）；现承载见第 7 章 7.3）。
