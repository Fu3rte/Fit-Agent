# 健身助手 Agent 记忆设计 ·

### 一、核心主张

**不上向量库。SQLite 管数据，Markdown 管语义，分层管注入。**

健身场景的记忆本质是带时间戳的数值时间序列，查询形态是“上次卧推多少”、“这周练了几次”等精准检索与聚合统计，一条 SQL 即可解决。向量检索解决的是模糊语义相关性，在此场景下不仅检索精度低，还会带来严重的算术与历史幻觉。



### 二、三层存储分工与生命周期治理

| **层级**       | **载体** | **存储内容**                                | **设计原理**                                             |
| -------------- | -------- | ------------------------------------------- | -------------------------------------------------------- |
| **结构化数据** | SQLite   | 训练明细（ADD-only）、体重围度、执行计划    | 用于计算容量趋势、渐进超负荷、1RM 估算；保证 100% 确定性 |
| **语义记忆**   | Markdown | 用户画像、沟通偏好、慢性伤病/红线、观察笔记 | 面向 LLM 的自然语言约束，保证言外之意与安全边界长久生效  |
| **时效状态**   | SQLite   | 当日疲劳、局部紧绷、睡眠不足等急性状态      | 字段带 `expires_at`，时效过后自动退出上下文，防过度保护  |

#### 1. 状态生命周期切分

- **慢性限制（永久常驻）：** 腰椎间盘膨出、肩峰撞击禁忌动作。写入 Markdown，永不自动过期。
- **急性状态（动态过期）：** “昨晚没睡好”、“今天右肩前束微紧”。存入 DB 并打上 TTL（如 24~72 小时）。过期数据保留在数据库供溯源，但立即停止向 Prompt 注入，避免出现“半年前落枕导致半年不敢安排深蹲”的缺陷。

#### 2. 急性向慢性晋升机制（Consolidation Worker）

建立离线/异步记忆整合任务（如每周定时执行）：



- **触发规则：** 扫描历史记录，当特定解剖部位在移动时间窗口内高频触发急性警报（如 60 天内连续 3 次打卡出现“右膝微痛/发炎”）。
- **晋升链路：** 异步 Worker 提取统计事实，向 Markdown 的“慢性限制/伤病观察”写入一条待确认条目（`[待确认红线] 近两个月深蹲后右膝不适 3 次，建议下调深蹲行程并提醒热身`），在下一次主交互中引导用户确认，闭环沉淀为永久安全红线。

### 三、输入解析与实体归一化管道（Ingestion Pipeline）

用户自然语言报练通常碎片且口语化（如“今天推了60，做不动了降到50做了两组各8次，热身不算”），必须在写入端完成标准化。



```
[ 用户口语输入 ]
       │
       ▼
[ 前置解析器: 轻量模型 / Tool Calling (JSON Schema 强校验) ]
       │
       ├─► 缺省字段处理: RPE 缺省标记默认值 (如 -1 / 兜底提示)
       │
       ▼
[ 动作实体归一化 (Entity Resolution) ]
       │  查别名映射字典 (Alias Dict) / 微型 Embedding 对齐
       │  "平板卧推" / "杠铃胸推" / "推胸" / "Bench" ──► exercise_id: 1001 (杠铃卧推)
       │
       ▼
[ 确定性写入 ] ──► SQLite (ADD-only 记录入库)
```

1. **严格 Schema 提取：** 通过单次 Tool Call 将文本转为强类型结构（`exercise_raw`, `weight_kg`, `reps`, `sets`, `rpe`, `is_warmup`），阻断脏数据入库。
2. **动作实体归一化：** 必须通过内置别名映射表将自然语言动作统一对齐至标准 `exercise_id`，防止 SQL 查询时因名称不匹配漏查历史数据。

### 四、四段式上下文注入体系（静态常驻 + 前置预取）

单轮上下文分为“常驻层”与“按需层”，由前置中间件（Middleware）完成组装，严格杜绝原始日志流水进入 Prompt。



#### 1. 常驻层（锁定前缀 ~294 token，保证 Prompt Caching 极致命中）

按优先级严格排序，顺序不可调换，确保安全红线始终置顶：



1. **安全红线（~72 token）：** 伤病禁忌、动作上限、禁做列表。永不覆盖、永不压缩、永不被挤出。
2. **用户画像（~87 token）：** 训练目标、训练年限、器械条件、每周频次、沟通风格偏好。
3. **当前计划（~52 token）：** 本周推进进度 + 今日待练部位/主项。
4. **动态状态卡（~83 token）：** 前置 Python 中间件执行 SQL 聚合计算后的结论文本（如：“*卧推近 4 周容量 +8%，RPE 稳定 7，建议 62.5kg；昨晚睡眠欠佳，注意组间休息*”）。**只注结论，永不注入原始流水。**

#### 2. 按需层前置化预取（Middleware Pre-fetching）

摒弃让主 Agent 在对话中再次发起 Tool Call 二次推理的传统做法（避免额外增加一次网络往返和千级别 Token 消耗），改由 API 网关/前置 Router 在进入主模型前直接完成 SQL 预取与拼接：



- **命中动作名称：** 正则或实体提取命中标准库动作 $\to$ 预先拉取该动作近 8 次负荷曲线（~90 token）。
- **命中伤病/疲劳词：** 输入包含“痛/紧/拉伤/难受” $\to$ 预先拉取同部位历史所有损伤记录与急性记录（~300 token）。
- **提出调整计划诉求：** 预先拉取近期周期依从性与关键指标趋势。
- **周期结束：** 预先拉取上期计划全貌与完成度汇总（~400 token）。

### 五、端到端系统架构流向

```
                        [ 用户自然语言输入 ]
                                 │
                                 ▼
                   [ API 网关 / 前置中间件 Pipeline ]
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
[ 写入解析器 (Schema 提取) ]                    [ 读取组装器 (Router 预拉取) ]
  ├─ 别名归一化 (exercise_id)                     ├─ 读取 Markdown (安全红线 + 用户画像)
  ├─ 写入 SQLite: ADD-only 明细                   ├─ 查 DB: 急性状态 (过滤已过期条目)
  └─ 写入 SQLite: 急性状态 (带 expires_at)        ├─ 执行 SQL: 算本周计划与趋势聚合结论
                                                 └─ 命中关键词: 预取近8次曲线/伤病记录
                                                         │
                                                         ▼
                                             [ 组装单轮 Prompt 上下文 ]
                                             (前缀字节级对齐，命中 Prompt Cache)
                                                         │

                                                 [ 主 Coach Agent ]
                                                 (单次直出教练建议)
                                                         │
                                                         ▼

┌────────────────────────────────────────────────────────────────────────┐

│ 扫描近期高频急性警报 (如 60 天内同一部位不适 ≥ 3 次) ──► 自动晋升长期安全红线  │

```

### 六、核心纪律与效能指标

#### 两条硬纪律

1. **数值必须确定性计算。** 容量趋势、1RM 估计、周期依从性计算全部封死在 Python / SQLite 内部，大模型只接收“计算结果”，彻底消灭算术幻觉。

#### 效能对比

- **Token 消耗与注意力收益：** 连续使用 2 年后，全量历史注入需 ~48,000 token，本方案分层注入稳定在 **~300 - 800 token**（压缩比超 50 倍），且绝无注意力稀释导致的安全红线失效问题。
- **Prompt Caching 命中率：** 由于常驻前三段严格保持字节对齐不变，主对话的 Prompt Caching 命中率可达 **95% 以上**，首字延迟（TTFT）稳定控制在 1 秒以内。
