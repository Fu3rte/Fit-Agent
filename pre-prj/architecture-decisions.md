## 已确认决策

| 决策 | 已选方案 | 原因或约束 |
|---|---|---|
| 语言边界 | 后端与 Agent 使用 Python；前端使用 TypeScript | 后端基座已定为 PydanticAI；不再按 pi 内核 Python 移植路线推进，前端历史选型不因本次同步自动重选 |
| Agent Python 基座（覆盖旧移植路线） | PydanticAI 定案（2026-09-06），LangGraph 对照取消；spike 三项缺口验收结果见根 PLAN.md | 不把 spike 通过当作完整产品已实现；业务规则独立于 Agent 框架，未定能力仍按根计划推进 |
| Harness 决策时序 | 本地配置 + 硬边界、Run 开始固定配置、有限分类重试与受限纠错原则已拍（2026-09-07） | 次数、超时、退避、错误映射、预算与压缩阈值仍待拍；先检查 PydanticAI 与 Provider SDK 已有机制，不再以等待 pi 移植源码为前置条件，不建设 Harness Web 设置页 |
| Agent 测评 | 代码确定性检查 + LLM judge + 人工校准、争议裁决与抽检；主体方案已确认（2026-09-07，见下节及 PLAN.md） | 产品核心流程落地后必须测评；不替代产品自动化测试和 Windows 人工验收，不授权当前实现或调用 |
| 首版产品测试范围 | 选择 A：核心自动化测试 + Windows 人工验收；自动化覆盖领域校验、事务、草稿过期与幂等，同一套核心测试须能在 Linux 和 Windows 运行；Windows 按清单实测安装、启动、业务流程与重启恢复 | 不采用 B“额外建设浏览器端到端自动化”；优先保障数据正确性，界面交互由人工验证；产品测试不替代已确认必做的 Agent 行为测评 |
| 前端基础栈 | React + TypeScript + Tailwind CSS + shadcn/ui | 保持轻量，只按需添加组件；其他库后续逐项决定 |
| 前端构建与交付 | 首版使用 Vite；开发时使用 Vite 开发服务器，生产构建产物由 FastAPI 静态托管 | 保持单 Python 进程部署，生产环境不增加 Node.js 运行时；具体目录结构属于实现细节 |
| 首版发布与启动方式 | 选择 A：以 Python 项目形式发布，用户安装 Python 与项目依赖后按文档启动；发布产物包含构建好的前端，运行时不需要 Node.js | 不采用 B“独立可执行程序”；不制作 exe 或其他桌面程序，保持可安装、可启动、可演示的本机 Web 产品交付 |
| 开发环境与首版验收平台 | 选择 B：Windows 为首版成品验收平台；Agent 在 Linux 端开发和编写代码，用户在 Windows 端已克隆的仓库中进行实测 | 利用 Linux 的命令行开发优势，同时以 Windows 实际安装、启动和核心流程验证作为成品验收依据；开发与验收须对应同一代码版本，Linux 检查通过不能代替 Windows 实测证据 |
| 运行架构 | 进程内异步单体 | 本地单用户场景不引入跨进程协调 |
| 业务模块划分 | 划分为档案与安全限制、动作目录、计划与训练指导、训练记录与更正、统计与复盘数据五项业务职责；共用应用层草稿确认流程 | 均在同一 Python 进程内，不拆独立服务，不要求每项职责建设复杂子系统；业务规则独立于 Agent 框架，应用层负责流程与事务编排 |
| 系统拓扑 | Browser → 单个 Python 进程 → 模型 HTTP 端点 | 本地和云端模型均位于 Agent 进程之外 |
| 部署与访问范围 | 选择 A：仅允许在本机部署并由本机浏览器访问；服务只监听回环地址，不提供局域网或公网访问，不建设账号系统；保留基本的 Host/Origin 校验 | 不采用 B“允许局域网设备访问”；降低健康数据与模型密钥暴露风险，保持本地单用户部署简单；此限制针对 Fit-Agent Web 服务，不改变已确认的云端模型调用能力 |
| ASGI 服务 | 单 Uvicorn Worker | 不依赖多 Worker 共享内存或任务协调 |
| Web 框架 | FastAPI + Uvicorn | 原生异步、请求校验及 ASGI 支持 |
| 流式通信 | SSE，使用 FastAPI/Starlette `StreamingResponse` | 浏览器只需接收服务端事件，不引入 WebSocket 和额外 SSE 库 |
| 外部队列 | 不使用 Redis、Celery 等外部队列 | 任务在单进程内异步执行 |
| 持久化底线 | 任务状态、消息和执行轨迹必须写入 SQLite，不得仅存内存 | 服务重启后仍可检查历史状态与执行记录 |
| SQLite 访问 | `aiosqlite` + 手写 SQL | 不引入 ORM；保持异步单体的简单边界 |
| SQLite 连接 | FastAPI 生命周期内保持一个连接；所有操作由同一个 `asyncio.Lock` 串行化 | 防止共享连接上的读取插入未提交事务 |
| Schema 迁移 | 编号迁移 + `PRAGMA user_version` | 不引入 SQLAlchemy/Alembic，也不以重建数据库代替迁移 |
| 会话事实源 | SQLite；不再并行维护 pi JSONL 会话副本 | 具体会话存储适配接口按 PydanticAI 与已拍持久化语义另行整理 |
| 事件循环保护 | 同步阻塞 SDK 必须通过 `asyncio.to_thread()` 执行 | 禁止阻塞 Uvicorn 事件循环 |
| 重启恢复 | 启动时将遗留的 `pending`、`running` 统一改为 `failed` | 不做断点续跑，由用户手动重试 |
| 中断错误码 | `interrupted_by_restart` | 区分服务重启中断与普通执行失败 |
| 本地模型边界 | Ollama 等作为独立 HTTP 服务调用 | 本地模型不占用 Agent 进程内的模型运行逻辑 |
| 首版模型 Provider（历史范围，未全部重选） | 历史目标为 OpenAI-compatible 与 Anthropic Messages API，含 DeepSeek 与本地 Qwen HTTP 端点；当前仅 DeepSeek 官方兼容端点完成 spike 验证 | Anthropic 与本地 Qwen 验证暂缓，不推定已支持或已取消；最终支持范围仍须确认；Token/Cache 指标仅留后台，不向产品页面展示 |
| Provider 验证目标（历史记录） | 历史要求覆盖 DeepSeek 与本地 Qwen；当前以根 PLAN.md 的 DeepSeek spike 验收及暂缓项为准 | 不以 Mock 代替真实互操作验证，不因 spike 通过扩大调用或联调授权 |
| 用户数据目录 | 使用 `platformdirs` 解析跨平台用户数据目录；Windows 数据库路径为 `%LOCALAPPDATA%\Fit-Agent\app.db` | 数据文件继承操作系统用户目录 ACL，不自建跨平台权限系统 |
| Provider 配置与密钥 | Provider 配置和明文 API Key 与会话、业务数据保存在同一个 SQLite 数据库 | 本地单用户场景接受依赖用户目录 ACL；拥有相同操作系统用户权限或数据库副本者可以读取 Key |
| Run 状态 | `pending`、`running`、`completed`、`failed`、`cancelled`；`cancelled` 为独立终态 | 用户主动取消不计作执行失败 |
| Run 并发与活跃会话 | 全局最多一个 `pending` 或 `running` Run；同一时刻只允许一个会话发起 Agent 对话 | 单用户首版不设计多会话并行或跨会话排队 |
| 同会话互斥 | 已有 `pending` 或 `running` Run 时，不同请求返回 `409 conversation_busy`；相同 `client_request_id` 返回已有 Run | 保证上下文与消息顺序确定 |
| 运行中输入 | 首版不支持 Queue 或 Steer | 先完成核心产品，成品后再评估 |
| 用户取消 | 仅由用户点击取消按钮触发；`pending` 或 `running` 转为 `cancelled` | SSE 断开或页面刷新不取消；取消为尽力中断，不承诺回滚已发生副作用 |
| 业务事实确认与写入 | 选择 A：对话发起业务变更并生成结构化草稿，允许草稿卡轻量纠错；用户点击确认按钮后，由业务接口校验并提交；适用于档案与限制变更、计划启用/替换、训练记录保存及历史记录更正 | 不采用 B“按钮与自然语言均可直接确认”；确认对象必须明确，不依赖模型解释“好的”等表述；Agent 不得绕过确认直接修改正式业务事实 |
| 首版业务交互形态 | 选择 A 增强版：对话与 Agent 是唯一业务变更发起入口，业务页面保持纯只读看板；草稿卡展示结构化结果和变更 Diff，并支持关键字段轻量内联纠错；所有正式写入必须再次确认 | 不建设 B“对话与完整业务编辑表单双入口”；避免单数字微调也必须重新对话，不建设完整计划编辑器 |
| 草稿隔离与确认事务 | 所有业务变更先生成 Pending 草稿；用户点击“确认采纳”后，在同一数据库事务内完成版本检查、领域规则复查、正式业务写入和草稿转为 Committed；提交须幂等 | 草稿与正式业务事实隔离，确认前不污染正式数据；不允许检查与写入之间出现 TOCTOU 空隙 |
| 业务意图与受限组合草稿 | 选择受限 B：同一次用户意图中具有直接依赖关系的变更，可放在同一计划草稿中，一张卡展示、一次确认、原子提交；拟议档案变更保存在 proposed_profile_patch_json，基线业务版本保存在 base_business_version | 不采用 A“按业务对象拆卡、分别确认”，也不支持任意跨业务拼装；暂存属于 SQLite 业务草稿，不是短期记忆，不新增记忆系统或通用组合草稿系统 |
| 草稿过期判定与版本范围 | 选择 A：使用统一业务版本 context_version，每次成功提交正式业务变更使其 +1，受限组合提交也只递增一次；草稿以 base_business_version 保存生成时的数据版本，首次确认事务内检查 draft.base_business_version == user.context_version | 不采用 B“按依赖分别检查版本”；单用户首版接受无关业务变更也会使旧草稿过期，以避免遗漏依赖及旧草稿覆盖新数据；不建设自动合并机制 |
| 过期草稿恢复 | 返回 409 Conflict，错误码 draft_stale，并指明变更项；用户点击“按最新数据一键重算”后生成新草稿，通过 parent_draft_id 关联旧草稿，展示新旧 Diff 并再次确认 | 采用“拦截 + 一键重算”的 A 增强版，而非自动合并或静默采纳；重算不直接修改正式业务事实 |
| 已生效计划与新限制冲突 | 选择 A：使用当前计划提供训练指导时，按最新限制复核；发现冲突则阻断整份计划的训练指导，旧计划仍可查看但不得作为可执行建议；修订草稿经校验与用户确认后才能继续 | 不采用 B“只阻断冲突训练日”；不静默修改正式计划，不引入部分可用状态或后台巡检；仍允许记录实际已发生的训练，红旗症状始终阻断常规训练处方 |
| 草稿能力当前交付范围 | 只锁定 P0：草稿工具与卡片、Diff、关键字段内联修改、幂等提交、版本拦截、一键重算和业务只读页；P1 及其他后期内容均待具体情况再拍板 | 后期需求、分期与优化方向均未确认，不作为当前成品的交付或验收前提，不预先设计具体机制；PRD 已明确的安全底线仍属于当前成品要求 |

## 业务数据关系与历史版本规则

### 已确认选择

| 决策 | 选项 | 选了 | 为什么 |
|---|---|---|---|
| 训练历史对照 | A 当前计划 / B 具体计划版本 / C 具体计划版本 + 当次安排快照 | C | 同时还原原计划、已接受的临时调整与实际完成情况，后续计划变化不改写历史 |
| 恢复旧计划 | A 重新激活旧版本 / B 基于旧版本生成新版本 | B | 保持版本顺序清晰，恢复前按最新条件重新校验并确认 |
| 训练记录更正 | A 原地修改附说明 / B 完整修订版本 / C 全业务事件溯源 | B | 最新有效版本参与统计，旧版本可追溯，不建设事件溯源系统 |
| 更正后的统计与复盘 | 历史数值重算；旧复盘标记依据已变更，不静默重写 | 已确认 | 数值反映最新有效事实，旧解释保留其历史语境 |
| 回归期归属 | 当次训练保留回归期标记，确认恢复只影响后续训练 | 已确认 | 切回常规计划不能把回归期历史重新混入常规表现对比 |

### 数据闭环与安排范围

```text
已确认档案与安全限制 → 正式计划版本 → 针对具体训练的安排快照
                                              ↓ 对照
                                        实际训练记录及修订
                                              ↓
                                        确定性统计与复盘
                                              ↓ 提出建议
                               后续训练安排草稿或新计划草稿 → 确认生效
```

- 计划表示长期准备怎么练；当次安排表示某次训练准备怎么练；实际记录表示真正练了什么，三者不能混为一份数据。
- “当次安排”不限于今天：用户可以训练结束后反馈，再制定未来几天的安排；每次安排明确对应的训练日期或训练次序。反馈不自动成为正式记录，后续建议不自动成为已接受安排。
- 当次安排绑定具体计划版本与训练日，并保存目标和已接受调整的快照。临时调整只影响对应训练，不改长期计划；长期调整及接回方案形成新计划版本。
- 未来安排仍受既定使用时安全复核约束，提前确认不代表可以绕过最新限制或红旗阻断。
- 聊天与复盘解释引用正式业务事实，不构成另一份事实源；此闭环不扩大既定受限组合草稿的事务范围。

### 调整接受时间与记录规范

- 用户点击确认接受调整时，必须立即持久化安排及接受时间；版本检查、领域复核、正式写入、草稿提交与 `context_version +1` 在同一事务完成，失败则全部回滚，重复确认不重复递增。
- 不得先在会话中视为已接受，等训练打卡或补录时再补写。训练发生时间与系统接受、记录、更正确认时间必须区分，不得把事后反馈倒填成当时已接受的调整。
- 后续计划修改不改变历史安排快照；已保存训练记录的对照安排不得被静默覆盖，也不能通过事后减组改写原来的执行标准。
- 补录有可信历史安排时可关联对应快照；没有时允许无计划、无对照安排，只保存实际表现，不强行套用当前计划或补造目标。
- **“符合处方目标的工作组”以当次安排快照判定，不以计划版本直接判定；无对照安排的记录仅是“历史表现数据”，不得作为“执行度证据”，Agent 复盘同样遵守。**

### 计划与训练记录的历史

- 正式计划版本的处方内容不可原地修改，同一时刻最多一个当前版本；旧版本保留历史。
- 恢复原计划采用 `v1 常规 → v2 接回 → v3 基于 v1 恢复的常规版本`，记录来源版本，按最新器械、限制和安全状态复核后由用户确认，不重新激活 v1，也不自动恢复。
- 更正保留同一次训练的完整修订版本、修改前后内容、确认时间和来源草稿；不是新增一次训练。误录整次训练可经草稿确认作废，不物理删除历史。
- 统计只使用每次训练最新有效的确认版本；新增、更正或作废后重新计算受影响统计，显示数据更新时间，不重复计入旧修订。
- 旧复盘文本不静默改写；其依据数据变化时标记已变更，可重新生成。
- 回归期标记随对应训练历史保留；恢复常规计划后，之前的回归期训练仍不进入 PR、常规连续进步及处方目标符合情况对比；首版不展示合格组百分比。标记录错只能经历史更正确认修正。
- 回归期实际工作组仍展示，按接回安排单独计算完成情况，不混入常规训练对比；用户确认恢复常规计划后，后续训练恢复常规口径，不按“1–2 次”自动结束。

### 验收用例（待实现验证）

- 接受卧推从 3 组减为 2 组后立即重启：安排及接受时间仍在，业务版本仅递增一次；重复确认返回原结果。以后长期计划改成 4 组，该次仍显示原计划 3 组、当次安排 2 组、实际完成 2 组，是否符合处方目标按当次安排判定。
- 用户训练后反馈并确认未来几天安排：未来安排生效，但不能把本次训练目标倒改为事后提出的目标；无对照安排的补录不得输出符合处方目标的组数或执行度结论。
- 确认恢复旧计划内容后形成新常规版本，旧版本内容不变；最新限制冲突时不得启用，回归期历史不因恢复而进入 PR。
- 卧推 80kg 更正为 60kg 后，PR 不再使用 80kg，旧记录可追溯且训练次数不增加；确认作废后不参与统计；受影响的旧复盘标记依据已变更。

## 统计验收口径

### 已确认选择

| 决策 | 选项 | 选了 | 为什么 |
|---|---|---|---|
| 训练完成率 | A 按训练次数 / B 按工作组 | A | 区分完成一次训练与组级处方执行，不用多做的组抵消漏练 |
| 安排变更对历史的影响 | A 始终按最新安排重算 / B 未来可调整、历史不倒改 | B；日程与当次处方分开锁定 | 不洗掉漏练，同时保留执行前的当日状态调整 |
| 工作组展示 | 三桶组数 / 额外计算合格组百分比 | 三桶组数，名称为“符合处方目标的工作组” | 表达执行情况，不暗示其他组无效；首版不额外展示百分比 |
| 缺失判定信息 | 当作未符合 / 单列待补全 / 忽略缺失要求 | 单列待补全，工作台与复盘共用状态 | 不编造事实，不让两个界面各用一套词汇或判定结果 |
| 一天多练 | 每天最多一次 / 独立训练身份允许同日多次 | 支持同日多次，歧义时询问 | 日期不作为唯一身份，不增加早晚模板、自动拆分或复杂排程 |
| 周与版本归属 | 全局自然周 / 按计划版本的 Wn | 完成率及训练复盘按 Wn，新版本独立统计 | 不迁移、不合并旧版执行度，仅做统计分段，不建设复杂周期系统 |
| PR 来源 | A 所有带数字的组 / B 正式有效且可比较的工作组 | B | 草稿和待补全训练记录不污染 PR，补全并确认正式有效后自动参与 |
| RIR 边界 | A 单值精确匹配 / B 隐含容差 / C 处方显式区间 | C，包含端点，无隐藏容差；单值为同值上下界 | 页面处方与确定性判定一致，不能事后改标准 |
| 三桶判定顺序 | A 缺字段优先 / B 已知未满足优先 | B | 已知未满足即可判为未符合，否则必要信息缺失为待补全 |
| 转正式门槛 | A 所有字段填满 / B 实际事实明确 / C 组级部分提交 | B，整条确认 | 不强迫编造 RIR 和反馈，不引入部分提交复杂度 |
| 训练反馈 | A 必填 / B 可选并主动询问 | B | 不阻塞事实落盘，缺反馈时仍依据既定渐进方法和可信数据提出建议 |
| 人工辅助 | 独立动作类型 / 单组执行信息 | 单组执行信息，异常申报制 | 未提时草稿显示无辅助并经用户确认；提及含糊辅助时区分保护与实际帮助 |
| 辅助组 PR | A 排除普通 PR / B 辅助 PR / C 拆算独立次数 | A | 保留真实工作组但不混入独立完成纪录，不建设辅助 PR 或拆算 |

### 完成率、锁定与归档

- 完成率 = 同一计划版本、同一 Wn 内已完成的计划训练次数 ÷ 截至当前已到训练日期的应训练次数。休息日不进分母，未来未到日期的安排不进分母，漏练保留；整周安排次数可另外展示。
- 不能只从已有打卡计算分母，必须能列出没有打卡的应训练安排。用户在正式记录中明确确认本次训练已完成，且至少包含一个实际工作组，才计入分子；完成不等于所有工作组符合处方目标。
- 同一次安排最多贡献一次完成，无安排训练、额外训练及同次多次反馈不增加计划完成次数。分母为零显示“暂无”，不是 0% 或 100%。
- 日程与完成率分母在训练日到达（或该次已确认完成／漏练）时锁定，不能删除或改期洗掉漏练。未来尚未锁定的安排可经草稿确认换日、删减，不改变已锁定部分。
- 当次处方单独处理：当天仍可在执行相关训练前确认减组等调整，立即落盘，沿用同一事务和 `context_version +1` 规则；不允许事后倒改。
- 事后真正补练作为额外训练展示，原漏练及分母不变；当天确实完成、后来才补录属于历史事实更正，不等同于事后补练。
- W1 = 计划版本开始日期起连续 7 天，W2 = 随后 7 天，以此类推。完成率与训练复盘按计划周 Wn，不能把“周一至周日”写成全局口径。步数、体重采用自然周的口径不构成新增这两项首版功能的承诺。
- 新计划版本开启独立统计区间，不继承旧计数；旧版本连同其历史完成率归档，不迁移、不合并。归档不禁止真实记录更正，相关历史统计仍按最新有效事实重算。
- 计划版本分段只改变对应完成率和训练复盘的归属，不建设复杂周期系统，也不把新版本无应训练次数显示成 0%。

### 组级判定与统一用语

- 展示名称统一为“符合处方目标的工作组”，用于说明实际表现是否符合当次处方，并为复盘、后续调整提供证据；不代表动作技术、安全性或训练效果合格，不能单凭组数自动加重。
- 工作台三桶与复盘沉淀共用“符合目标／未符合／待补全”组级状态及同一确定性计算结果，一一对应；原“信息不足”统一称为“待补全”，不另设同义状态。首版展示组数，不额外展示合格组百分比。
- 判定顺序：存在已知未满足的目标则为“未符合”，可同时提示缺失字段；否则缺必要判定信息为“待补全”；全部目标满足才为“符合目标”。不能只因缺失信息判为未符合。
- RIR 使用已确认处方的显式接受区间，包含端点，没有隐藏容差；单值按同值上下界处理。次数同样按已确认区间判定，超出上界不算符合，但不代表该组无效，不能在复盘时修改标准。
- RIR 接受非负有限数值，包括小数，不自动取整；负数、非有限数值不得通过校验。处方优先使用整数或明确区间，不从模糊语言推导小数；模糊表达保留原文并询问，未明确时结构化 RIR 可空。
- 无对照安排、额外组或不适用次数＋RIR 的训练不进入三桶，单独展示实际表现，不以待补全为由要求补造目标。
- 组级处方判定与整条记录的正式有效性分开：正式记录的组可因缺 RIR 判为待补全，但已确认的重量和次数仍可参与 PR；整条训练记录处于草稿或待补全时不参与 PR。共用“待补全”用语不意味着把不同对象的状态混成一个状态。
- Agent 复盘报告是否完成不作为 PR 条件，也不得由 Agent 重新解释或改写工作台三桶数值。

### 待补全记录转正式

- 转正式条件为“必填事实完整 + 用户确认最终草稿 + 后端校验通过”，采用整条记录确认，不做组级部分提交。正式提交继续遵守草稿隔离、幂等、版本检查及原子事务。

| 内容 | 必填边界 |
|---|---|
| 日期 | 实际发生日期明确；“今天”等相对日期解析后在草稿展示具体日期 |
| 归属 | 新增、补充或更正明确；目标不唯一必须询问 |
| 动作 | 标准动作及必要器械变式明确 |
| 组类型 | 最终草稿明确热身组或工作组；用户未说时不得静默认定，须展示并确认 |
| 完成数据 | 实际组数与每组次数／时长明确，热身摘要除外；外加负重次数型还须重量、单位及负重口径 |
| 计划关联 | 可空；关联时准确匹配安排 |
| 确认 | 用户确认最终草稿，后端校验通过 |

- 外加负重次数型保存组数、每组次数、重量、单位与负重口径；自重次数型保存组数和每组次数，不虚构 0kg；计时型保存组数、每组时长及单位，不强填次数或 RIR。
- 当前不建设器械辅助／配重抵消的“辅助负重型”。人工辅助是执行信息，不是动作记录类型。
- “递增至 60kg”等热身摘要保留原文，不强迫补齐逐组明细，不进入精确组次统计，不因此阻塞其余明确事实转正式。
- 训练反馈可选，确认卡可主动询问；RIR、动作质量、中断原因、辅助次数可空。“力竭”或“有人辅助”不自动转换为 RIR。
- 未报告疼痛只能保存为未报告，不能改写成无疼痛；明确疼痛时保存事实并触发既定安全处理，不把事实记录等同于可执行推荐。
- 无体感反馈不阻塞记录或后续建议，按用户目标、既定渐进方式和可信记录提出调整；不将缺反馈视为正常、轻松或默认加重条件，计划变更仍须确认。
- 正式记录与完成一次计划训练分开，完成率仍使用独立条件；补全不等于自动提交，更正草稿未确认前旧正式版本仍有效。

### 人工辅助、保护与 PR 边界

- 异常申报制：未提辅助时最终草稿显示“无辅助”，用户确认后视为独立完成，不在确认前当作正式事实，也不逐组额外追问。
- 用户说“有辅助”等含义不明时必须询问：仅有人旁边保护，还是有人实际接触、发力帮助完成动作，不自行选择。
- 独自完成或有人旁边保护但全程不碰杠铃、未发力帮助完成动作，按独立完成；实际帮助深蹲起立、卧推推起等标为“有辅助”。
- 人工辅助组可正式保存，计入实际工作组及总次数并标明辅助，不能把真实完成抹掉；重量仍为实际器械重量，辅助次数知道则记、不知道可空，不估算朋友承担的重量。
- 人工辅助组排除普通重量／次数 PR，不新增辅助 PR，也不自动拆算独立完成次数。辅助标记不单独阻止记录转正式或主导计划调整，不自动推导 RIR、强度匹配或加重条件。

### 一天多练与 PR

- 每次训练具有独立身份，日期不唯一。同日可以记录多次独立训练；给同次训练补充一组、同次安排分多次反馈，不自动变成新训练。
- 对“补充同次训练还是新增一次”“对应哪个安排”有歧义时，在确认卡前询问用户；不做早晚训练模板、自动拆分或复杂排程，不改变全局单 Agent Run 架构。
- PR 仅使用正式有效记录最新修订中的可比较、独立完成工作组；排除草稿、待补全训练记录、作废、旧修订、热身组、回归期数据及人工辅助组。旁边保护但全程不接触、不发力帮助完成动作不算人工辅助。
- 待补全训练记录经补全并由用户确认成为正式有效记录后自动参与 PR，无需另行确认“纳入 PR”；正式写入继续遵守既定草稿确认、版本检查及事务规则。
- 无计划关联的正式有效记录可贡献 PR，但不是执行度证据。缺 RIR 本身不阻止正式确认或已确认重量、次数参与 PR。
- 同一动作、器械变式、负重记法分别比较；单位可以换算，单只哑铃重量与双只总重不能直接混比。
- 最高重量要求至少一次明确完成的次数；同重量最高次数按单组计算，不累计多组。自重、计时、反向辅助负重不套用“重量越大越好”的 PR，首版保留实际表现，不新增特殊 PR 算法。

### 验收用例（待实现验证）

- 同一版本 W1 截至当前应训练 3 次，正式确认完成 2 次、漏练 1 次，另有额外训练 1 次：完成率为 2/3（66.7%）；事后补练不改变该漏练及分母。
- 训练日到达后，删除或改期该次日程被拒绝；在执行相关训练前确认减组仍可生效且立即落盘，事后减组不能改写执行标准。
- 计划版本从周四开始，W1 为该周四至下一周三，W2 从下一周四开始；新版本没有应训练次数时显示“暂无”，旧版本数据不迁移。真实补录或更正仍可更新旧版本统计。
- 同一天新增两次独立训练得到不同身份；对同次训练补充记录不增加训练次数，同次安排无论反馈几次都最多贡献一次完成。
- 对目标 8–10 次、RIR 1–3：9 次且 RIR 2 为符合目标，6 次且 RIR 空为未符合，9 次且 RIR 空为待补全；工作台与复盘均显示“符合目标 1 组／未符合 1 组／待补全 1 组”，不另显示信息不足状态或百分比。
- 目标 RIR 1–3 时，1、1.5、3 均可符合，3.5 不符合；负数与非有限数值被拒绝，小数不取整，模糊表达不被擅自转换。
- 一条正式有效记录的工作组缺 RIR、但重量与次数已确认：组级处方判定可以待补全，重量／次数 PR 仍可参与；整条待补全训练记录不进 PR，补全并确认正式有效后自动参与，不受复盘报告是否生成影响。
- 同动作及变式下，正式有效工作组 60kg 分别完成 8、10 次，同重量 PR 为 10 而非 18；更正或作废后按最新有效记录重算。

- 深蹲先独立完成 100kg，一周后实际由他人帮助完成 110kg：后者可成为正式工作组，但 PR 仍为 100kg；若用户确认仅旁边保护、全程不碰杠铃并独立完成，则满足其他条件时可更新为 110kg。
- 用户只说“有辅助”时，确认前询问保护还是实际帮助；未提辅助时最终草稿显示无辅助，经确认后按独立完成，不自动把保护写成辅助。
- “热身递增到 60kg，70kg 工作组 5×5，最后两组朋友实际发力帮助”且动作、日期等已明确：热身摘要不强求逐组补齐；正式工作组为 5 组、25 次，其中 2 组有辅助并排除 PR；无体感反馈或 RIR 不阻塞转正式。

## 业务模块职责

| 业务部分 | 负责什么 | 不负责什么 |
|---|---|---|
| 档案与安全限制 | 训练目标、经验、器械、时间条件、动作限制与红旗阻断规则 | 医学诊断、Agent 自行解除限制 |
| 动作目录 | 标准动作、别名、器械变式、动作模式、可推荐标记、本地媒体关联 | 全量动作数据集、独立内容管理后台 |
| 计划与训练指导 | 计划版本、今日训练、校准与渐进、状态调整、中断接回、使用时安全复核 | 自动启用计划、复杂周期系统 |
| 训练记录与更正 | 实际完成的动作和组数据、记录校验、更正留痕 | 擅自补造 RIR、直接覆盖记录而不留痕 |
| 统计与复盘数据 | 确定性计算完成率、符合处方目标的工作组及三桶状态、PR 等，提供数据与缺失项 | 让模型计算或修改统计数值；Agent 仅基于这些数据解释与复盘 |

- 以上是同一 Python 进程内的职责划分，不是独立服务，也不要求每项职责对应一个复杂子系统。
- 接回、校准、动作替代属于计划与训练指导的业务流程，不单独拆成大模块。
- PPL 作为首版模板数据，不写死为唯一可表示的计划结构，也不建设模板插件系统。
- 共用应用层草稿确认流程：领域工具生成草稿，前端展示内容与 Diff 并允许轻量纠错，用户确认后执行版本检查、领域校验和原子提交。
- 领域规则由业务代码负责，应用层负责串联流程和事务；规则不塞进 Agent 框架，也不依赖 Prompt 充当正式写入的安全校验。
- 模块职责不改变已确认的受限组合草稿边界：直接依赖的档案与计划变更可由应用层在同一事务内提交，不因模块划分而强制拆卡。
- 表名、字段、索引和文件组织属于实现细节，不逐项拍板；涉及新的业务语义、事务边界或验收变化时仍须另行确认。

## 业务交互与确认边界

- 对话是唯一业务变更发起入口；业务页面可独立查看，但不直接编辑正式业务事实。
- 草稿卡展示结构化结果和变更 Diff；允许关键字段轻量内联纠错，例如重量、次数、日期，纠错只修改待确认草稿，展示结果与 Diff 随之更新，不自动提交。
- 所有正式写入都必须由用户对最终草稿再次点击确认，并通过业务接口校验；卡片纠错不替代最终确认。

| 业务对象 | 首版交互边界 |
|---|---|
| 档案 | 查看为主，通过对话修改；草稿卡可修正单个字段 |
| 动作限制 | 通过对话增删，必须再次确认，不能在页面直接静默删除 |
| 训练计划 | 通过对话修改并进行版本化确认；不建设完整计划编辑器 |
| 训练打卡 | 自然语言录入；确认卡允许纠正动作、重量、次数和 RIR |
| 历史正式记录 | 首版只查看；通过“发起更正”进入对话并产生新草稿，确认后生效且保留修改痕迹，不直接覆盖而不留痕 |

## 当前计划的使用时安全复核

- 使用当前计划提供训练指导时，按最新动作限制复核整份计划，而不只检查当天的动作。
- 发现任一冲突后，整份计划暂不作为可执行训练建议；仍可查看旧计划，并明确提示冲突与阻断原因。
- 通过对话生成修订草稿；经领域校验与用户确认形成正式计划版本后，才可恢复基于该计划的训练指导，不自动删除或替换原计划动作。
- 阻断不妨碍历史查看或记录用户实际已发生的训练；事实记录不等于推荐执行其中的动作。
- 红旗症状独立阻断常规训练处方，不能因计划修订成功而自动解除。
- 首版采用使用时复核，不建设后台巡检，也不引入计划部分可用的状态。
- 验收用例（待实现验证）：当前计划含卧推，用户确认新增卧推限制后，再请求该计划任一训练日的指导，均不得获得基于旧计划的可执行处方；旧计划与历史仍可查看，实际训练仍可记录。

## 草稿生命周期与业务事务

### 端到端链路

```text
自然语言输入
→ Agent 提取意图并调用领域工具
→ 将生成所用数据的 context_version 记录为 base_business_version，生成结构化草稿（Pending）
→ 展示草稿卡片、结构化结果与变更 Diff，允许关键字段内联纠错
→ 用户点击“确认采纳”
→ 数据库事务内检查版本并复查领域规则
→ 同一事务内写入正式业务数据并将草稿标记为 Committed
```

- 草稿态隔离指不修改正式业务事实，沿用单 SQLite 数据库的持久化边界，不另建“草稿数据库”。
- `context_version` 是统一的用户业务版本号，不是模型上下文或压缩机制；草稿中的 `base_business_version` 保存这一版本的生成基线，不引入第二套版本计数器。草稿必须绑定实际生成所依据的数据版本，不能在生成结束后补标为最新版本。
- 每次成功提交正式业务变更使 `context_version +1`，包括档案、伤病/动作限制、器械条件、正式计划变更或恢复、训练安排及调整的确认、训练记录新增、更正或作废；同一次受限组合提交只递增一次，不按修改的表或对象数量递增。
- 聊天、草稿生成与内联纠错、拟议档案变更暂存、运行轨迹、模型设置不递增 `context_version`。
- 草稿生命周期为 Pending／Committed／Discarded；过期是业务基线冲突，不替代已丢弃状态。确认时先处理已提交草稿的幂等返回，再拒绝已丢弃草稿；不能因后续版本变化而把重复确认误报为草稿过期。
- 对可首次确认的草稿，在确认事务内严格复核 `draft.base_business_version == user.context_version` 及用户所见草稿修订版本，拒绝已被修改的草稿，并以最终草稿内容复查领域规则；前端纠错不能绕过后端校验。含拟议档案变更时，先校验补丁，再按应用该补丁后的拟议条件校验调整后的计划，不能只按旧器械条件校验。
- 版本检查、领域规则复查、正式写入、统一业务版本递增和草稿状态变更作为一次原子提交，任一步失败都不得留下部分正式写入或版本递增。
- 接受保守拦截：正式业务变更成功提交后，所有旧版本的未提交草稿均过期，即使该变更实际与某份草稿无关。
- 验收用例（待实现验证）：同一版本生成两份草稿，第一份成功提交后，第二份首次提交必须返回 `draft_stale`；重复确认第一份仍返回原结果，且不重复写入、不再次递增版本。
- 事务内的规则复查是本地确定性校验；模型调用与重算在事务外进行，遵守既定的“不跨模型请求持有数据库事务”约束。

### 受限组合计划草稿

- 暂存不是短期记忆，也不新增任何记忆系统；尚未确认的业务变更保存在 SQLite 的现有计划草稿中。
- 正式档案仍是长期档案事实的唯一来源；用户确认前绝不修改。草稿中的拟议条件只用于这份草稿的计划调整与校验，不能被当成已确认的长期事实。
- 仅允许同一次用户意图中具有直接依赖关系的变更组合提交；不支持任意跨业务拼装，不建设通用组合草稿系统。

计划草稿增加以下字段：

| 字段 | 含义 |
|---|---|
| `proposed_profile_patch_json` | 可空，保存拟议档案变更，例如 `{"equipment":["dumbbell"]}` |
| `base_business_version` | 草稿生成时读取的统一业务版本，即当时的 `user.context_version` |

“以后只能用哑铃，帮我调整计划”的处理流程：

1. 读取当前档案、限制和计划，以及对应的统一业务版本。
2. 将“长期器械改为仅哑铃”保存在计划草稿的拟议档案变更中。
3. 基于该拟议条件生成调整后的计划；模型生成在正式提交事务之外进行。
4. 用一张卡展示长期器械变更及计划 Diff，不要求先单独确认器械变更。
5. 用户确认时，在同一数据库事务内重新检查统一业务版本，并复查拟议档案变更及新计划的领域规则。
6. 同一事务内更新正式档案中的可用器械、激活新计划版本、废止旧计划版本、将草稿标记为 Committed，并使统一业务版本 +1；旧计划版本保留历史，不删除。
7. 任一步失败则全部回滚；用户拒绝则丢弃草稿，正式数据与统一业务版本不变，已丢弃草稿不得再提交。

“今天只能用哑铃”只作为当次训练条件处理，不写入 `proposed_profile_patch_json`，也不修改长期档案。

验收用例（待实现验证）：确认前正式档案和当前计划均不变；确认后档案与新计划一起生效且版本只递增一次；任一步失败均不留下部分正式变更；重复确认不重复提交；“今天”的条件不污染长期档案。

### 过期拦截与一键重算

- 版本不一致时返回 `409 Conflict`，机器错误码为 `draft_stale`，并指出相关变更项，例如“已新增动作禁忌”；不得直接提交旧草稿。
- UI 提供“按最新数据一键重算”按钮，以最新业务上下文生成新草稿（如 draft-v2），并以 `parent_draft_id` 关联旧草稿。
- 新草稿展示与旧草稿的 Diff，以及将对正式业务数据产生的变更；用户必须再次确认，新草稿才可生效。
- 一键重算是对话与 Agent 变更链路的快捷操作，不是独立业务编辑入口；若触发 Agent 执行，仍遵守全局单 Run、用户取消等既定应用层约束。
- 不做自动合并，也不因用户曾确认过旧内容就自动采纳重算结果。

## Provider 密钥与数据目录约定

- Web 设置页支持录入、替换和显式删除 API Key。
- Provider 查询接口默认只返回 `has_api_key`；仅在确有识别需求时才返回掩码。
- 完整 Key 不得进入响应、日志、Trace、`run_events` 或异常详情。
- 模型调用时按需从 Provider 配置读取 Key，用完不得持久化到其他表。
- Web 提供“打开数据目录”按钮，但不提供数据库在线下载。
- 服务停止后才允许用户手动复制或删除数据目录；运行中备份必须使用 SQLite Backup API。

## SQLite 持久化决策

### 连接与事务

- FastAPI 生命周期内保持一个 `aiosqlite` 连接，不使用连接池。
- 所有数据库操作通过同一个 `asyncio.Lock` 串行访问，包括读取和单语句写入。
- 多语句事务从 `BEGIN` 到 `COMMIT` 或 `ROLLBACK` 全程持有该锁。
- 启用 WAL、外键和 `busy_timeout`。
- 事务只包含数据库操作，绝不跨越模型请求、工具执行或 SSE 推送。

### 最小运行时表

| 表 | 职责 |
|---|---|
| `conversations` | 会话 |
| `messages` | 用户与 Agent 消息 |
| `runs` | 一次 Agent 执行及其状态 |
| `run_events` | 后台工具轨迹、状态变化和指标；不承担客户端事件补读契约 |

业务表职责已于 2026-09-07 收口：11 张业务表采用 SQLite 关系骨架、不可变 JSON 处方快照、完整训练修订与库内 Markdown 复盘正文，见根 PLAN.md“业务表设计”；尚未授权建表或业务实现。前端展示契约不必直接复制数据库表。

固定业务时区、到期日程锁定、新计划启用时原子取消旧版未来未锁定日程并生成新版日程、`[开始日期, 复核日期)` 生成边界亦按根计划执行；不再将这些列为待设计业务语义。

### Run 与事件约定

- `runs.status` 仅允许 `pending | running | completed | failed | cancelled`。
- 正常状态流转为 `pending → running → completed | failed`；用户可以将 `pending` 或 `running` 转为 `cancelled`；所有终态不可恢复。
- `runs.client_request_id` 全局唯一；先按该字段查重，相同客户端请求返回已有 Run，不重复创建，再检查是否已有活跃 Run。
- 已有活跃 Run 时，不同请求返回 `409 conversation_busy`，不创建消息或 Run。
- `runs.error_code` 保存机器可读错误码；重启中断使用 `interrupted_by_restart`。
- `run_events.id` 使用 `INTEGER PRIMARY KEY AUTOINCREMENT` 作为数据库行身份，不作为前端恢复游标；首版不做事件 ID 补读或重放。
- `run_events` 使用 `event_type + payload_json`；不为每种轨迹建立独立表。
- 回答实时流式展示，合并文本分批持久化，不逐 Token 或逐传输块写库；取消、失败及断线后可恢复已保存部分，最后尚未落盘片段允许丢失。部分回答不冒充完整成功 Assistant 消息。
- 用户消息与 `pending` Run 在同一事务创建。
- Assistant 消息与 `completed` 状态在同一事务提交，且状态更新必须检查原状态为 `running`。
- 用户点击取消后，以条件更新将 `pending` 或 `running` 改为 `cancelled` 并在同一事务追加取消事件；取消后不得再写 Assistant 消息或改为其他终态。
- 取消会尽力中断当前模型请求并禁止启动后续模型调用或工具；已经开始且无法安全中断的调用允许收尾，已发生的副作用不自动回滚，唯一执行名额在底层调用实际退出后才释放。
- SSE 断开、页面刷新及客户端暂时离线均不触发取消。
- 手动重试创建新 Run，通过 `retry_of_run_id` 指向旧 Run，不复活旧记录。
- Schema 迁移完成后，在一个事务内将遗留的 `pending`、`running` 改为 `failed`，写入 `interrupted_by_restart` 并追加对应错误事件。

## 当前架构不变量

1. Agent 执行句柄可以存在于内存，但任务状态、消息和轨迹必须持久化到 SQLite。
2. SSE 只负责实时展示；断线或刷新后通过业务接口查询 SQLite 中的 Run、已保存会话内容及草稿当前状态，替换本地展示，不重放事件。
3. 服务重启后不恢复未完成任务，也不自动重试。
4. 不引入 Redis、Celery、独立 Agent Worker 或其他外部任务队列。
5. 全局只执行一个 Agent Run，同一时刻只允许一个会话发起对话；首版不支持 Queue 或 Steer。
6. 新增依赖和模块必须在对应功能讨论时再拍板。
7. Agent 只能提出业务变更草稿；正式业务事实的变更必须由用户点击确认按钮，经业务接口校验后提交，自然语言同意不直接生效。
