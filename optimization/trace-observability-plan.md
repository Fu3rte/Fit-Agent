## 1. 要拿到的数据

每次 Agent 执行记录一条 Trace。
Trace 中的 Span 表示一次具体操作，记录它的耗时、结果和必要属性。
通过本地命令查看一次执行的明细，或统计最近 30 天的指标。

采集以下指标：

- 整次运行耗时、首次正文输出延迟。
- 每次模型调用耗时、首次正文输出延迟、Token 与缓存用量。
- 每次工具调用耗时，以及已有的执行、后处理耗时。
- 压缩次数与耗时，包括压缩中的摘要模型调用。
- 确认保存耗时。
- 各类调用次数、失败率、取消率、平均耗时、p50、p95、最大耗时。
- 每组最慢的 20 次调用。

指标来自真实执行与模型返回值。
统计结果注明时间窗口和有效样本数。

## 2. 采集方式

参照 `D:/repository/pi/packages/telemetry` 的三个设计：

- 显式传入父上下文，子操作从父 Span 创建。
- 用 `start_span(name, attributes, callback)` 包住操作，等待 callback 完成后自动结算。
- 在运行内存中收集结构化记录，存储由采集模块统一负责。

callback 恰好执行一次，业务返回值和原始业务异常继续传递。
观测故障隔离沿用 Pi 的 Adapter Contract：记录方法保持被动，观测失败允许缺样。
创建 Span 失败时，使用无记录上下文继续执行同一个业务 callback。
属性更新、状态结算与观测存储的故障均保持业务结局不变。
业务与观测同时失败时，原始业务异常继续传播。
Span 支持补充白名单属性和显式设置结果。
已结算 Span 的迟到属性写入保持无效。
所有必要子任务结束后，父操作才能结算。

一条 Trace 使用一个运行级记录器。
根身份使用 `uuid4().hex`，子 Span 使用该 Trace 内从 1 递增的整数。
根 Span 的编号为 1，父编号为空。
业务关联直接记录已有的 `session_id`、`run_id`、`operation_id`。
幂等查询通过已有业务身份查找观测记录。
编辑和重新生成各自建立新 Trace，Steering 使用当前运行的上下文。

## 3. 在哪里记录

| Span | 开始与结束 | 接入位置 |
|---|---|---|
| agent_run | 请求受理至运行终态提交完成 | `interfaces/http.py` 的受理与 coordinate |
| turn | 一轮开始至模型、工具及本轮收尾完成 | `agent/agent_loop.py` |
| model | 发起模型请求至对应响应流关闭 | `ai/stream.py` 与模型适配器 |
| tool | 工具调用准备至执行和后处理完成 | `agent/tool.py` |
| compaction | 压缩开始至检查点提交完成或失败 | Agent 压缩入口 |
| confirmation | 已受理确认开始校验至保存结果确定 | 确认 HTTP 入口与确认服务 |

Agent 根 Span 包含请求投影耗时。
循环结束后，根 Span 继续等待现有运行协调器提交终态。
根结果沿用真实运行结局；业务终态提交失败时，根 Span 记录 failed。
这个诊断状态不会更新业务库，状态恢复复用现有 coordinate 与 recover_interrupted。

Turn 下的模型与工具分别创建子 Span。
并行工具共享 Turn 父 Span，各自拥有独立编号。
Compaction 下的摘要调用创建 model 子 Span，并标记调用用途。
确认保存使用独立 Trace，通过已有 operation_id 查询。
同一已受理操作的重复请求复用其执行结果和观测记录。

模型 Span 覆盖响应流的消费与关闭。
取消、异常和提前关闭均参与收尾。
工具的执行与后处理耗时复用现有测量。
准备阶段拒绝执行的工具保留实际结果，执行耗时为空。

`first_text_ms` 记录首个非空正文增量。
Agent 从受理时计时，到正文通过现有安全检查并进入 SSE 队列时结束。
模型从请求开始计时，到首个非空正文增量时结束。
这两项分别反映服务端首正文输出和模型首正文输出。
浏览器绘制与网络传输时间属于客户端测量范围。

## 4. 保存与查看

使用现有 `aiosqlite`，写入 `backend/data/trace.db`。
数据库只保存一张 `spans` 表，根操作也作为 Span 保存。

执行期间记录保存在内存。
根操作收尾后，一次事务尝试写入整条链路，随后释放记录器。
观测写入失败允许整条 Trace 缺样，记录器仍需释放。
正常完成、失败和协作取消都走同一收尾路径。
HTTP 主事件循环负责数据库连接与最终写入。
执行线程显式接收记录器和父 Span，登记操作时保护共享内存。
最终写入等待执行线程与子任务结束。
成功路径顺序为业务终态提交、根 Span 结算、尝试写入 Trace、发送终态通知或返回确认响应。
纯观测故障隔离后，终态通知继续沿用真实业务结果。
根耗时截止业务终态提交，随后的观测写入可能增加终态通知等待时间。

保留按根开始时间计算的最近 30 天记录。
启动和每次链路写入时，按 Trace 整体清理过期数据。
本地报告只读取该时间范围内已落库的终态链路。

通过 `python -m app.agent.trace_report` 输出 JSON：

- `metrics`：分组指标与最慢调用。
- `show --run-id <UUID>`：一次 Agent 执行的全部 Span。
- `show --operation-id <UUID>`：一次确认保存的全部 Span。

命令从 `backend/` 目录执行。
命令与数据字段见[数据与报告契约](trace-observability-contract.md)。
聊天 HTTP、SSE 和业务 JSON 保持现有契约。

## 5. 前端耗时展示

在每次回答的消息区域底部显示运行用时。
复用现有运行与历史接口中的 started_at、finished_at，取时间差并转换为秒。
已有终态后的历史刷新负责取得最终起止时间。
运行中或结束时间未知时保持现有界面；有完整起止时间时展示。
该值表示业务记录的 UTC 时间差，系统时钟调整可能影响测量。
本地 Trace 报告中的 duration_ms 继续使用 perf_counter。
展示层传递已有时间字段，HTTP、SSE 和业务 JSON 字段保持现状。
用时以一行文本显示在该轮回答条目之后、状态与未知操作提示之前，容器、字号与颜色沿用既有消息展示。
数值取 UTC 毫秒差除以 1000，按一位小数呈现，起止相同显示 0.0 秒。
启动恢复的中断运行结束时间为空，按结束时间未知保持原有界面。

## 6. 状态与安全

Span 的终态为 completed、failed、cancelled。
工具返回 is_error 时记为 failed。
模型完整返回合法 length 响应时记为 completed。
Agent 的输出上限结局沿用业务失败状态。
确认结果以真实保存结果为准，授权与幂等逻辑保持现状。

只记录操作名、可信身份、模型名称、用量、时间和受控错误码。
属性由现有 Pydantic 按操作类型校验，并执行现有凭据检查。
对话、伤病信息、附件、工具参数与结果、凭据和原始异常详情保持在既有安全边界内。

目标契约中的故障隔离仅限运行中的纯观测操作。
观测字段校验或凭据检查失败时拒绝相应记录，保持敏感信息白名单。
业务输入、公开内容、授权和保存前校验继续遵循现有安全与异常处理规则。
业务保存已经提交时，观测故障保持已提交结果和终态通知的业务结局不变。
业务异常、协作取消与进程退出继续沿用现有控制流。
落库事务在 BEGIN 至 COMMIT 的任一环节失败时同批回滚并结束本次事务，同一连接继续承接后续 Trace。
开库初始化的任一步骤失败时关闭本次新建连接，初始化错误保持原样传播，观测句柄获取继续返回空。
本地报告的参数、数据校验和数据库读取错误直接报错。
流关闭及操作状态恢复复用现有协调机制。

## 7. 样本边界与验收

已确认采用内存收集、收尾整批写入。
已接受进程强制退出可能丢失尚在内存的本次 Trace。
已提交的业务记录继续保持真实状态。
指标描述已采集、已落库的样本；异常退出或纯观测故障可能缺样。
终态通知确认真实业务结果；对应 Trace 可能因观测故障缺失。

验收覆盖真实模型调用、并行工具、失败、取消、断连、压缩与确认幂等。
同时验证父子关系、计时边界、缺失用量、统计公式、30 天清理和敏感信息边界。
提交锁冲突后的事务收尾与同连接恢复、初始化清理故障后的连接关闭使用真实 SQLite 与真实触发器验证。
测量一次事务写入的耗时及真实运行的额外开销。
实现代码由用户派发的 agent 编写与修正；测试代码编写与实际运行由 subagent 负责并回报证据，文档由原主会话维护。
