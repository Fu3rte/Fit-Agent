# Fit-Agent Prompt Cache 优化方案

## 1. 已确定的范围

本方案包含四部分：

1. 模型请求投影与适配器的稳定性。
2. 业务上下文 `custom_message` 的持久化与协议转换。
3. 后端固定 5 分钟的缓存保留策略目标。
4. 逐模型调用的缓存观测与回归验证。

当前没有需要新增拍板的方案项。服务商能力核验按用户要求暂停；具体 TTL 请求参数在恢复核验后，依据服务商协议确定。

本文件记录设计约束与验收要求，业务实现尚未修改。

## 2. 当前问题与证据

会话树中的记录保持追加，模型请求还经过上下文转换与协议适配。

当前 `dynamic_system_message()` 每次请求前生成 `business_context`，由 `transform_context` 追加为临时 `SystemMessage`。该内容没有持久化，下一次请求重新生成。

`get_current_system_message()` 合并全部系统消息，同名 `sections` 使用最新值。OpenAI 与 Anthropic 适配器将合并后的内容放入请求头部的系统提示词。

工具执行、提案关联与 Steering 会改变业务上下文，进而改变请求头部。KV 状态依赖此前的 token 序列，首个变化点之后的历史失去原前缀复用条件；变化点之前仍可能命中。

已通过生产 `to_openai_request` 的本地断言验证：

- 追加新的同名系统 section，会改变第一条请求消息。
- 工具定义与普通对话内容可以同时保持不变。
- 仅改变消息 timestamp，不改变最终序列化请求。

相关源码：

- `backend/app/interfaces/http.py`：`dynamic_system_message`、`transform_context`、`message_nodes`。
- `backend/app/ai/context.py`：`get_current_system_message`、`get_current_system_prompt`。
- `backend/app/ai/api/openai_completions.py`：`to_openai_request`。
- `backend/app/ai/api/anthropic_messages.py`：`to_anthropic_request`。

该验证说明当前前缀变化机制；它尚未量化对 P0 实测 20.2% 命中率的因果贡献。

## 3. 业务上下文消息

### 3.1 承载内容

内部增加业务上下文 `custom_message`，承载后端主动生成的上下文元数据：

- 业务时区与对应真实用户节点的业务日期。
- 当前处理的 `request_entry_id`。
- 模型可见来源节点、工具调用与业务提案的关联。
- 待确认提案的定位、展示节点与状态引用。

画像、计划、训练记录等真实业务工具返回值继续使用现有 `toolResult`。

内部上下文事件由后端生成，没有对应的模型工具调用。工具结果继续遵循真实 `tool_call_id` 配对规则。

### 3.2 持久化与追加规则

- 资料事件持久化到对应会话分支，保留固定内容、来源与发生位置。
- 新增或变化的资料追加为新事件。
- 已发送的历史事件内容与位置保持不变。
- 资料事件按实际变化生成，控制重复节点信息的规模。
- 分支重放与重启恢复得到相同的历史资料内容和顺序。
- 新事件表达更新后的资料；历史资料保留其发生时的事实。

### 3.3 模型协议转换

`convert_to_llm` 将内部资料消息转换为原位置的 user-role 内容，并明确标记后端资料来源。

资料转换后的协议角色不会创建用户保存授权。真实聊天、编辑输入与附件不能创建内部资料类型。

前端继续使用真实用户消息与工具结果的既有展示逻辑，内部资料不冒充用户发送。

新增消息类型本身不保证缓存命中。缓存所需条件是最终模型输入的历史内容与位置保持稳定。

## 4. 请求投影与适配器

- `transform_context` 使用分支中的固定资料事件，重放结果保持确定性。
- 基础 system 内容保持稳定，工具声明与工具顺序保持稳定。
- 业务资料通过转换后的 user-role 消息在原位置发送，不参与 system sections 的头部重建。
- OpenAI 与 Anthropic 两条最终请求投影均纳入验证。
- 业务工具实例的真实执行身份继续由后端绑定。
- 附件引用、工具调用 ID 与参数序列化保持确定性。
- Steering 的业务日期与来源绑定到对应真实用户节点。
- 请求估算与最终模型投影使用一致口径。

本方案的资料路径使用普通 user-role 协议，中途 system 支持不属于必要条件。Pi 的 `CustomMessage` 与 `convertToLlm` 提供了相应的内部消息转换参考。

## 5. 持久化、压缩与业务安全

实现需连通消息类型定义、持久化、分支投影、协议转换、压缩与恢复。

- 编辑与重新生成使用各自真实分支的资料事件。
- 压缩检查点保留后续读取所需的业务关联。
- 被压缩资料进入固定的新上下文基线。
- 压缩前后的请求预算包含实际发送的资料内容。
- 提案来源、展示节点、完整内容读取与确认状态保持可核验。
- 后端继续独立核验来源、当前路径、快照状态及业务限制。
- 确认保存继续由独立后端接口执行。
- 缓存资料的协议角色不会扩大授权范围。

## 6. 固定 TTL 策略

- 后端固定采用 5 分钟的缓存保留策略目标。
- 前端不增加 TTL 或缓存能力配置选项。
- 对应请求参数依据已核验的服务商、endpoint、API 与模型范围映射。
- 当前 Stepfun 端点的 5 分钟支持与参数映射保持待核验。
- 客户端无法强制远端精确保留 300 秒，实际保留与淘汰仍由服务商控制。
- TTL 不改变上下文内容，也不替代请求前缀稳定性约束。

模型能力核验暂停。当前不开展服务商文档调研或远端能力测试，不声明远端 TTL 已生效。

## 7. 缓存观测

观测以每次真实模型调用为单位，关联 `session_id / run_id / message_id / compaction_id`。

记录以下信息：

- 请求时间、模型身份与 endpoint。
- 系统提示词和工具声明的 hash。
- 历史投影的首个差异位置与已知上下文事件。
- 真实 `input / cache_read / cache_write / output` 用量。

凭据不进入诊断信息；诊断产物使用已配置 gitignore 的本地目录。

命中率口径：

`cache_read / (input + cache_read + cache_write)`

普通追加、首次调用、摘要及重置后的调用分别统计。

工具声明变化、系统内容变化、模型切换、编辑、分支与压缩记录已知原因。缺少服务端证据的过期判断标记为疑似原因；无法确定的路由与淘汰原因保持未知。

最终 payload 的字节或结构差异用于定位客户端变化，它不直接等同于服务端 tokenizer 的公共前缀长度。

## 8. 验收要求与未验证边界

客户端回归覆盖：

- 普通对话和多工具循环。
- Steering 与附件。
- 重启恢复、编辑与重新生成。
- 分支重放、压缩与压缩后恢复。
- 模型切换与请求投影变化的观测。

验收检查历史消息内容、位置、工具声明与资料来源的稳定性，同时覆盖业务日期、工具配对、提案读取与确认授权边界。

服务端实际缓存效果需要真实模型验证；TTL 生效需要对应服务商协议证据。这两项在用户允许模型核验时执行。

当前状态：设计已确定；新的消息类型、资料事件持久化、请求投影与观测逻辑尚未实现。业务功能与服务端缓存效果均不能据此声明已优化。
