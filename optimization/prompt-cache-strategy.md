# Fit-Agent Prompt Cache 优化方案

数据、存储、模型转换及公开接口见 [业务上下文消息契约](prompt-cache-contract.md)。

## 1. 范围与目标

- 保持模型请求历史前缀、工具声明和协议投影稳定。
- 将业务上下文持久化为会话分支中的 `custom_message`，按发生位置转换为模型输入。
- 后端采用固定 5 分钟缓存保留策略目标，参数映射受服务商能力约束。
- 按真实模型调用观测请求变化和缓存用量。

缓存复用依赖最终 token 序列。系统提示词头部的业务资料变化会影响后续前缀复用，因此业务资料采用按位置追加的固定消息。消息类型本身不保证命中。

## 2. 业务上下文消息

内部消息使用泛型 `CustomMessage[TData]`，节点使用 `CustomMessageEntry[TMessage]`。业务具体类型为 `BusinessContextMessage` 和 `BusinessContextEntry`，固定 `role="custom"`、`custom_type="business_context"`、`display=false`、`type="custom_message"`，绑定当前真实运行。

强类型 `BusinessContextData` 承载：

- 业务时区、真实用户节点对应的业务日期及 `request_entry_id`。
- 模型可见来源节点、工具调用及业务提案关联。
- 待确认提案的身份、状态、来源、展示和确认引用。

首次资料事件保存完整基线，后续仅在资料变化时追加增量。节点按 `entry_id`、提案按 `(business_kind, proposal_id)` 合并；移出提案记录后端核实的原因。空增量、重复键及新增移除冲突拒绝入库。

`details` 为结构化依据，后端一次性生成带来源和无保存授权标记的 `content`，同事务保存。历史内容和位置不可变，重放直接使用固定文本；模板变化仅影响新事件。

资料节点自身不进入来源集合。下一次模型请求前追加变化资料；准备调用的全部结果和展示绑定完成后追加该批资料。Steering 消费后更新对应请求来源及业务日期。

真实业务工具返回值继续使用 `toolResult`，保持真实 `tool_call_id` 配对。内部资料只由后端生成，不接受普通聊天、编辑、附件或 Steering 输入创建。

## 3. 请求投影

- `transform_context` 从当前分支重放固定资料事件，内容和顺序保持确定性，每条事件仅出现一次。
- `convert_to_llm` 在原位置将固定 `content` 与时间转换为 user-role 消息；`custom_type/display/details` 不作为额外协议字段发送。
- 基础 system 内容、工具声明和工具顺序保持稳定；业务资料不参与 system sections 的头部重建。
- OpenAI 和 Anthropic 最终请求投影均遵守相同稳定性约束。
- 附件引用、工具调用 ID 和参数序列化保持确定性；预算估算与最终投影使用一致口径。
- 工具执行身份及保存授权继续由后端独立绑定和核验，资料的协议角色不扩大权限。

## 4. 分支、压缩与恢复

- 编辑和重新生成读取各自真实分支的资料事件，重启恢复保持历史顺序。
- 当前资料状态从最近完整基线开始，依次应用后续增量。
- 消息来源采用模型可见集合；待确认提案按完整分支核验，保留被压缩来源的受控读取关联。
- 资料内容计入摘要输入和请求预算，资料节点不作为真实用户回合或压缩切点。
- 压缩检查点与完整新资料基线同事务提交，执行位置和会话叶指向新基线。
- 提案来源、展示节点、状态和完整内容读取保持可核验；确认保存继续经过独立后端接口。
- 旧会话不回填过去的临时资料，原节点身份、父子关系及确认绑定保持完整。

## 5. 运行中通知与前端

资料落库后通过现有 SSE 流发送 `custom_message`，仅公开 `type/entry_id/parent_id/run_id/created_at`。`run_id` 必填且匹配当前运行。

先通知父节点身份，再通知资料节点，随后开始下一次模型消息。完整工具批次结果、Steering 消费及压缩完成通知先于相应资料通知。

前端保留隐藏结构节点、祖先链和运行归属，不生成可见聊天条目。按 `entry_id` 合并，相同身份字段冲突视为协议错误；断线和刷新沿用运行查询及历史读取恢复。

## 6. TTL

- 后端固定采用 5 分钟缓存保留策略目标，前端不增加配置选项。
- 请求参数须按服务商、endpoint、API 和模型能力映射；Stepfun 端点的支持及映射尚未核验。
- 实际保留及淘汰由服务商控制，客户端无法保证精确 300 秒。
- TTL 不改变上下文内容，也不替代前缀稳定性约束。

## 7. 缓存观测

按真实模型调用关联 `session_id/run_id/message_id/compaction_id`，记录请求时间、模型及 endpoint、system 和工具声明 hash、历史投影首个差异、上下文事件及真实 `input/cache_read/cache_write/output` 用量。

命中率为 `cache_read / (input + cache_read + cache_write)`，按真实调用身份去重；首次、普通追加、摘要和重置分别统计，零分母记 `null`，缺失用量单独统计。

已知原因包括工具或系统内容变化、模型切换、编辑、分支及压缩。缺少服务端证据的过期原因标为疑似，路由及淘汰原因无法确定时保持未知。payload 差异仅定位客户端变化，不等同于服务端 tokenizer 公共前缀长度。

凭据不进入诊断，产物写入已忽略的本地目录；观测遵循既有被动观测和错误隔离机制，不改变业务结局。

## 8. 验证要求

- 覆盖普通对话、多工具循环、Steering、附件、编辑、重新生成、分支、重启及连续压缩恢复。
- 检查历史内容、位置、工具声明、业务日期、来源、工具配对、提案读取和确认授权。
- 验证持久化、迁移、公开白名单、SSE 顺序、前端隐藏节点及请求预算一致性。
- 缓存效果须有真实模型用量证据；TTL 生效须有对应服务商协议及端点证据。局部投影验证不构成远端缓存命中结论。
