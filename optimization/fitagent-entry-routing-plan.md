## A 架构与模型

入口采用普通分类函数。每次有效用户输入通过一次模型调用返回路由结果。

路由与业务执行共用本次运行读取的 `ModelConfig`。模型名称、协议、地址与凭据保持一致。

代码根据路由结果选择公共规则、业务专项规则与允许工具集。

现有单个业务 Agent 继续执行 ReAct，负责事实读取、业务澄清、参数整理与工具调用。

同一请求的多个动作交给该业务 Agent 推进。入口分类函数没有独立工具执行循环。

保存继续由用户点击指定快照的确认按钮，经独立后端接口完成，全程无需模型。

动作检索沿用当前 RAG 契约。入口只负责业务范围选择。

## B 入口输入与结果

### 受控 state

后端从当前真实分支组装：

- 当前用户原文、附件元信息及真实用户节点。
- 理解指代所需的对话与未完成任务。
- 当前有效待确认提案、准备类型、状态及必要摘要。
- 当前画像、当前计划等业务状态摘要。

提案准备类型从真实快照取得。当前 `PendingProposalReference` 需要在入口 state 中补齐该信息。

附件与引用保持数据身份。入口上下文设定预算，保留完成当前判定必需的信息。

### 动作列表

```json
{
  "actions": [
    {"tasks": ["plan_generation"], "interaction": "cancel_pending"},
    {"tasks": ["workout"], "interaction": "new_request"}
  ]
}
```

以上结果对应：“取消刚才那份计划，再记录昨天的训练。”

普通请求返回一项 action。不同交互动作分别表达，顺序保留用户请求中的依赖。

`tasks` 允许以下标签：

- `profile`
- `plan_import`
- `plan_generation`
- `plan_adjustment`
- `workout`
- `query`
- `other`

`interaction` 允许以下动作：

- `new_request`：发起新任务。
- `revise_pending`：修改指定待确认提案。
- `cancel_pending`：取消指定待确认提案。
- `clarify`：任务或操作对象存在歧义。

入口输出纯 JSON，使用 Pydantic 严格校验。

`actions` 与每项 `tasks` 均非空；拒绝额外字段、非法标签与重复标签。

`other` 在同一 action 内独立使用。代码校验交互动作与业务类型的组合。

入口结果表达任务范围。提案 ID、用户节点及展示绑定使用后端真实身份。

业务 Agent 根据原始输入与真实候选定位目标。对象无法确定时澄清。

`clarify` 用于任务或目标歧义。已确定业务缺少的参数由该业务流程收集。

调用失败或 JSON 校验失败时明确报错，终止本次业务执行。

## C 运行接入与权限同步

### 接入时机

统一接入 `http.py` 的运行装配层。

新运行受理后，使用真实分支建立 state，在首次业务模型请求前完成路由。

覆盖普通发送、编辑与重新生成。相同操作重试复用现有受理结果。

Steering 真正消费后，更新用户节点、业务日期与任务状态，再执行入口判定。

补充输入的 state 包含仍有效的未完成任务，保持复合请求完整。

工具结果续接与压缩恢复复用本轮路由。每次新消费的用户输入触发对应入口判定。

### 统一请求策略

由同一份策略提供专项规则与允许工具集合。

模型请求投影、预算计数、压缩输入、初始工具注册表和批次工具绑定共用该策略。

执行端核对有效声明与白名单。越界工具调用被拒绝。

专项系统规则支持替换与移除，保持当前请求范围准确。

历史会话内容、节点与确认绑定保持完整。

现有 `accept_send()` 仅为空会话创建系统消息。

现有 `transform_context()` 每次从持久化分支重建投影。路由策略必须参与该投影。

## D 业务规则与工具映射

公共提示词始终保留来源忠实性、医疗风险、器械与动作限制、附件安全及授权边界。

专项规则与工具按以下任务加载：

| 任务 | 准备工具 | 必需能力 |
|---|---|---|
| profile | `prepare_profile_update` | 画像读取、完整更新、状态核对、按需动作核实 |
| plan_import | `prepare_plan_import` | 画像与当前计划依据、附件读取、按需动作核实 |
| plan_generation | `prepare_plan` | 画像准备流程、当前计划、近七日训练、可信日期与动作检索 |
| plan_adjustment | `prepare_plan_adjustment` | 调整对象、画像、最近十条完整训练、按需检索与画像更新 |
| workout | `prepare_workout` | 可信日期、当天记录、动作身份、完整记录准备 |
| query | 对应只读工具 | 画像、计划、训练、动作、提案及原操作状态 |
| other | 对话 | 公共规则 |

复合请求合并所需工具，保留全部明确任务。合并顺序固定，声明与执行一致。

修改待确认提案按真实业务类型与准备类型选择工具。

尚未采纳的生成建议修改时，继续使用 `prepare_plan`。

`cancel_pending` 提供提案读取与指定提案取消能力。

业务参数和实际依赖继续遵守原工具契约。

例如用户要求根据刚记录的训练调整计划，需要取得该记录已保存的真实事实。

### 纯附件

纯附件发送仅授权完整读取本次全部附件。

读取完成后澄清本次处理意图，等待后续文字。

此期间禁止业务准备、提案取消、保存及更新。

### 复合动作的提交结果

每个业务动作使用自身事务与既有确认流程。

已提交的取消结果持久保留。后续任务失败时准确报告各项实际结果。

用户明确表达的依赖由业务 Agent 遵守。目标有歧义时询问用户。

## E 指定提案取消契约

### 入口与参数

新增业务工具 `cancel_pending_proposal`，画像、计划和训练记录共用。

参数仅包含 `business_kind` 与真实 `proposal_id`，复用 `PendingProposalArguments`。

会话、运行、请求节点与来源节点由后端绑定。

调用使用顺序执行模式，沿用工具 harness、结果持久化与 Trace。

### 校验与状态变更

后端在一个数据库事务内完成：

- 校验目标属于当前会话和当前有效路径。
- 校验快照处于 pending，完整展示已绑定且与快照一致。
- 校验当前用户节点包含文字，且属于当前路径。
- 校验展示节点早于本次用户节点，本次用户节点早于工具来源节点。
- 校验来源节点中存在对应工具调用与相同参数。
- 校验该提案没有已受理且正在处理的确认操作。
- 将指定快照状态改为 `invalidated`。

复用既有状态、事务锁与状态更新方法。

成功结果包含 `business_kind`、原 `proposal_id` 与固定 `status="invalidated"`。

已保存、处理中、已失效、冲突、未展示、跨会话及路径外提案，按真实状态拒绝取消。

已失效提案重复取消时报告当前状态，保持业务数据完整。

成功取消仅使指定待确认快照失效，保留已保存业务数据与其他提案。

恢复内容需要重新准备、完整展示新快照，再等待按钮确认。

### 确认互斥与界面

确认受理、保存和取消使用同一数据库事务协调。

确认操作受理后，即使快照仍显示 pending，取消也须按处理中拒绝。

取消提交后，原快照确认请求被后端拒绝。

运行期间沿用既有确认按钮占用规则。

运行终态刷新历史，已失效提案移出 pending 引用，旧卡片停止提供确认操作。

当前前端的历史刷新与按钮规则继续复用。

停止 Agent 执行沿用现有运行取消机制。提案取消成功以业务工具真实结果为依据。

## F 预算、观测与验收

入口模型调用共用本次运行的配置快照、取消信号与请求预算。

入口调用使用独立用途分类，记录真实模型、题库与策略版本、结果、耗时和用量。

记录关联 `run_id` 与本轮用户节点。记录本身没有保存授权。

总延迟与成本同时包含入口判定及业务执行。

同版本基线对照检查：

- 完整动作列表与任务标签正确率。
- 工具范围正确性和必要步骤覆盖率。
- 参数值、事实来源与提案目标正确性。
- 端到端任务成功率。
- 未授权保存、错误目标保存与已知限制违反次数。
- 真实耗时分布、模型调用数、tokens、费用与缓存表现。

用例覆盖相邻意图、复合动作、提案修改、指代歧义、纯附件、文字确认、编辑、重新生成及 Steering。

取消业务覆盖三类快照、旧确认拒绝、保存互斥、跨会话、路径外、纯附件、执行取消与重启。

效果数值全部来自实际评测。样本不足时说明样本量与分布。
