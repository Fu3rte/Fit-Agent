# 动作检索增强方案

实现契约见 [动作检索数据与业务契约](action-retrieval-contract.md)，任务依赖与并行边界见 [实现顺序](action-retrieval-implementation-order.md)。

## 1. 已确认范围

- 服务动作核实、计划生成和动作替换。
- 优化目标为增强现有检索的表达覆盖、召回质量和排序能力，提高别名与描述查询命中率，确保器械约束正确、返回上下文受控。
- 查询覆盖动作别名、中英文表达、口语描述及带条件需求，例如“家里有哑铃，想练背”。
- 基于现有 1324 条动作数据，补充人工审阅的中文俗称、英文名称和筛选字段中文映射。
- 使用 Milvus 内置 BM25 与阿里云百炼 Embedding API 混合召回，通过 `hybrid_search` 与内置 `WeightedRanker` 对归一化后的分数线性加权融合。
- 已选择方案 A：名称、已审阅别名、英文名称、器械、目标肌群及中文映射和步骤组成统一 BM25 文本，与 dense 检索构成两路召回。
- 当前结果按混合检索融合分数排序；精确匹配优先保留为待评测决策的可选设计，本次不实现。
- Milvus 使用 Standalone，通过 Docker Compose 部署并持久化数据。
- Embedding 模型为 `qwen3.7-text-embedding-flash`，输出 1024 维。
- API 密钥和调用配置通过后端环境变量读取；本次交付聚焦 API 接入及检索优化。
- 搜索默认返回前 10 条简要候选，按 ID 获取完整说明；搜索与详情均限制输出体积。
- 不可用器械跨会话保存，复用画像字段 `unavailable_equipment`。
- 画像页、对话画像和待确认快照展示不可用器械清单，保存继续遵循按钮确认规则。
- 单杠、双杠、训练凳等实际设施依赖补标暂不纳入本次范围。

理论收益：提高事实命中率，减少错误推荐与重复查询；受控结果减少单次工具返回量。整轮模型输入量、响应耗时与成本收益需实际测量。

## 2. 数据与索引

每个动作对应一条 Milvus collection 记录，使用原始动作 ID 作为主键，关联检索文本、1024 维 dense 向量、内置 BM25 生成的 sparse 向量和结构化筛选字段。检索文本包含名称、已审阅别名、英文名称、器械、目标肌群及中文映射和动作步骤。

### 2.1 BM25 字段组织（已确认方案 A）

名称、已审阅别名、英文名称、器械、目标肌群及中文映射和步骤按固定编码规则组成一份 BM25 检索文本，配置一个 BM25 Function、一个 sparse 字段及其索引。dense 字段保存同一检索文档的语义向量。

混合检索固定为 `[BM25, dense]` 两路，WeightedRanker 的权重分别为 `[α, 1−α]`。名称与已审阅别名参与统一文本检索，其命中效果纳入专项评测。

统一文本的长度分布及步骤长度对名称查询的影响纳入评测。

别名允许对应多个动作，保留来源和审阅状态。歧义名称返回具体变式候选。原始目录继续提供动作身份、事实字段和完整说明。

中文分词、BM25 sparse 向量生成和向量检索由 Milvus 处理，Python 后端通过 PyMilvus 调用。中文 analyzer 与中英文混合名称的分词效果通过 `run_analyzer` 验证。目录 dense 向量通过 Embedding API 预计算并写入 Milvus；在线请求只调用 API 编码查询，BM25 路径直接提交查询文本。

Milvus 与 PyMilvus 固定兼容版本，索引配置记录 analyzer、BM25 Function、各向量字段、度量类型和检索路径。运行需要可访问的 Milvus Standalone 服务，部署采用 Docker Compose。

索引记录目录哈希、别名版本、服务地址、模型标识、维度、编码规则和索引配置。目录或编码配置变化后重建索引。配置缺失、索引不匹配或 API 调用失败时明确报错。服务商未提供固定模型版本时，记录构建时间与返回的模型信息，并在回归中检查向量一致性。

## 3. Embedding API 与环境配置

采用仓库已有的 OpenAI Python SDK，通过异步客户端调用 `embeddings.create`。

- Base URL：`https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`。
- 请求端点：`POST https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/embeddings`。
- `{WorkspaceId}` 从环境变量 `DASHSCOPE_WORKSPACE_ID` 读取，SDK 自动追加 `/embeddings` 路径。
- 模型：`qwen3.7-text-embedding-flash`。
- 请求参数：`dimensions=1024`、`encoding_format="float"`。
- 官方模型表规定单次最多 20 条文本；目录分批编码，在线请求只编码查询。

后端环境变量约定如下，业务空间 ID 与密钥由用户在本机填写：

```dotenv
DASHSCOPE_API_KEY=
DASHSCOPE_WORKSPACE_ID=
FIT_AGENT_EMBEDDING_MODEL=qwen3.7-text-embedding-flash
FIT_AGENT_EMBEDDING_DIMENSIONS=1024
```

环境配置可保存在已被 gitignore 排除的 `backend/.env`，由启动命令显式加载至进程环境。必需配置缺失或为空时立即报错。密钥仅由后端读取，禁止写入前端、日志、索引、评测证据或提交到仓库。Embedding 配置与聊天模型配置独立。

查询与目录文本使用相同模型和已冻结的编码规则。通过 OpenAI 兼容接口获取 dense 向量，稀疏召回使用 BM25。文本直接作为 `input` 发送，校验返回数量、`index` 对齐、1024 维、数值有限性及非零范数，dense 路径使用 Milvus 的 `COSINE` 度量计算余弦相似度。

目录向量写入 Milvus，成功完成数量、维度和版本校验后发布新索引。更换模型或编码配置时重新编码，避免混用向量空间。只向 Embedding API 发送检索所需文本；画像中的器械限制由后端转换为 Milvus 结构化过滤条件，并在输出时复核。

1324 条、1024 维的 float32 目录向量约占 5.17 MiB，仅为向量矩阵理论大小。API 网络延迟、配额、Token 用量和计费进入评测；具体账单以服务商记录为准。

官方文档已确认模型名称、1024 维和业务空间专属的 OpenAI 兼容接口。业务空间 ID 和 API Key 配置后，使用真实请求验证空间权限、模型可用性及返回维度。

官方资料：

- <https://help.aliyun.com/zh/model-studio/qwen3-7-text-embedding-flash>
- <https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api>

## 4. 召回与融合排序

1. 规范化查询，按显式条件确定可返回动作集合。
2. BM25 与 dense 两路分别召回，每路使用同一硬过滤条件，通过 Milvus `hybrid_search` 按主键合并候选。
3. 使用内置 `WeightedRanker`，启用分数归一化，按固定路径顺序传入权重。
4. 候选按融合分数排序，执行返回门槛、最终约束复核和结果预算裁剪。

查询规范化规则随检索配置冻结。本次不实现精确命中查找、优先分组或对应开关。

精确匹配优先保留为可选设计：查询与规范化后的名称或已审阅别名完全一致时，应用层独立获取合规动作，与混合候选按 ID 合并去重并优先展示。若评测发现指名动作漏召回或排名不满足验收要求，再依据评测证据决定是否实现。该设计仍遵守硬过滤、候选数和体积预算。

融合公式：`S = α × N_BM25(B) + (1 − α) × N_COSINE(V)`，请求顺序为 `[BM25, dense]`，对应 `WeightedRanker(α, 1−α)`。

归一化使用 Milvus 内置的度量相关映射，记录 Milvus、PyMilvus 版本与归一化设置。某动作未进入某一路召回时，该路贡献为零。每路召回深度与最终返回前 10 条分别配置，召回深度通过开发集评测冻结。

融合分数表达排序依据。无答案样本用于校准返回门槛，允许空结果；门槛与权重、召回深度、分词及索引版本绑定。

稀疏总权重偏高属于待验证假设。测试 `α = 0、0.25、0.5、0.7、0.85、1`，端点用于量化稀疏与 dense 的贡献。用开发集选择配置，冻结后评估留出测试集。

Milvus 官方依据：

- <https://milvus.io/docs/full-text-search.md>
- <https://milvus.io/docs/weighted-ranker.md>
- <https://milvus.io/docs/analyzer-overview.md>

本次候选重排采用线性融合。独立 Cross-Encoder 的引入需另有质量与耗时证据。

## 5. 器械约束与跨会话记忆

动作核实可查询受限动作并说明要求；生成与替换建议使用硬过滤。相关性分数不得覆盖器械或禁用动作限制。过滤进入候选选择过程，输出时再次校验。

器械默认遵循 PRODUCT.md：居家或户外默认仅 `body weight`，其余或未知环境默认目录器械可用；用户明确声明可用器械时按声明放行。可用声明与“只使用某器械”的显式筛选分别处理。例如“家里有哑铃，想练背”允许符合限制的徒手与哑铃背部候选。已保存不可用限制发生冲突时，遵循澄清与确认解除流程。

用户反馈“没有哑铃，换一个”时，本次检索排除 `dumbbell`。需要长期保存的限制进入画像更新流程，用户点击对应画像快照的“确认保存”后持久化。后续会话从已保存画像读取限制。用户声明器械已可用时，通过同一确认流程解除限制。

临时限制仅用于对应任务，含糊的器械名称或作用范围需要澄清。长期限制直接从结构化画像读取，动作目录索引保持与目录版本关联。

画像与计划各自确认。画像版本变化后，处理既有计划提案依据失效与重新准备；计划保存继续执行服务端限制校验。未确认的画像修改不进入长期状态。

当前目录的 `body weight` 包含依赖单杠、双杠的动作。本次过滤正确性按现有目录标签验收，实际设施可用性受标注范围限制。

## 6. 返回上下文控制

搜索默认返回前 10 条候选，包括 ID、名称、器械、目标肌群和简短字段匹配依据。设置总字符数硬上限，按完整候选裁剪，保持输出结构有效，并提供是否还有候选及后续查询所需信息。

选定候选后，按 ID 批量获取完整说明；详情工具也设置批量与体积上限。具体字符预算通过目录字段长度分布确定。

端到端统计包含搜索和详情查询的全部结果与模型输入，检查整轮上下文成本。

## 7. 验收与实验

验收依据别名与描述查询命中改善、器械约束正确和返回上下文受控，不设置检索质量提升的数值门槛。保留量化指标和逐例证据，用于评估表达覆盖、召回质量、排序能力及调参。

建议建立至少 120 条检索查询，覆盖标准名称、动作别名、中英文表达、口语描述、带条件需求和无答案。带条件样本包括“家里有哑铃，想练背”，同时检查返回动作的目标肌群相关性及器械条件符合性。相关动作按等级人工标注，允许多个合理答案。按意图与别名家族划分开发集和测试集，防止测试信息泄漏到别名维护与调参。

- 检索质量：Recall@10、MRR@10、nDCG@10、无答案误返回率；分查询类别报告，精确名称查询设置无退化检查。
- 指名查询：单独统计标准名称与已审阅别名查询的 Recall@10、MRR@10 和漏召回样本，覆盖多动作别名及硬约束排除场景；作为是否启用精确匹配优先的决策依据。
- 过滤正确性：显式约束违反数为零；条件查询同时检查目标肌群相关性、器械条件及画像中不可用器械限制。
- 结果体积：候选数与字符预算全部合规，记录结果字符数及估算 tokens 的 P50/P95。
- 端到端成功率：动作核实、计划生成、反馈后替换；固定模型和前置状态，每例三次，记录成功率、稳定通过率、重复搜索次数、详情查询次数、真实 tokens 和响应耗时。
- API 与索引：真实接口连通性、返回维度与顺序、编码耗时 P50/P95、调用次数、Token 用量、索引构建耗时、重启后的索引复用，以及鉴权失败、限流和超时的明确失败行为。
- 跨会话：新会话读取、重启读取、解除限制、重复确认幂等、未确认零提交、计划提案依据有效性。

对照组包含当前名称检索、稀疏检索、向量检索和混合检索。各组使用相同语料、别名和结果预算，并单独记录别名补充与结果裁剪的贡献。按查询类别报告相对当前检索的命中和排序改善，保留新增命中、漏召回、排序退化及无答案误返回的逐例证据。

`quantitive-index/v1.md` 为历史业务基线。实验需在同一当前提交上重测对照组，报告检索专项与端到端结果。

保存 query、约束、金标 ID、候选 ID、分数、模型和实验版本，支持人工复核及后续 LLM-as-judge。动作身份和硬约束使用程序核验，主观合理性可交由评审。

## 8. 交付边界

预计涉及 Catalog、BusinessService、动作检索工具与说明、按 ID 查询详情的工具、工具注册、别名数据、Embedding API 客户端及环境配置、索引构建、画像展示和专项测试。修改前核查调用方与回归用例。业务测试执行交给 subagent，依据其命令、退出码和输出判定结果。

本次范围为 Embedding API、Milvus 检索链路、业务约束、评测及 Milvus Standalone 的 Docker Compose 部署配置。Milvus Standalone 使用官方 Docker Compose 部署，通常包含 Milvus、etcd 和 MinIO 服务，并通过持久化目录保存数据。Python 后端连接 Milvus 服务地址；本机运行后端时常用 `http://localhost:19530`，容器内后端使用 Compose 服务名访问。

Windows 本地部署可使用 Docker Desktop 的 WSL 2 Linux 容器环境。具体版本与机器资源在部署验证时确认，Fit-Agent 整体容器化仍按用户安排处理。部署时持久化数据目录必须保留，服务端口限制本机或受控网络访问。

部署参考：<https://milvus.io/docs/install_standalone-docker-compose.md>。
