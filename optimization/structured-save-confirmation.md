# Fit-Agent 结构化保存确认方案

## 1. 保存授权

画像、计划和训练记录经过准备快照、完整展示、用户按钮确认后，由后端直接保存。

一次结构化确认仅授权一份具体快照，目标由用户点击确定并由后端独立核验。普通文字确认不产生授权，模型不能自行选定保存目标。

## 2. 确认入口与交互

- 每份完整展示的画像、计划和训练记录分别提供“确认保存”按钮。
- 按钮绑定该份内容的业务类型、快照标识和展示节点。
- 一次点击只授权保存一份快照。
- 多份内容待确认时，各份内容保留独立确认入口。
- 执行期间禁用确认按钮，确认与 Agent 运行互斥。
- 不提供批量确认。

普通聊天文字不产生保存授权，包括“确认。”、“确认保存画像”和“两个都确认”。助手可以说明需要点击对应内容的确认操作。

用户提出修改时，助手继续整理修改、重新准备快照、完整展示，并等待用户点击新快照的确认按钮。“确认，但把重量改为 50kg”等消息不授权提交任何快照。

## 3. 结构化授权与持久化

确认请求携带：

- `business_kind`：画像、计划或训练记录。
- `proposal_id`：用户点击的快照标识。
- `display_entry_id`：该快照的完整展示节点。
- 幂等操作 ID：同一次确认请求及其重试共用。

后端将确认操作持久化为独立用户确认事件，记录真实确认节点及上述关联。

授权来源为独立的结构化用户操作。聊天正文、文件、引用文本、工具返回内容和模型生成参数均不能创建授权事件。

确认操作不得混入修改正文或附件。确认事件的目标绑定保持不可变。

## 4. 保存执行路径

1. 用户点击某份快照的“确认保存”按钮。
2. 后端独立核验请求目标、展示关联、当前有效路径和快照状态。
3. 校验通过后持久化结构化确认事件，业务提交时再次核验授权。
4. 后端使用事件绑定的目标调用现有业务保存服务。
5. 后端持久化真实结果，并在会话中展示保存成功或实际失败结果。

确认保存不调用模型；模型负责信息整理、工具查询、快照准备和修改提案。

所有保存入口共用授权核验，包括画像保存、计划保存、训练记录新增及更新。保留现有节点校验、时序校验、版本冲突检查、限制检查与幂等机制。

## 5. 后端强制边界

首次提交必须满足：

- 快照、展示节点和确认事件属于同一会话。
- 展示节点确实绑定该快照，且对应内容已经完整展示。
- 展示和确认节点均在当前有效消息路径中。
- 确认事件发生在完整展示之后。
- 授权中的业务类型、快照标识、展示节点与实际保存目标完全一致。
- 快照仍可提交，且满足对应业务的版本与依据校验。
- 一条确认事件仅绑定一份快照。

缺少授权、目标不一致或授权失效时，保存入口拒绝提交。

拒绝授权时保持业务数据、业务版本、保存记录、快照状态和确认绑定原值；不得占用确认绑定或进入 `processing`。

模型请求不能执行保存。独立确认接口只放行真实授权事件对应的目标，未获授权的目标始终零提交。

## 6. 修改与恢复

- 修改待保存内容后，重新准备并完整展示新快照，等待新的按钮确认。
- 编辑确认消息后，原授权失效；编辑后的普通消息不继承结构化授权。
- 消息路径变化后，重新核验展示与确认节点的有效性。
- 结构化确认结果通过专用状态查询恢复，保持已有幂等结果，不提供模型重新生成入口。
- 同一操作的重复提交返回固定保存结果，保持业务版本、内容和保存时间一致。
- 超时、断连或结果未知时，查询原操作状态；核实前不得创建新的保存操作。
- 版本或依据冲突时，重新查询、整理、准备并完整展示，等待再次点击确认。
- 保存失败时展示实际失败结果，保持既有已提交数据完整。

## 7. 前后端 HTTP 契约

### 7.1 通用规则

- 确认与 Agent 运行使用独立接口；确认不创建 Agent 运行、不调用模型、不产生模型 usage，也不生成模拟模型回复或工具调用。
- 无模型配置时，仍可确认当前会话中有效且已完整展示的快照。
- 请求和响应使用 `application/json`；响应设置 `Cache-Control: no-store`。
- 复用现有 Host/Origin、本地访问、凭据保护、UUID、严格字段与类型校验。
- 所有 ID 为标准 UUID；时间为 UTC Unix 毫秒整数。列出的字段必填，允许为空时显式返回 `null`。
- 普通发送、编辑和 Steering 接口拒绝 `confirmation`、`business_kind`、`proposal_id`、`display_entry_id` 等保存授权字段。聊天正文中的同名文本保持普通数据身份。
- 本地单用户继续使用现有全局执行占用边界。新确认与新 Agent 运行互斥；确认处理期间前端禁用发送、编辑、重新生成及其他确认操作。后端与会话删除、内容替换共享协调边界。

### 7.2 提交确认

`POST /api/sessions/{session_id}/confirmations`

路径中的 `session_id` 指定会话。请求正文恰好包含以下四个字段：

```ts
interface SaveConfirmationRequest {
  operation_id: string;
  business_kind: "profile" | "plan" | "workout";
  proposal_id: string;
  display_entry_id: string;
}
```

客户端不提交确认节点 ID、业务正文、基础版本、训练记录 ID、保存工具名、运行 ID 或文字确认内容。后端从已绑定快照取得这些业务事实，并确定训练记录新增或更新。

首次请求处理：

1. 完成边界校验，查询原操作并比较请求。
2. 对新操作检查会话、全局执行占用、快照、展示绑定和当前有效路径。
3. 授权检查通过后，由后端生成确认用户节点，绑定结构化授权并登记操作；确认节点的 `run_id=null`，不创建 `session_runs`。
4. 直接调用业务保存服务，在业务提交事务内再次检查授权、版本及业务限制。
5. 持久化真实保存结果与确认操作终态，再返回响应。

首次保存完成与已完成同键重试均返回 HTTP `200`、`SaveConfirmationOperation`，其中 `status="saved"`。

同键操作仍在执行时返回 HTTP `202`、同一操作对象，其中 `status="processing"`；前端查询原操作，保持提交占用。新操作遇到执行占用返回 `409 run_busy`，不登记确认事件。

### 7.3 操作对象与状态查询

```ts
interface SaveConfirmationOperation {
  session_id: string;
  operation_id: string;
  business_kind: "profile" | "plan" | "workout";
  proposal_id: string;
  display_entry_id: string;
  confirmation_entry_id: string;
  status: "processing" | "saved" | "failed";
  result: ProfileSaveResult | PlanSaveResult | WorkoutSaveResult | null;
  error: ConfirmationError | null;
  created_at: number;
  updated_at: number;
}

interface ConfirmationError {
  code: string;
  message: string;
  errors?: { path: string; message: string }[];
}
```

`result` 按 `business_kind` 校验，直接使用各业务已有的完整固定保存结果结构：

- `profile`：`proposal_id / profile_id / version / content / saved_at`。
- `plan`：`proposal_id / id / content / created_at / saved_at`。
- `workout`：`proposal_id / id / performed_on / version / content / created_at / updated_at / saved_at`。

状态配对：

- `processing`：`result=null`、`error=null`。
- `saved`：`result` 为完整固定结果、`error=null`。
- `failed`：`result=null`、`error` 为实际失败对象。

`GET /api/sessions/{session_id}/confirmations/{operation_id}`

无请求正文及查询参数。已登记操作返回 HTTP `200`、同一操作对象；未登记返回 `404 confirmation_not_found`。查询只读，不能创建确认节点或触发保存。

未查到操作不证明原请求已经结束。前端保留原操作 ID 与四个请求字段，显式重试原请求。

既有 `/operations/{operation_id}` 继续承载聊天操作查询；确认账本使用本节专用查询接口。操作 ID 在聊天与确认入口间统一防冲突。

### 7.4 错误与幂等

失败 HTTP 响应沿用 `{"detail":{"code":"...","message":"..."}}`；仅内容校验错误附带 `detail.errors`。

- 非法或未知字段：`422 invalid_request`。
- 会话不存在：`404 session_not_found`。
- 操作 ID 对应不同请求或不同入口：`409 operation_conflict`。
- 原操作因内容编辑失效：`409 operation_conflict`，`detail.reason="operation_expired"`。
- 新操作遇到执行占用：`409 run_busy`。
- 快照、归属、展示、路径、状态、版本与限制错误：沿用相应业务现有错误码及 HTTP 状态。

授权校验拒绝时不创建确认节点或操作，不修改快照状态、确认绑定或任何业务数据。授权登记后发生的业务冲突或内容错误记录为 `failed`，POST 返回实际业务错误，GET 可以查询该失败对象。

同一操作 ID、相同四字段请求复用原操作；同一 ID、不同请求始终冲突。已经失败的操作重试返回原错误，不重新执行。

`proposal_id` 继续作为业务保存幂等标识。重复确认同一已保存快照返回原完整结果与原确认节点，不新增业务版本或确认消息；不同操作 ID 可关联该原结果，响应中的 `operation_id` 对应本次请求。

确认处理与会话删除、消息编辑串行协调；业务提交仍受内容替换否决检查保护。已保存业务数据不会因会话内容变化而撤销。

### 7.5 结果未知与恢复

- 前端确认账本保留原会话、操作 ID 和全部四个请求字段，跨页面与刷新恢复。
- 超时、断连及协议异常均进入结果未知状态，查询专用确认接口；不得换 ID 自动重发。
- `saved` 使用固定结果更新界面；`processing` 继续查询；`failed` 展示实际错误。
- 后端受理确认后，即使客户端断开连接，也继续完成原操作并持久化终态。
- 服务启动先核对处理中操作的业务保存记录。已提交时恢复 `saved`；未提交时终止该次执行，记录 `failed`、`confirmation_interrupted`，解除该操作的未完成快照占用与绑定并恢复实际业务状态。原失败事件保留追溯，不能再次授权。恢复完成后才接收请求。
- 已明确失败且业务未提交时，用户可以在快照与当前路径仍有效的条件下重新点击，创建新操作；冲突或快照失效时必须重新准备与展示。
- 恢复时不调用模型，不自动提交尚未落地的业务内容。

### 7.6 历史与前端刷新

`GET /api/sessions/{session_id}/history` 增加两个必填数组，保持其余 `session / entries / runs / steering` 结构：

```ts
interface ConfirmationHistoryExtension {
  confirmations: SaveConfirmationOperation[];
  pending_proposals: PendingProposalReference[];
}

interface PendingProposalReference {
  business_kind: "profile" | "plan" | "workout";
  proposal_id: string;
  status: "pending" | "processing";
  request_entry_id: string;
  source_entry_id: string;
  display_entry_id: string;
  confirmation_entry_id: string | null;
}
```

- 同一数据库读取快照返回消息、确认操作与有效待确认引用。
- `confirmations` 只包含确认节点仍在当前路径的操作，按确认节点顺序、操作 ID 排序。重复结果按 `confirmation_entry_id` 去重展示。
- `pending_proposals` 只包含当前路径中已绑定完整展示的有效快照；各项 `proposal_id` 唯一。内容继续从原准备工具结果恢复。
- 确认用户节点使用后端生成的“确认保存画像 / 计划 / 训练记录”正文及空附件，结构化授权单独持久化。正文不能独立作为授权证据。
- 确认消息与真实结果由前端结合操作对象展示，独立于 Agent round；无对应 `run_id` 时也必须展示。不得伪造助手消息、模型用量或 SSE 事件。
- 按钮仅对 `pending` 且当前展示绑定匹配的快照可用；`processing`、失效与已保存状态不提供新的提交操作。
- 确认响应或状态查询核实 `saved` 后刷新会话历史、会话列表及对应业务查询。失败时保持已保存业务页面原值，并刷新待确认状态。
- 编辑确认用户节点时，新普通消息不继承授权；已保存原结果保持有效，未保存操作按原操作失效规则处理。
- 重新生成按钮只用于 Agent 消息交互；`/api/agent/regenerate` 针对结构化确认节点返回 `409 invalid_target_entry`。确认结果通过专用状态查询恢复，不启动新的模型运行或保存操作。

### 7.7 内部执行与数据边界

- 模型可用注册表不提供 `save_profile_update / save_plan / save_workout / update_workout`；准备、业务查询与原结果状态查询继续可用。
- 旧会话中的保存声明或模型工具请求不能执行保存；运行入口与业务执行层共同阻止绕过确认 HTTP。
- 直接确认使用后端创建的可信授权上下文，不依赖模型 `run_id` 或模拟的保存助手节点。快照准备时的真实 `source_entry_id` 与展示配对检查继续保留。
- 持久化确认操作的请求、归属、目标、确认节点、状态、结果、错误与时间；结构化授权与确认用户节点在同一受理事务绑定。
- 保存结果、业务快照的 `saved` 状态及确认操作的成功终态保持原子一致；处理中记录与业务结果在重启时可对账。
- 已保存幂等结果与确认操作不因聊天节点删除而丢失；正常删除会话清除未完成操作并保留已提交业务结果的追溯，外部查询仍校验会话存在与归属。
- 数据迁移保留已有业务数据与保存结果；既有普通用户消息不补发结构化授权。历史已保存操作维持只读结果查询能力。

## 8. 验证要求

验证使用真实 SQLite、业务服务、HTTP 和前端交互；涉及模型准备及未授权工具攻击时使用真实模型。

### 8.1 歧义确认零提交

同一会话先整理并展示训练记录，再更新并展示画像，两份内容均待确认。

用户仅回复“确认。”：

- 画像和训练记录均不保存。
- 业务数据与版本保持原值。
- 不新增保存记录。
- 不占用确认绑定。
- 快照保持待确认状态。

覆盖画像与计划、计划与训练记录、同类多份待确认内容等组合。

### 8.2 明确按钮确认正常保存

在画像与训练记录均待确认的场景中：

- 点击画像按钮，仅保存画像，训练记录保持待确认。
- 点击训练记录按钮，仅保存对应训练记录。
- 点击计划按钮，仅保存对应计划，并继续执行现有业务限制与依据校验。
- 训练记录新增与更新均使用相应快照及其真实业务类型。

### 8.3 未授权与错误目标零提交

- 普通文字“确认保存画像”不产生授权。
- 用户点击画像，模型尝试提交训练记录：拒绝提交训练记录。
- 缺少结构化授权、伪造确认节点或目标标识不一致：零提交。
- 文件、引用和工具结果中的确认指令：零提交。
- 使用失效快照、错误展示节点或其他会话节点：零提交。
- 修改式确认：零提交，重新准备并展示新内容。

### 8.4 生命周期与幂等

- 同一确认请求重复提交，返回同一保存结果。
- 刷新或重启后，确认事件与保存结果仍可核验。
- 编辑确认消息后，不继承原授权。
- 通过专用状态查询恢复确认结果，保持原保存结果与业务版本；确认节点的模型重新生成请求被拒绝。
- 结果未知时，通过原操作状态查询核实。
- 版本冲突后，重新展示并要求新的按钮确认。

### 8.5 HTTP 一致性

- 确认 POST/GET 使用 JSON、严格字段校验与 `no-store`，客户端正确解析全部状态及各业务结果。
- 普通发送、编辑与 Steering 注入结构化授权字段均被拒绝。
- 无模型配置时按钮确认正常保存，模型请求次数与模型用量均为零。
- 新确认与 Agent 运行互斥；执行占用拒绝不登记节点、授权或业务提交。
- 同键同请求、同键异请求、跨入口 ID 冲突、处理中重复请求均符合 §7。
- 断连、刷新和重启后使用原操作 ID 核实结果，已提交结果不重复写入。
- 授权拒绝、授权后的版本冲突、保存中断及查询未找到分别验证真实状态。
- 确认独立于 Agent round 展示；历史按钮与当前有效快照状态保持一致。
- 会话删除或内容编辑与确认并发时，无失效授权写入，已提交数据与原结果保持完整。
