# 前端业务纵向闭环阶段计划

## 用途与边界

本文件保存已确认的粗阶段计划，作为后续逐阶段制定详细开发计划的骨架。阶段详细计划统一放在本目录，当前不提前拆解或创建空白计划文件。

- 本文件不是代码实施、真实后端联调、真实 API Key 或模型调用授权。
- 当前授权和后续覆盖规则以根目录 `PLAN.md`、`AGENTS.md` 为准；前端呈现层已拍决策存档见 `pre-prj/architecture-archive/frontend-presentation-decisions.md`（原 frontend/PLAN-FRONTEND.md 的仍有效部分），与架构正本冲突时以 `pre-prj/design-decisions.md` 及 `pre-prj/architecture/` 各章为准。
- 业务依据为 `pre-prj/PRD.md`；历史架构记录见 `pre-prj/design-decisions.md`，不因本计划自动完成历史技术选型重选。
- 现有决策文档保留原路径，本目录集中存放本阶段总计划及后续详细开发计划。

## 推进原则

按用户业务闭环推进：每阶段串起页面、对话、草稿、确认和查询，不按“先写完所有页面”推进。已有页面尽量复用，不重建一套 UI。

阶段 0–5 先用 mock 跑通；后端对应接口就绪且获得授权后，逐条闭环替换为真实接口，不必全部堆到最后联调。阶段 6 是整体验收，不是首次接后端。

每阶段同时覆盖正常、空数据、失败和冲突状态；mock 通过不代表真实链路通过。

## 阶段总览

| 阶段 | 纵向闭环 | 阶段验收重点 |
|---|---|---|
| 0．对齐第一版基础 | 修订契约与 mock → 对话运行状态 → SSE／查询恢复 → 草稿公共流程 | 断线不重跑；确认检查修订版本；已提交可幂等返回、已丢弃不可提交 |
| 1．建档闭环 | 未建档提示 → 对话收集条件 → 档案草稿 → 纠错、确认 → 档案与限制页更新 | 确认前正式档案不变；缺失事实不编造；所有业务变更仍从对话发起 |
| 2．计划启用闭环 | 根据档案提出计划 → 展示处方与日程 → 确认启用 → 当前计划及安排可查看 | 清楚展示生效范围；换计划同时展示旧日程取消；限制冲突明确阻断指导 |
| 3．训练与打卡闭环 | 查看当次安排 → 对话调整并确认 → 实际训练反馈 → 记录草稿 → 确认 → 记录与统计更新 | 区分原计划、接受安排和实际记录；支持待补全、无安排训练及同日多练 |
| 4．更正与历史闭环 | 记录页发起更正 → 对话定位训练 → 修订／作废草稿 → 确认 → 历史与统计刷新 | 不新增训练身份；旧修订可追溯；过期草稿拦截并可重算；旧复盘标记依据变化 |
| 5．复盘与后续调整闭环 | 查看确定性统计 → 对话生成复盘 → 保存并展示 → 提出后续安排／新计划草稿 → 再次确认 | 数值不由前端或模型重算；复盘建议不自动生效；校准、渐进与中断接回沿用同一确认链路 |
| 6．真实联调与交付验收 | Provider 配置 → 真实运行 → 逐条复验上述闭环 → Windows 人工验收 | mock 通过不算真实通过；检查密钥不回显、失败可理解、重启可恢复查看 |

## 后续详细计划

阶段 0 和阶段 1 的具体任务与验收清单已制定：见 `stage0.md`、`stage1.md`（经用户确认后生效，确认前不视为开工或授权）；其余阶段暂不细拆。各阶段详细计划由用户逐项制定与确认，不在本文件中预先决定尚未拍板的业务语义、技术选型或实现授权。

当前状态：阶段 0、1 详细计划已制定待确认；其余阶段仅保存骨架计划。所有阶段均不因文档落盘而视为已开工或已验收。
